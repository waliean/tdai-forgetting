# 补丁落地验证（2026-10-26）

计划里 A 阶段的任务，一次做完。结论比预期难看：**手写的三份补丁不是合法 patch，一行都应用不了**；重做之后能应用、能构建、能过类型检查，但验证过程里挖出一个真缺陷——**归档之后，记录仍然可以被召回**。

## 一、手写补丁根本不可用

三份补丁全部被 git 拒绝：

```
0001-l1-forgetting-schema.patch: error: No valid patches in input
0002-l1-recall-decay.patch:      error: No valid patches in input
0003-l1-forgetting-cli.patch:    error: No valid patches in input
```

原因是它们照着代码手写出来，只有 `--- a/...` 头与 `+` / `-` 行首，hunk 头写的是裸 ``````，没有行号行数。git 需要 ```@ -641,7 +641,12 ```@ 这种坐标，否则连要改哪一段都定位不了。

这暴露的是流程问题：**补丁不能靠肉眼写**。正确做法是在临时副本里改出真实差异，再用 `git diff` 导出。

## 二、PowerShell 的 Out-File 会把补丁弄坏

用管道 + `Out-File` 导出的补丁，内容看着与真实 diff 一模一样，git apply 却报：

```
error: patch failed: MemoryCore/src/core/store/sqlite.ts:641
error: MemoryCore/src/core/store/sqlite.ts: patch does not apply
```

因为 `Out-File` 在 Windows 上写 CRLF，上下文行的行尾跟着变成 `\r\n`，与上游（LF）逐字节比对全部不匹配。`-w` 关不掉。

改成 Node 的 `writeFileSync` 写字符串、显式 `replace(/\r\n/g, '\n')` 后：

```
bytes: 3739 CRLF in source: 0 LF after: 50
RESULT: applies cleanly
```

## 四、真正的发现：视图挡不住召回

A3 的前提是"把召回查询换成 `l1_recallable` 视图，归档记录就自动消失"。实测这个前提是错的。

### 视图本身是对的

在快照副本上加列、建视图、把 2 条记录标 `archived`：

```
table rows      : 822
view rows       : 820
archived hidden : true
lookup archived : undefined
```

### 但召回路径不经过视图

读码确认三处：

```
sqlite.ts:1137  searchL1Fts  →  SELECT ... FROM l1_fts
sqlite.ts:726   stmtGetMeta  →  SELECT ... FROM l1_records WHERE record_id = ?
sqlite.ts:1203  l1-reader    →  SELECT ... FROM l1_records
```

三处都不知道视图存在，于是：

```
archived id visible through:
  queryBySessionId   YES
  queryAll           YES
  migrationCursor    YES
via l1_recallable:   no
archived row still present in l1_fts: true
```

**归档只改 `l1_records.state`，没有动 `l1_fts`。** FTS 索引里那行还在，BM25 照样命中；向量路径的 KNN 从 `l1_vec` 取候选，再用 `stmtGetMeta` 查元数据，而它查的是表不是视图。

当时为什么没暴露：那两条被归档的记录 BM25 排在 188 和 66 位，落在 `limit × 3 = 15` 的窗口外。**这是 token 频率的巧合，不是机制保证。**

### 两种修法的实测

| 方案 | 做法 | token="用户"（冷缓存） | 其余 token |
|---|---|---|---|
| JOIN | `l1_fts JOIN l1_records ... AND m.state='active'` | 0.42 → 2.45 ms | +0.1～0.2 ms |
| 子查询 | `AND record_id IN (SELECT ... FROM l1_recallable)` | 0.42 → 2.56 ms | +0.2～0.4 ms |
| 客户端过滤 | 查完再丢 | 0 | 白占候选窗口名额 |

采用 **JOIN**。子查询每次重新展开视图，略慢；客户端过滤不花钱，但会把 `LIMIT` 窗口浪费在注定丢弃的行上——窗口本来就稀缺（`candidateK = limit × 3`）。

向量路径：`stmtGetMeta` 改查视图，查不到就 `continue`。现有代码已有"记录有向量但没有元数据"的跳过分支（`sqlite.ts:1533`），正好接上。

### 修复实测

用真实快照，把**排第一**的记录归档（不是落在窗口外的那种），对比窗口成员：

```
"用户" victim=m_1792…（记录 id 打码）
  unpatched: in window before true → after true   ← 泄漏
  patched  : in window before true → after false  ← 堵住
  patched window still full: 15 of 15             ← 没有留空
  meta via view: undefined → hit skipped
```

三个 token 结果一致。

### 对计划的影响

A3 的验收从"视图能被两条检索路径替代"改成"**归档后的召回路径必须逐条堵住**"，并因此多出第四份补丁。`l1-reader` 的读语句**故意不改**——它们服务于 L2 生成，L2 需要看到历史，过滤掉归档记录会让场景提炼丢上下文。

这是"改 schema 容易、改查询难"的典型：视图是好抽象，但**没人用它的抽象等于不存在**。

## 五、回归测试

新增 `test/recall-filter.test.ts`（5 个测试），把这件事钉住：

1. 归档不会把行从 `l1_fts` 移除。
2. 单靠视图挡不住 FTS 查询（复现泄漏本身）。
3. 视图确实能挡住元数据查询。
4. JOIN 形式堵住泄漏，且窗口回填不留空。
5. 归档记录的向量命中会走"跳过"分支，不会返回半填结果。

写这组测试时踩了个坑：FTS5 默认 tokenizer 把整串中文当一个 token，所以要按 tdai 的真实做法预分词（`tokenizeForFts` 先用 jieba 切再存），否则 `MATCH` 只命中那一条恰好单独成词的记录——那是 fixture 的假象，不是被测代码的行为。
