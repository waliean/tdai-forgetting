## 2. 为什么是 `084bed45`，不是 `65730e9`，也不是 origin HEAD

R0 提示词把 `origin/feat/server_team = 65730e9` 当作上游现值。会话开始时本地引用确实是它，但 `git ls-remote` 显示远端真实值是 `084bed45`：

```
$ git ls-remote --heads origin
084bed45cad6bb7f877455082cee82835d65671a  refs/heads/feat/server_team
```

`git fetch` 后本地引用更新为 `084bed45`，两者相差 1 个提交（`git rev-list --count 65730e9..084bed45` = 1）。这一个提交叫「release v2.0.3」，改了 126 个文件（`MemoryProxy` 60 / `MemoryPanel` 34 / `MemoryKnowledge` 20 / `MemoryCore` 9 / `deploy` 2 / `CHANGELOG.md` 1）。其中落到补丁范围里的 9 个文件全在 `MemoryCore/src/metadata/` 下，包括 `metadata_config_params.json` 新增的 `team_memory` 模块总开关——**这 9 个文件的镜像版本是 `084bed45` 的版本，不是 `65730e9` 的版本**（md5 逐一实测，9/9 与镜像相同、与 `65730e9` 不同）。

所以：

- 拿 `65730e9` 当基线，R1–R3 的重做本身不受影响——重做要触及的 11 个文件在两个提交上对象哈希完全相同（§3）。但基线**缺生产镜像里有的那 9 个 `src/metadata/` 文件**，以后任何触及 metadata 的补丁都会踩到缺口；而且「基线 = 生产」这句话会变成近似，不再是逐字节相等。
- 拿真正的 origin HEAD（`084bed45`）当基线，源码与生产逐字节相同，且不落后。

顺带纠正两个数字：`5299c00..65730e9` = 46，`5299c00..084bed45` = 47。提示词里的「落后 46」是按会话开始时的 stale 引用算的，不是错，只是基准点早了一个提交。

### 为什么不直接取「最新 origin」当成「生产」

这次二者恰好重合，但那是运气。判断顺序应当是：先按内容定位生产在跑哪棵树，再确认上游是否还有更新的提交；不能反过来「取最新，假设生产跟着走」。这次就是先做内容比对、后确认提交的。

### 一个必须写下来的时点反常

## 6. `decay` 重排该放哪：`memory-search.ts`，不是 `l1-candidate-recall.ts`

结论：**留在 `memory-search.ts` 的 `:160` 之前**（`const trimmed = results.slice(0, limit)` 上面）。但 0003 的位置不是这次唯一的问题，见本节末尾。

三条理由：

1. **`recallL1Candidates` 有两个调用方，只有一个是召回。** 除了 `memory-search.ts:135`，还有 `l1-dedup.ts:272`：去重时拿新记忆的内容去检索已存记忆，算它们像不像。把衰减塞进 `recallL1Candidates`，去重的候选顺序也会被「最近用得多」影响，等于让一次检索行为的副产品去改写入路径的判断。这两件事的排序依据不该共用。
2. **衰减要作用在过滤后的集合上。** `:148–158` 先按 `type` / `scene` 过滤，`:160` 才裁剪。放在 `recallL1Candidates` 里，衰减就发生在过滤之前——`candidateK = limit * 3` 的过取窗口会被「不该命中的类型」占掉，覆盖率的分母也不对。
3. **`l1-candidate-recall.ts` 的 `toL1Hit`（`:132`）是个收窄映射**，只搬运 `L1SearchResult` / `L1FtsResult` 已有字段。衰减要读 `access_count` / `last_access_time`，这两个字段现在这条链上根本没有位置；塞进 `toL1Hit` 会把「召回」和「排序数据供给」两件事捆在一起，而 `memory-search.ts` 的 DTO 本来就是为展示层准备的，加字段更合适。

### 但只接线还不够——这是 R0 挖出来的第二个坑

0003 的死代码有两个层次，A4 只发现了第一个：

1. **没人传 `decay`**：`tdai-core.ts:452` 与 `v2-router.ts:1222` 都不带这个参数，`if (decay)` 永不成立。这个已写在计划里。
2. **就算传了，重排也是恒等变换**：`MemorySearchResultItem`（`:22–36`）没有 `access_count`，没有 `last_access_time`。`trackingCoverageOf` 会算出覆盖率 0，低于 `minTrackingCoverage = 0.1`，于是整集关闭年龄项，乘数全为 1.0。

第二条是实测的，不是推的。同一条候选列表，两种数据：

```

order after(access)   = b,a
multipliers(access)   = 1.210,0.301
```

左边这组就是「接线接好了、配置也开了、日志里 `[decay] candidates=… coverage=0%` 打得很好看、排序一动不动」的样子，且**不会有任何报错**。这正是本仓库最贵的那类 bug。

六段，缺一段就退回恒等。这属于 R3 的实现范围，R0 只负责把它记下来并给出行号。

## 7. 交给 R2 评审的一条风险

`:587` 的 `stmtGetMeta` 改成查 `l1_recallable` 之后，`deleteL1`（`:1445`）与 `deleteL1Batch`（`:1481`）的隔离校验会连带受影响：

```ts
const meta = this.stmtGetMeta.get(recordId) as {...} | undefined;
if (!meta || !rowMatchesIsolation(meta, filter)) return false;   // :1450
```

归档记录在视图里查不到 → `meta` 为 `undefined` → 带 `filter` 的删除对归档记录返回 `false`。路径是 `v2-router.ts:1316` 的按 id 删除端点。

旧 0004 里同样存在这个性质（旧基线 `sqlite.ts:1591` 结构一样），所以这不是新引入的回归，但也**不能用「0004 就是这样」搪塞过去**：软删除机制接入后，归档记录会被大量产生，那时「想物理删掉一条已归档记录」会成为真实操作，返回 `false` 而不报错就是静默失败。

R2 的评审要点：确认这个行为被写进注释或报告；如果要修，就为删除路径单独准备一条查 `l1_records` 的语句，别让视图承担两种语义。

## 10. 给 R1–R3 的交接约定

1. 基线只有一个，就是 `084bed45`。任何「补丁可应用」的结论都要带这个 sha，只写「上游」「origin」不算数。
2. 补丁编号 `0101`–`0103`，旧的 `0001`–`0004` 不覆盖、不删除。
3. 补丁必须真实 `git diff` 导出，Node `writeFileSync` 写 LF。手写 hunk 头、PowerShell `Out-File` 都是已踩过的坑。
4. 0102 的 FTS 语句里，`MATCH` 左操作数保持虚拟表名 `l1_fts`，不要跟着 `f` 别名走。
5. 0103 别把验收停在「日志里有 `[decay]`」。要证明 `coverage` 非 0 且顺序真的变了，否则就是 §6 第二种死代码。
6. `.scratch/origin-wt`（`65730e9`）与 `.scratch/baseline`（`5299c00`）都不是基线，别误用。
