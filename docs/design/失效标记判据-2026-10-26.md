# 失效标记判据（画布 C / c2-criteria）— 2026-10-26

## 一句话

**谁来判「新结论推翻了旧结论」：人工命令为基线，LLM 为增强——但 LLM 必须过三道闸才允许默认生效。** 本任务交付人工命令 + 本文档；LLM 的实现归 `c6-llm-criteria`，本文只写设计。

---

## 1. 为什么这事需要先定判据

受控实验（`bench/supersede.ts`，每事实 90/60/30 天三次复述）把问题钉死了：

| 配置 | 最新复述排第一 | 窗口内过期副本数 |
|---|---|---|
| baseline | 0.000 | 2.00 |
| decay（门槛关闭） | 0.000 | 2.00 |
| decay-forced（强制开启） | **1.000** | **2.00** |
| decay+dedupe | 1.000 | 2.00 |
| **explicit-supersession** | **1.000** | **0.00** |

读法：时间衰减能把最新那条**顶到第一**，但它**挤不掉**过期副本——衰减改排序，不改取舍。而显式标记两件都做到。

**结论：时间衰减是失效标记的代理。代理只在时间戳可信时有效，字段能表达的东西不该用启发式去猜。** 这一条是本画布的存在理由，也是 `c5-effect-recheck` 要复跑验证的东西。

所以问题从「阈值调多少」变成「**谁有权宣布一条结论失效**」。这个问题的答案决定了误标的代价由谁承担。

## 2. 三条可能的路

| 方案 | 机制 | 成本 | 主要风险 | 裁定 |
|---|---|---|---|---|
| **人工命令** | CLI `supersede --old <id> --new <id> --reason "…"` | 零（不新增 LLM 调用） | 覆盖不了自动进库的新结论；依赖有人真的会去用 | **基线** |
| **dedup 时 LLM 判** | `core/record/l1-dedup.ts` 写路径上多一次调用 | 每次 dedup 一次 LLM 调用 | 误标率高、**无复核人在场**、写路径上多一个可失败的依赖 | **要，但必须过闸** |
| **规则判** | 时间戳 + 相似度阈值 | 零 | **等价于衰减代理**，上表已经证明不够 | **不做** |

### 2.1 为什么不是「只做人工」

人工命令的覆盖缺口是可量化的：记忆是**自动**进库的（auto-capture → L1 抽取 → dedup），而失效标记需要**人**主动发现「这条被推翻了」。真实使用里，一个人不会在每次记忆更新后回来翻旧记录。缺口不会自己关上。

**但缺口关不上不等于可以降低标准。** 所以不是「只做人工」，也不是「直接把 LLM 打开」，而是**做 LLM 判定、默认不生效、用数据决定何时生效**。

### 2.2 为什么规则判不做

规则判的两个输入（时间戳、相似度）恰好是衰减已经用过的两个信号。上表第四行是它的最好结果：`decay+dedupe` 拿到了 1.000 / **2.00**——排序对了，取舍错了。再加阈值只是把同一个代理调得更用力。

**一个已经证明不够的机制，不该因为「零成本」而入选。**

### 2.3 为什么以人工为基线（不是「先人工，以后再说 LLM」）

三条理由，按重要性排：

1. **误标的不可逆程度不对称。** 漏标（false keep）只是继续噪声——旧结论和新结论一起被召回，人自己会看出来哪条新。**误标（false supersede）是让人再也找不回正确的东西，而且不会报错**：召回集里干干净净，没有任何迹象提示「这里少了一条」。这是本画布最核心的风险判断，也是下面所有保守设计的来源。
2. **谁在什么时机能做判断。** 只有人知道「项目 A 取消了」。LLM 能看到两条文本像不像、时间谁新谁旧，看不到「这条是三个月前开会说的，会上后来改了主意但没写进记忆」。**人的信息集严格大于任何从库里能读到的信号。**
3. **错判的追责路径。** 人工命令的每一次失效都有 `--reason` 和 `actor`；审计里能读出「谁在什么时候因为什么标了它」。LLM 自动判定没有这个属性——它可以记录「模型判 supersede」，但记录不了「为什么」。

**人工是基线，意味着 LLM 的判定必须向人工的判定看齐，而不是反过来。** `c6` 的误标率就是拿 LLM 的判定去比人工标注的 ground truth。

## 3. 失效 ≠ 淘汰（语义必须分开）

| 维度 | 谁在写 | 含义 | 撤销方式 |
|---|---|---|---|
| `state` | planner / applier（淘汰策略） | 这条记录**在不在活跃集里**。「没人在用它了。」 | 改 state（一条 UPDATE，但那是状态机的一次迁移） |
| `invalid_at` | `supersede` 命令（人）；日后 `c6`（LLM，过闸后） | 这条记录的**主张还成不成立**。「有更新的东西推翻了它。」 | **清空 `invalid_at`**（一列更新） |

**一条记录可以 `invalid_at` 非空且 `state='active'`**，语义是「它还在库里，但已被推翻」。

为什么不合成一个字段：

- **撤销成本差一个数量级。** 标错了要能立刻反悔。清 `invalid_at` 是一列更新，不碰状态机、不碰 `forget_reason` / `forgotten_time`、不影响任何依赖 state 的逻辑。如果揉进 state，撤销就是一次状态迁移，得回答「它原来是什么」——而那个信息在覆盖时已经丢了。
- **两者的判定者不同。** state 由策略判（配额、分数、年龄），`invalid_at` 由人判（或过闸后的 LLM）。同一个字段两个判定者，就是两次误判互相掩盖。
- **审计要能分开统计。** `action='invalidate'` 与 `archive`/`retire` 是不同的事件。混在一起，你既看不出淘汰策略干了什么，也看不出有人标错了多少条。

代码里这条区分是硬保证：`src/invalidation.ts` 的 UPDATE **只写 `invalid_at` / `superseded_by`**，从不碰 `state`；有测试断言失效后 `state` 仍是 `active`。

## 4. 人工命令的契约

```bash
node src/cli.ts supersede --db <path> --old <record_id> [--new <record_id>] --reason "<为什么>" [--apply]
```

| 行为 | 约定 |
|---|---|
| 默认 | **dry-run**。打印将被改的记录（id / type / 当前 state / 当前 invalid_at / 正文前 60 字）与将写的审计行，**不写任何东西** |
| `--apply` | 才真写。一个事务里 `UPDATE l1_records` + `INSERT INTO forgetting_audit`，**要么都成、要么都不成** |
| `--reason` | **必填且非空**。缺失或只有空白 → 退出码 **4**，不写任何东西 |
| `--new` | 可选。项目取消这类没有替代者的情况，**强制填 `--new` 会逼操作者随便填一个 id，那是在审计里写假话** |
| 退出码 | `0` 成功 / `4` 被拒（理由为空、old 不存在、new 不存在、已经失效） |

被拒的四种情况都有各自的 stderr 文案，告诉操作者**改什么**，而不只是「失败了」。

### 4.1 为什么默认 dry-run

一个会标失效的命令，正是那种人会用「先跑跑看」来试的命令。**「看」必须是默认行为，写必须显式。** 这条不是体验问题：误标不可逆、不报错（§2.3 第 1 条），所以摩擦要放在写的那一侧。

### 4.2 为什么空理由要拒绝而不是补一个默认值

审计是后来的人**唯一**能查出「当初为什么标它」的地方。自动填 `"superseded"` 会看起来像一条理由，实际不含任何信息——甚至更糟：它让「没有理由」这件事不可见。

### 4.3 为什么已经失效的记录会被拒绝

重复标记说明操作者遇到的不是「要标它」，而是「它怎么已经是失效的了」。静默改写 reason 会把第一次的记录覆盖掉，而第一次往往才是对的。拒绝并要求先 `--restore`，是让第二次意图变成一次显式操作。

## 5. LLM 判据设计（**只写设计，实现在 `c6-llm-criteria`**）

### 5.1 判定输入

必须给**新旧两条完整记录**：正文全文、`type`、时间戳、所属场景，外加场景上下文。

**为什么不能只给相似度分数**：相似度高只说明两条在说同一件事，不说明谁推翻了谁。要判断的是**方向性**——「B 是 A 的修正」还是「A 和 B 是同一件事的两种说法」还是「A 和 B 只是都在讲同一个主题」。

方向性在分数里不可见。两条互为反义但用词高度重合的句子（「项目 A 下周交付」/「项目 A 不再交付」）的 shingle 相似度会**很高**，而它们恰恰是 supersede 的典型案例。反过来，同一事实的两次复述（「下周三交第一版」/「本周三交付初版」）相似度中等，答案却是 keep-both。

**分数可以作为输入之一，但不能是主输入。** 主输入必须是文本本身——这也是 LLM 相对规则判的唯一优势所在。

### 5.2 判定输出：三分类

| 判定 | 语义 | 下游动作 |
|---|---|---|
| `supersede` | B 明确推翻了 A：A 的主张不再成立 | **只有这一类**可能写 `invalid_at`（apply 模式下） |
| `keep-both` | A 与 B 是同一事实的不同表述，或互补，互不推翻 | 都不写 |
| `unrelated` | 两条讲的是不同的事（相似度误报） | 都不写 |

三分类而不是二分类，是为了让模型有地方安放「像但没关系」——**二分类会逼它在 `supersede` / `not-supersede` 之间选，而「像」这个信号会把边缘案例推向 supersede。**

「不确定」不是一个类别，而是一个**结果**：模型无法判断时应当输出 `keep-both`（见 5.3）。

### 5.3 误判不对称如何影响取舍

把 §2.3 第 1 条量化成判定规则：

- **false supersede（把有效记录标失效）**：用户再也找不到正确的东西，**且无任何提示**。代价 ≈ 永久损失一条正确记忆。
- **false keep（漏标）**：旧结论继续和新结论一起出现，用户自己会看出哪条新。代价 ≈ 一次噪声。

因为代价差着「静默且不可逆」这个维度，**三分类的边界必须向 keep-both 一侧偏**：

1. **只有在模型能指出「B 在哪个具体主张上取代了 A」时才输出 `supersede`**，而不是「B 看起来更新」。
2. **模型无法判断时输出 `keep-both`，不输出 supersede。** 不确定必须落到安全侧。
3. **判定阈值偏保守**：宁可漏掉一部分真 supersede，也不让 false supersede 混进来。漏掉的那些仍然会被人看到（噪声），误标的那些不会。

### 5.4 shadow 如何落地

三道闸，全部落成可检查的机制：

1. **shadow 模式（默认）**：LLM 判定**只写 `forgetting_audit`**（`action='llm-suggest'`），**不改 `invalid_at`**。判定不生效。
   - 与人工的 `action='invalidate'` 可分组区分——审计里要能一眼看出「这条是模型建议的」还是「这条是有人决定的」。
   - `--mode=shadow` 是默认；`--mode=apply` 才生效。
   - **shadow 下退出时 `invalid_at` / `superseded_by` 必须全为 NULL**——这条要有测试证明，不能只是口头约定。
2. **50 条人工复核样本**：人工标注 ground truth，与 LLM 判定逐条比对。样本集的构建规则必须可复现（抽样规则、标注人/时间/verdict 记录、样本集文件路径）。
3. **误标率 < 5%** 才允许 `--mode=apply`。未达门槛（误标率 ≥ 5% 或无报告）时 **apply 被硬拒、退出码非 0**，stderr 要说明**当前误标率与门槛**。

### 5.5 失败必须降级为「不判定」

LLM 调用超时 / 网络失败 / 输出解析失败时，**降级为「不判定」，绝不返回 supersede、绝不写 `invalid_at`**。

这条是 §5.3 的直接推论：一个会失败的依赖，失败时的默认行为必须是「什么都不做」。把失败当成「没有找到推翻关系」是安全的，把失败当成「可以标了」是灾难性的。**要有失败路径的测试。**

## 6. 误标之后怎么找到它（可回滚 / 可发现）

审计不是日志，是**查询接口**。查到一条标错的路径有三条，都不需要事先知道 record_id：

| 手段 | 命令 | 用途 |
|---|---|---|
| 按 action 查审计 | `SELECT … FROM forgetting_audit WHERE action='invalidate' ORDER BY decided_at DESC` | 看**谁在什么时候因为什么**标了它；`reason` 是操作者填的原文 |
| 列出全部失效记录 | `node src/cli.ts invalidated --db <path>` | 扫一眼当前所有失效记录，**不需要先知道 id** |
| 恢复召回 | `node src/cli.ts invalidated --db <path> --restore <record_id>` | 清空 `invalid_at` / `superseded_by`，立即恢复可召回 |

三条补充事实：

- **恢复只动一列。** 不碰 `state`、不碰 `forget_reason`、不碰其余的审计行。
- **恢复不删审计。** 「曾经有人标过它」是历史事实，删掉它就等于抹掉发现误标的线索。
- **失效记录仍在库里。** 它只是不进 `l1_recallable` 视图；正文、向量、FTS 行都还在（`c3-recall-filter` 的过滤是查询侧的，索引行不删）。所以恢复不需要重建任何索引。

`invalidated` 的渲染是固定列序：id / invalid_at / type / state / superseded_by / 正文前 60 字。**state 显示出来是刻意的**——操作者要能一眼看到「它没有被淘汰，只是被推翻了」。

## 7. 范围边界

| 归属 | 内容 |
|---|---|
| **本任务（`c2-criteria`）** | 人工 `supersede` 命令；本判据文档；`invalidated` 列表与 `--restore` |
| **`c6-llm-criteria`** | LLM 判定接口的**实现**；shadow 管线；50 条复核集的构建与落盘；误标率报告与复算脚本；`--mode=apply` 的门槛硬拒 |
| **`c4-planner-pass`** | planner 里的失效 pass（位于 hard pin 之后、绝对阈值之前；失效记录一律 archive 不 retire）|
| **`c5-effect-recheck`** | 用真实字段重跑 `bench/supersede.ts`，验证 `stale-in-window 2.00 → 0.00` |

**本任务的 impl 不得夹带任何自动判定路径。** `supersede` 命令要求调用方显式给出 `--reason`，没有任何一条代码路径能自己决定「A 被 B 推翻了」。LLM 的判定在 `c6`，且在它自己的门槛之下——即便 `c6` 完成，判定接进命令或默认生效也仍然要按 §5.4 走闸。

## 8. 遗留与已知风险

1. **人工命令的覆盖缺口没有关闭。** 本文 §2.1 只说清了缺口存在与为什么不能靠降标准去补，没有给出「多大的缺口可以接受」。那个数字要等 `c6` 的复核集跑出来才有。
2. **5% 这个门槛是拍的**，与冷启动覆盖率 10% 同源（都只有小样本支撑）。跑出第一份真实误标率报告后应当重新审。
3. **LLM 判定的 ground truth 来自人工**，而人工标注本身有噪声。50 条样本上的 < 5% 与 500 条上的 < 5% 不是同一个置信度——样本规模写进报告，不要只报比率。
4. **失效不阻断向量检索的候选生成**，只阻断结果（`c3` 的跳过分支）。若某个部署依赖「失效即省算力」，需要另做，本画布不做。
5. **审计表会随失效次数增长**，且目前没有归档策略。量级=人工操作次数，短期不是问题。
