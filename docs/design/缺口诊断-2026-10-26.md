# 缺口诊断（2026-10-26）

读码 + 线上实测的结论：tdai 有"清理"，没有"遗忘"。区别在于清理是按日期一刀切，遗忘是按价值降级。

## 线上实测

```
L1 原子记忆   822 条（episodic 529 / instruction 227 / persona 66）
L0 消息       1774 条
数据类型      单库 24.8 MB，自 2026-08-29 起累积
按月份        08 月 68 条 / 09 月 541 条 / 10 月 213 条
priority -1   59 条（上游的"全局指令"约定）
永久性措辞     197 条正文命中"永久记住 / 不得遗忘 / 不得删除"类表述
淘汰记录      0 条
```

四个月里没有任何一条记忆离开过可召回集。

## 逐项证据

### 1. 打分不含时间、频次、重要度

检索走 `rrfMergeL1`，纯排名融合：

```ts
// MemoryCore/src/core/tools/memory-search.ts:62-80
function rrfMergeL1(...lists) {
  // 每条得分 1 / (RRF_K + rank + 1)，多路命中则累加
}
```

向量路径 `searchL1Vector` 只按余弦距离排序，`priority` 字段读都不读：全文 grep 下来，`priority` 只出现在写入和返回值里。

后果：一条昨天刚被召回的记忆，和一条两个月没碰过的记忆，排序上完全等价。

### 2. 没有访问痕迹

`l1_records` 建表语句（`sqlite.ts:626-646`）字段为：`record_id / content / type / priority / scene_name / session_key / session_id / team_id / task_id / user_id / agent_id / version / timestamp_str / timestamp_start / timestamp_end / created_time / updated_time / metadata_json`。

没有 `last_access_at`，没有 `access_count`。用进废退无从实现——这条最关键，因为它决定了后面所有公式有没有数据可用。

### 3. 清理器默认关，且没在生产开

```ts
// MemoryCore/src/config.ts:383-396
const rawRetentionDays = num(captureGroup, "l0l1RetentionDays") ?? 0;
// 0 → retentionDays = undefined → 清理器不启动
```

`deploy/global-images/.memory-core-config/tdai-gateway.yaml` 的 `capture` 只有 `{ enabled: true }`，没有 retention 项。容器环境变量里也没有。清理器全程未启动。

### 4. 即使打开，判据也是错的

`memory-cleaner.ts` 按 `updated_time < cutoff` 删（`sqlite.ts:1666` `deleteL1Expired`）。问题在于 L1 记忆会被 dedup 反复 merge/update，`updated_time` 一直刷新——**活得越久的记忆反而越删不掉**；真正冷门但关键的旧结论会被整片砍掉，且 L0 一起删，白盒溯源断裂。

还有两道硬闸会静默拦下大部分删除：

- `MIN_RETAIN_L0 = 50` / `MIN_RETAIN_L1 = 20`（`memory-cleaner.ts:28-29`）
- 单次删除比例超 80% 直接 BLOCKED 返回 0（`sqlite.ts:1684-1690`）

调用方拿到 0 会以为"没有过期数据"，实际是被保护闸拦了。这两道闸本身合理，问题是没有对外区分"没有过期"和"被拦下"。

### 5. 只有硬删，没有中间态

现有能力：

- `/v3/chat-memory/clear`：清空一整个 (team, agent) 的记忆内容（`chat-memory-handlers.ts:166`）
- `/v2/atomic/delete`：单条删（`v2-router.ts:422`），但没有任何策略去调它

没有冷层、没有归档表、没有软删除标记。要么全留，要么全丢。

### 6. 过时结论不失效

dedup（`core/record/l1-dedup.ts`）只在写入时用 LLM 判合并/更新/新增，被取代的旧结论不会被标失效。两条矛盾记忆并存，检索时都能召回。

真实表现：搜"遗忘机制"，top6 里 4 条是"用户要求 AI 永久记住 XXX"式的元记忆，字面高度相似、信息量低、互相冗余，长期霸占召回位。

### 7. MCP 检索不吃阈值

`auto-recall` 用 `cfg.recall.scoreThreshold`（默认 0.3，`auto-recall.ts:459`），但 MCP 工具 `memory_search` 直接打 `/v3/atomic/search`，不传阈值，无论相关性多低都返回 `limit` 条。噪声因此更容易被看见。

## 一个必须先解的冲突

命中永久性措辞的 197 条里有 162 条是指令型（`type = instruction`），其中 51 条同时带 `priority = -1`。它们明确写着"永久有效、不得遗忘或覆盖"，举例：

- C 盘清理记录
- JFPE 第十六轮盲审
- 课题3 三架构编排收口
- RRS 策划案补正
- tdai 复刻部署文档

遗忘机制必须先有 pin 语义。没有豁免标记，衰减上线第一天就会把它们衰减到三成，而且这件事不会报错、不会告警，只会安静地让下次召回少一条。

## 四句话

1. 只增不减，且没有任何按价值淘汰的机制。
2. 唯一的清理器默认关闭，打开也是按日期截肢而非按价值遗忘，判据字段还被 dedup 天天刷新。
3. 没有访问痕迹，所以"用进废退"这一最基础的遗忘原理无从落地——这也是为什么改动必须先补数据，再谈公式。
4. 过时结论不失效，冗余记忆长期污染召回。
