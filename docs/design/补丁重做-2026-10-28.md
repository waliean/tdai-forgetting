## 4. 三个必须记住的技术坑

这一节是这份文档最该被读到的地方。三条坑的共同点是**失败要么静默、要么延后到运行时**，当下的命令全返回 0。

### 4.1 `git diff` 不含未跟踪的新文件

**现象**：0103 导出的补丁只有 **19,597** 字节、8 个文件，而正确的补丁是 **27,518** 字节、9 个文件。差的 7,921 字节正好是 `l1-decay.ts` 的整段新增 diff（该文件本体 7,506 字节，多出来的是 diff 头与 201 行前缀）。更麻烦的是这份残缺补丁 **`git apply` 依然 exit=0**——我实测过：残缺 diff 打在 0101+0102 的树上，应用成功，但 `l1-decay.ts` 不存在，而 `memory-search.ts` 已经 `import ... from "../record/l1-decay.js"`。运行到第一次检索才 `Cannot find module`。

**原因**：`git diff` 比的是 worktree 与 index，**未跟踪文件在 index 里没有条目，因此根本不出现在 diff 里**。它不会报错，只是安静地少一个文件。

**正确做法**：导出前对每个新增文件 `git add -N`（intent-to-add）——让它在 index 里有一条空条目，diff 就把它按「新增」输出，同时不改 index 里的实际内容。

```powershell
git -C .scratch/baseline-wt add -N MemoryCore/src/core/record/l1-decay.ts
```

**自证方法**（每次导出后都跑）：重跑一遍 `git diff --no-color`，把字节与磁盘上的补丁比 sha256。补 `add -N` 后我实测 `27,518` 字节、`9865611F…`，与落盘补丁 **identical=true**。

**判据一句话**：补丁的 `files` 数必须等于你「以为改了」的文件数。8 ≠ 9 就是这个坑。

### 4.2 `git apply` 前不 `add -A`

**报告记录的现象**（R3 实现阶段第一次验证）：0101、0102 apply 之后没有 `git add -A`，直接 `apply --check 0103` **通过**，但真 `apply` 在 **9 个文件上全报 `patch does not apply`**。当时的判断是「git 的 apply 默认对着 index 做三方匹配，而 index 里还是 0101 之前的 blob」。

**我这次复核到的边界**（git `2.55.0.windows.3`，工作副本已是 0101+0102、index 停在 HEAD 或停在 0101）：

| 用法 | 结果 |
|---|---|
| 裸 `git apply 0103`（worktree 已是 0101+0102，index 未跟上） | **exit=0，应用成功** |
| `git apply --check` 同上 | exit=0 |
| `git apply --index 0103` | exit=1，`memory-store.ts: does not match index` |
| `git apply --cached 0103` | exit=1，`patch failed: memory-store.ts:618` → `patch does not apply` |
| `git apply --3way 0103` | exit=1，`does not match index` + `Falling back to direct application...`，其余 7 个文件 cleanly |

即：**裸 apply 只改工作区、不看 index；一旦这条路径要碰 index（`--index` / `--cached` / `--3way` 的回退），陈旧 index 就立刻变成硬失败。** 我没有在裸 apply 上复现出「9 个文件全报错」，所以不把那条现象当成必然规律写。

另一种能造成同一症状的成因，值得一起记：**worktree 被外部进程复位。** 如果 `--check` 之后、真 `apply` 之前工作区被外部进程复位到只剩 0101（FE-001 修复期间确实发生过：两个 worker 同时写 `baseline-wt`，`status --porcelain` 在几十秒内从空变成 `MM` 再变回空），0103 就会对着少了 0102 的树应用，9 个文件全失败。这个成因与 index 无关，但下面两条操作规则同样覆盖它。

**结论和操作规则不变**：

- **每层 apply 之后立刻 `git add -A`。** 这既让下一层导出 `git diff` 时不会把上一层再吐一遍（实测：不 add 时导出的「0102」是 **11,655** 字节、同时含 `CREATE VIEW l1_recallable` 与 `JOIN l1_records m ON`；add 之后是 **8,114** 字节、sha256 与落盘 `0102` 全等），也让任何走 index 的 apply 模式可用。
- 验证脚本里不要省这两行。省掉的代价不是「命令报错」而是「补丁内容悄悄多了一层或少了一个文件」。

### 4.3 FTS5 别名约束：`bm25()` 与 `MATCH` 的左操作数必须是虚拟表名

**现象**：`SELECT bm25(f) FROM l1_fts f WHERE l1_fts MATCH ?` 与 `... WHERE f MATCH ?` 都报 `no such column: f`。

**原因**：FTS5 的 `bm25()` 与 `MATCH` 不是普通列函数/操作符，它们要求左操作数是**虚拟表名本身**，别名不参与解析。给 `FROM l1_fts f` 加 `f.` 前缀改列名是对的，但表名那两处不能跟着改。

**正确做法**（0102 就是这么写的，实测通过）：

```sql
SELECT f.record_id, f.content_original AS content, ..., bm25(l1_fts) AS rank
FROM l1_fts f
JOIN l1_records m ON m.record_id = f.record_id
WHERE l1_fts MATCH ? AND m.state = 'active'
ORDER BY rank ASC
LIMIT ?
```

我这次在 `node:sqlite`（SQLite 3.53.1）内存库上复验：`bm25(l1_fts)` + `l1_fts MATCH ?` 正常返回；`bm25(f)` 报 `no such column: f`；`bm25(l1_fts)` + `f MATCH ?` 也报 `no such column: f`。

### 4.4 四条环境坑（不修代码，但会让验证结论整个错掉）

**① 中文 query 走 PowerShell argv 会变乱码。** 实测把 `用户` 作为 argv 传给 node，node 收到的是 `鐢ㄦ埛`（3 个字符）。后果很隐蔽：FTS 半路返回 0 条，检索退化成纯向量，日志里 `strategy=embedding` 而不是 `hybrid`——看起来「跑通了」，其实走的是另一条路径。**正确做法：query 放 UTF-8 JSON body 文件里，脚本读文件而不是读 argv。** 本次所有容器日志都是修好之后取的，`strategy=hybrid`。

**② 容器运行中从宿主机就地改挂载的 WAL 库会静默写坏索引。** 现象是 UPDATE 返回 `changes: 1`、宿主机读回也是新值，但 `integrity_check` 报 `row 696 missing from index idx_l1_state` 而 `quick_check` 报 ok；视图 `l1_recallable` 走 `idx_l1_state`，索引没更新 → 归档行仍被选出 → 召回照旧，症状看起来是「补丁没生效」。同一条误用还有第二种表现：`HTTP 500 disk I/O error`，堆栈落在 `PRAGMA journal_mode = WAL` 那一行。**正确做法：停容器（`docker stop -t 20`）→ 宿主机独占改库 + `PRAGMA wal_checkpoint(TRUNCATE)` → 起容器。** `busy_timeout` 解决不了这件事——它管锁等待，管不了跨 OS 的 WAL 一致性。机制与完整证据见 [补丁落地验证](补丁落地验证-2026-10-26.md) §8.7。

**③ PowerShell 5.1 的 `>` 写出的是 UTF-16LE，不是 UTF-8。** 实测 `'dummy' > file` 的前两个字节是 `FF FE`（UTF-16LE BOM），而 `cmd /c 'echo dummy > file'` 是 `64 75 6D 6D 79 20 0D 0A`（ASCII + CRLF）。所以**用重定向把 `git diff` 落成补丁文件，会同时得到 BOM、UTF-16 编码与 CRLF**，补丁直接坏掉；`Out-File` 是另一条同族路径（写 CRLF，上下文行行尾跟着变，与 LF 的上游逐字节比对全不匹配），两条都记在 [补丁落地验证](补丁落地验证-2026-10-26.md) §2。正确做法只有一条：**Node `writeFileSync` + `\r\n` → `\n`**。

**④ 仓库里没有 `.gitattributes` 时，`core.autocrlf=true` 会在 checkout 时把补丁写成 CRLF。** 这条只在**别人 clone 下来**时才暴露，作者自己的工作树是 LF，所以很容易漏。本机实测：全新 clone 里 `0001` 是 3,793 字节 / CR=50（原件 3,743 / CR=0）；拿那份 CRLF 补丁 `git apply --check` 报 `patch does not apply`，LF 原件 exit=0。而且不是全有全无——`0002`（纯新增文件）在 CRLF 形态下**仍能应用**，所以症状是「有的补丁能打、有的打不上」。已在仓库根加 `.gitattributes` 写 `*.patch -text`（`git check-attr` 已确认 `text: unset`），此后两个方向都不做换行转换。

## 6. 残余风险

前三条必须写清影响面；后两条是机制层面的，属于评审提出、不阻塞放行但会咬人。

### 6.1 `access_count` 没有任何写入方

0101 只建列、0103 只读列。**全树没有一条 `UPDATE` 写它**——我这次在打满三补丁的树上扫了一遍：命中 `SET ... access_count = ...` 的语句 0 条；`UPDATE l1_records` 只有 5 条，全是隔离字段回填与 `version` 修正。

**影响面**：所以 §5 那个「重排会跑」是在**种子数据**上证明的（546/822 条被填了确定性用量历史）。真实生产数据上打开 decay，`coverage` 仍是 0%、年龄项仍然关闭，只是日志会明确写 `coverage=0%, decay=off (cold start)`。

**写法纪律**：这一层的成果是「**通路打通 + 降级可见**」。**绝对不能写成「衰减已生效」**，也不能把「`[decay]` 有日志」当成「衰减在跑」。写值方在画布 B（`access-trace`）的 b1/b2/b3/b5。

### 6.2 `score` 语义变化 —— 落点是 API 契约，不是 `scoreThreshold`

开了 decay 之后返回的 `score` 是乘过系数并 clamp 到 [0,1] 的值（`reportedScore`），不再是 RRF 原分。

**评审纠正过一处口径，必须照纠正后的写**：R3 实现报告原话是「`scoreThreshold` 这类基于分数的下游阈值从此语义变化」。核过全树：`scoreThreshold` 的唯一消费者是 `auto-recall.ts:460`（读配置，在 `:498` / `:564` / `:631` 过滤），而 auto-recall 走**自己的** `searchMemories`（`auto-recall.ts:434`，直调 FTS/向量），**不经过** `executeMemorySearch`，所以它**不受 decay 影响**。

真正变的是：

| 落点 | 变化 |
|---|---|
| `POST /v3/atomic/search` 返回的 `score` 字段 | 开启 decay 后是乘过系数并 clamp 到 [0,1] 的值 |
| MCP 工具对外暴露的 `score` 字段 | 同上 |
| `reportRecallMetrics` 的 `recall_top_score` | 上报的是重排后的分数（`v2-router.ts:1250` 把 `result.results` 的 `score` 传给 `reportRecallMetrics`） |

**不要写成「`scoreThreshold` 变了」**——那会让下一个人去改一个本来不用改的地方。默认关闭时无影响（§5.2 三张默认表的分数逐位相同）。

### 6.3 `state` 没往 DTO 传

`DecayCandidate.state` 是可选字段，`isPinned`（`l1-decay.ts:95`）用 `state !== "archived"` 排除已归档的 pin。

**当前为什么不出错**：召回集本来就只含 active 行——FTS 侧 `AND m.state = 'active'`（0102 加的），向量侧 `stmtGetMeta` 查 `l1_recallable` 视图（`SELECT * FROM l1_records WHERE state = 'active'`）。顶层拿到的记录全是 active，不传 `state` 不会误判。

**风险在哪**：只在「将来把重排前移到过滤之前」那一天。这句话**代码里没有注释**，理想落点是 `memory-search.ts` 的 `if (decay)` 段（`:194` 起）。R3 明确决定不改补丁——改注释要重新导出、换 sha256、重跑全套容器验证，收益不抵风险。留给下一个动这段代码的人。

### 6.4 测的包装 ≠ 发货的包装

`test/l1-decay.test.ts` 覆盖的是 `rerankL1`（含它的 `[l1-decay]` 日志与空集短路），而 MemoryCore 实际调用的是 `rerankCandidates` + `trackingCoverageOf`，并在 `memory-search.ts:194–205` **自己重写了一遍 `[decay]` 日志**。

决策逻辑是同一个 `rerankCandidates`（这部分有单测，13 条里的 3 条直接测它），所以不是逻辑漂移。但「被测试的包装不是实际发货的包装」正好是本仓库最贵那类 bug 的同款形状——它是**危险信号**，不是缺陷。补测试的前提是先有 MemoryCore 的测试入口，而基线工作副本里 `*.test.ts` 计数为 0。

### 6.5 分数随墙钟漂移

同一配置、同一份库两次跑，on 组首位分是 `0.031005` 与 `0.031009`——差 **4e-6**。来源是年龄项按天连续变化、`now` 取墙钟（`l1-decay.ts:124` `settings.now ?? new Date()`）。同容器连跑两次顺序全同，所以这不是随机性。

**影响**：C 画布做参数 A/B 时，若拿不同时刻的分数比较，会被这个漂移污染。`DecaySettings.now` 支持注入，但**HTTP 路径没有入口**——容器实验拿不到固定时钟。
