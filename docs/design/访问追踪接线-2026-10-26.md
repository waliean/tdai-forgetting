## 2. 落点：为什么是这一个返回点

### 2.1 落点

`MemoryCore/src/core/tools/memory-search.ts`，`executeMemorySearch`（`:78`）里 **`:160 const trimmed = results.slice(0, limit);` 之后、`:167 return` 之前**，一次调用、一次写盘。

必须是"返回前"而不是"召回后"，四个理由：

1. **rank 要有意义**。`appendRecall` 只记 `rank <= maxRankCounted`（默认 10，`src/recall.ts:38-40`）。rank 的定义是"在**返回给调用方**的列表里的 1-based 位置"。`:145 results = recalled.hits.map(toSearchItem)` 之后还要过 `:148` type 过滤、`:152` scene 过滤、`:160` 裁剪，只有 `trimmed` 才是最终列表。放在召回点上，rank 记的是候选池内位置——那是"出现在候选池里"，不是"被用到"。
2. **候选池与返回集不是一个量**。`:134 candidateK = limit * 3`，一次 `limit=5` 的检索会拿 15 条候选。全记等于给每条候选发一张"用过"的票。记在裁剪之后，两者自然对齐。
3. **一处覆盖多入口**。四个已覆盖入口都在 `executeMemorySearch` 汇合——它只被 `tdai-core.ts:39` 与 `v2-router.ts:27` 两处 import、只在 `:452` 与 `:1222` 两处调用。
4. **策略演进不影响埋点**。三条内部分支在 `:135` 之前分流、在 `:145` 之后合流（§2.2）；以后加第四条分支，只要 return 还是那一个，埋点不用改。

**不要**在 `:145` 的 `map` 里或单条 hit 的循环里埋：那是循环内 I/O（一次检索 15 次同步写）。`appendRecall` 的签名本来就是"一次检索一个数组"。

### 2.2 三条内部分支各自怎么走到这个返回点

`executeMemorySearch` 自己不做检索策略，它把活交给 `l1-candidate-recall.ts:43 recallL1Candidates`，拿回 `{ hits, strategy }` 后统一处理。`:145` 之后三条分支**完全合流**（同一段过滤 + 同一段裁剪 + 同一个 return）。

| 分支 | 触发条件 | 代码路径（`084bed45`） | 回到返回点的位置 | 埋点看到什么 |
|---|---|---|---|---|
| **native-hybrid（TCVDB 单次混合）** | store 声明 `nativeHybridSearch`（TCVDB：`store/tcvdb/memory-store.ts:595` = `embeddingEnabled && hasBm25`） | `:69` `hasNativeL1Hybrid` 判定 → `:71 searchL1Hybrid({query, topK})` → `:74 return { hits, strategy:"hybrid" }` | `:135 recalled` → `:145` map → `:148/:152` 过滤 → `:160` 裁剪 → `:167` return | 服务端已完成 dense+sparse+RRF 融合，rank 即融合名次 |
| **双路 RRF（FTS ∥ 客户端向量）** | 无 native hybrid，FTS 与 client embedding 至少一路可用 | `:84 Promise.all([recallFts, recallVector])`（`:175` / `:205`）→ `:99-111` 定 strategy → `:114 rrfMergeL1Hits(ftsHits, vecHits)`（`:154` 定义，`RRF_K=60`）→ `:118 return` | 同上 | 融合后的名次。**本部署实际走这条**（`getCapabilities().nativeHybridSearch` 在 sqlite 后端恒为 `false`，`store/sqlite/memory-store.ts:3324`） |
| **单路降级** | 双路里只有一路有结果/可用 | `:102-111`：fts 有 vec 空 → `"fts"`；vec 有 fts 空 → `"embedding"`；两边都空 → `:110` 早退 `{hits:[]}`；`:121 return { hits: ftsOk ? ftsHits : vecHits }` | 同上（空结果时 `:145` 得到空数组） | 单路名次；空结果**不产生日志行**（`appendRecall` 对空数组返回 false） |

还有一条更早的单路短路容易漏读：`:62 if (vectorStore.getCapabilities?.().nativeBm25Search)` → 直接 `searchL1Fts` 返回 `strategy:"fts"`（TCVDB 无 embedding 时用）。属"单路降级"一族。

**结论**：三条分支不需要各自的埋点。分支判断发生在 `:135` 之前，埋点在 `:160` 之后；三条都从 `:167` 那一个 return 出去。

### 2.3 三类"没有 hit 的早退"不记

`executeMemorySearch` 自身三个早退：`:108`（空 query）、`:113`（无 vectorStore）、`:123`（FTS/embedding/native 全不可用）。都直接 `return { results: [], strategy: "none" }`，连 `recallL1Candidates` 都没调到，没有 record_id 可记。

**后果**：日志行数 ≠ 检索次数。B5 想用 fold 出的行数反推检索量时必须减掉这部分（§6.2）。

## 3. `appendRecall` 的调用契约

### 3.1 函数本身（`src/recall.ts:46`，已实现，不改）

```
appendRecall(logPath: string, hits: RecallHit[], now?: Date, opts?: RecallLogOptions): boolean
RecallHit = { record_id: string; rank: number }   // rank 1-based
DEFAULT_RECALL_LOG = { maxRankCounted: 10 }
```

行为：先 `hits.filter(h => h.rank <= maxRankCounted)`，空则 `return false`（**不写行**）；否则 `appendFileSync(logPath, JSON.stringify({at, hits:[record_id...]}) + "\n")`；任何异常吞掉返回 `false`。**永不抛**。

### 3.2 谁调、传什么

| 项 | 契约 |
|---|---|
| 调用点 | `MemoryCore/src/core/tools/memory-search.ts`，`executeMemorySearch` 内、`:160 trimmed` 之后、`:167 return` 之前。一处，不进循环 |
| 入参 `hits` | `trimmed.map((r, i) => ({ record_id: r.id, rank: i + 1 }))`。**`toSearchItem`（`:48`）已把 `record_id` 改名成 `id`**，写成 `r.record_id` 会拿到 `undefined` 并静默写出垃圾行 |
| 入参 `opts` | `{ maxRankCounted }`，取自 `memory.recall.accessLog.maxRankCounted`（默认 `DEFAULT_RECALL_LOG.maxRankCounted = 10`，`src/recall.ts:38-40`；解析见 §3.2.1）。`limit` 可大于窗口（MCP 工具钳在 1–20，`index.ts:412`；HTTP 默认 5，`v2-router.ts:1208`），超出的名次由 `appendRecall` 自己丢，调用方不必再切。**窗口必须来自配置**：FE-001 前在这里硬编码 `DEFAULT_RECALL_LOG`，配置键因此无人消费 |
| 日志路径来源 | `memory.recall.accessLog.path`（0104 新增，键名与默认值见 §3.2.1）。写本文时的读数是"不存在这个键"——0103 只往 `MemoryCore/src/config.ts` 加了 `RecallDecayConfig`（含 `minTrackingCoverage`），2026-10-28 在 `patches/*.patch` 上 `grep -i 'accessLog\|access_log\|recallLog\|recallLogPath'` 命中 0。B2 已按本节不变式补齐；b1 当初不预设键名，只钉不变式（下一行） |
| 路径不变式 | ① 必须能由部署指定（写死路径等于部署无法指定，且测试会污染仓库——B2 prompt 原文）；② 默认值应落在数据目录下；③ **父目录必须已存在**——`appendFileSync` 不建目录，父目录缺失时每次检索都失败、表现只是返回 false |
| 路径怎么送进函数 | `executeMemorySearch` 现在拿不到 `dataDir`（它的入参见 `:78-87`）。要么加一个显式参数，要么走 `V2RouterDeps` / `TdaiCore` 的 getter（0103 的 `getDecaySettings` 就是这个形状，可直接照抄）。**不要**在这个函数里 `import node:path` 自己拼 |
| 写失败处理 | 调用方**不得**因写失败改变返回值或抛错：`appendRecall` 已吞异常返回 `false`，埋点只调用、丢弃返回值。若要观测，最多累计"失败次数"打一条低频 `debug`（每条检索一条 warn 会把日志淹掉）。这就是"拿检索的主功能换副功能"的反面 |
| 同步代价 | `appendRecall` 内部是 `appendFileSync`——**同步写**。"fire-and-forget" 在这里指"失败不影响检索结果"，**不指"不占检索线程"**。热路径 p99 由 B4 量（阈值：+5ms 以上改批量异步写） |

### 3.3 一行日志长什么样

```json
{"at":"2026-10-28T00:03:48.827Z","hits":["m_1791802911343_25b697ad","m_1789554969447_56fae700"]}
```

一行 = 一次**有命中**的检索；`hits` 是该次返回列表的前 N（默认 10）条 record_id，顺序即 rank。行内没有 rank 字段——rank 由数组下标隐含，这是 `appendRecall` 的既有格式。B2 不改它：改格式会让已实现的 `foldAccessLog` 与 103 个测试一起返工。

## 4. dedup 为什么不算访问

**与画布 prompt 表格不一致（必须按这条写）**：`084bed45` 上 dedup **不再直调** `searchL1Fts` / `searchL1Vector`，它走 `l1-dedup.ts:272 recallL1Candidates(...)`——和 `executeMemorySearch` 用**同一个共享函数**（`l1-candidate-recall.ts:43`，文件头注释写着 "Used by memory_search and l1_dedup"）。prompt 表里的 `l1-dedup.ts:229 / 279` 是旧树 `5299c00` 的直调点，新树上已不存在（§7.4）。

**这不改变结论，反而让它更硬**：

1. **语义**：dedup 是写入时查重——"这条新记忆和库里哪条像"。它问的是历史记录的**内容**，不是"谁在用"。算成访问，等于"越常被写入的记忆越像被用过"。tdai 现有 cleaner 的病恰恰是按 `updated_time` 判新旧、被 dedup 合并一直刷新——同一个病换个字段复发没有意义。
2. **量级**：本窗口实测 dedup 驱动的 `recallL1Candidates` 调用 **20 次**（6 个 batch，每 batch 内每条新记忆一次），显式检索 `executeMemorySearch` **15 次**。若埋点下沉到 `recallL1Candidates`，访问记录会被写入路径放大 **20/15 ≈ 133%**，且放大量随写入量涨、与使用量无关。
3. **位置**：这是"必须埋在 `executeMemorySearch`、不能下沉"的**第二个理由**（第一个是 rank 语义，§2.1）。R0/R3 已就 decay 重排论证过同一件事（[基线锁定](基线锁定-2026-10-27.md) §6、[补丁重做](补丁重做-2026-10-28.md) §3.3）：**共享函数不是公共语义**。

**留给未来的自己一句话**：若哪天有人提议"dedup 的候选命中也是信息，顺手记一下"——不要用同一个日志。进了同一个日志就会进 `access_count`，进了 `access_count` 就会进衰减与淘汰的证据链。要记就另开 append-only 文件、另起 fold 目标，永远不要与"被用到"共用一个计数器。

### 5.2 为什么这个窗口里"记录到的覆盖率"没被低估

两条证据叠起来：

1. 显式检索 15 次、`POST /v3/atomic/search` 15 次、`CALLED` 15 次——三个数严格相等，说明**没有第二个检索入口在偷偷跑**（v1 的 `/search/memories` 也是 0 次）。
2. 本部署注入 prompt 的 L1 记忆由 MemoryProxy 完成（`MemoryProxy/src/tdai/client.ts:191-224 searchL1ForCtx` → `POST /v3/atomic/search`，`deploy/global-images/start-proxy.sh:103` 写死 `recallL1: true`）。**它走的是已覆盖的 #2 路径**。

所以"自动注入的记忆有没有被记账"的答案是：**这个部署里有——因为它们走 proxy，不走 core 的 auto-recall**。这是本块最值得写下来的一条，与画布 prompt 的默认假设不同。

**未验证、需保留的疑点**：15 次 `/v3/atomic/search` 里多少来自 proxy 注入、多少来自 MCP 工具，日志分不出来（`CALLED` 行不带调用方身份，`REQUEST_START` 只有 path）。要分清需加字段（`v2-router.ts:1233-1234` 的 `reportRecallMetrics({ instanceId: auth.serviceId, ... })` 已经在拿调用方身份，可复用）。本文不猜比例。

### 5.3 缺口本身：能给的量级与不能给的量级

若部署切到 in-core auto-recall 形态（`POST /recall` 或 openclaw-plugin 的 `before_prompt_build`），缺口就真实存在。分两个口径，一个能算、一个算不出：

**（a）检索次数口径——能算，但只是条件估计**：

auto-recall 每轮对话跑一次（`index.ts:681 before_prompt_build`；`server.ts:1567` 由调用方按 turn 调）。固定窗口（容器启动至今）：18 次 `POST /v3/conversation/add`（capture turn）对 15 次显式检索。若同一窗口换成 auto-recall 形态，会额外产生 ≈18 次检索 → 检索次数低估 **18/(15+18) ≈ 55%**（区间 45%–60%，取决于 turn 与显式检索的实际配比）。这是**次数**，不是覆盖率。

**（b）覆盖率口径——给不出，这是本节的主结论**：

`trackingCoverage` 的口径是"带访问证据的记录数 / 总记录数"（`src/l1-decay.ts:105-110`），不是"检索次数 / 记录数"。auto-recall 每次注入 top-5（容器实配 `recall.maxResults: 5`），与显式检索命中的记录**高度重叠**（同一批用户文本、同一份语料、同一套 FTS+向量），所以"少记 18 次检索"不等于"少记 18 份证据"——重叠部分记不记都已被显式检索记过。这个重叠率是本部署特有的数，现有数据里没有任何字段能算出它。

**要估这个数，缺什么数据、怎么采**：

| 缺的 | 怎么采 | 拿到之后怎么算 |
|---|---|---|
| auto-recall 每次实际注入的 record_id 及名次 | 在 `performAutoRecallCore` 的 `memoryLines` 成型处（`auto-recall.ts:190` 之后）落一份**只观测**的 JSON 行（与 `appendRecall` 同格式）；或临时让 `searchMemories` 的返回结构带上 record_id 再打 debug | 与同期显式检索的记录做集合交并：`Jaccard = \|A∩B\| / \|A∪B\|` |
| 同期显式检索的 record_id（已有） | B2 接线后 `appendRecall` 的日志 | 同上 |
| 总记录数（分母） | `SELECT count(*) FROM l1_records WHERE state='active'`（0101 之后） | 覆盖率 = 带证据记录数 / 该分母 |

**最小可行观测**：把两份记录喂给一个**离线**交集脚本（不进 `foldAccessLog`），跑一周，得到"auto-recall 独占、显式检索没覆盖"的记录数。那个数才是"覆盖率低估"的真值；在拿到它之前**给出任何百分比都是编的**。

### 5.4 未来接入方案（只写方案，本版不实施）

**难度不在"加一次 `appendRecall`"，在"拿不到 record_id 与真实 rank"**：

- `auto-recall.ts:384-389` 的 `SearchResult` 只有 `lines: string[]`、`timing`、`scores?: number[]`——**没有 record_id**。`lines` 是格式化后的自然语言行（`formatMemoryLine`，`:824`），record_id 在格式化那一步就丢了。
- 更要命：`applyRecallBudget`（`:854`）会**裁剪/截断 lines**——注入条数 ≠ 检索返回条数。rank 到底指"检索名次"还是"注入名次"要先定义清楚，否则记下的 rank 与环境里的顺序对不上。

接入要动三层，改动面约是 B2 的 3 倍：

| 层 | 文件 | 要改什么 | 为什么在这层 |
|---|---|---|---|
| L1 数据层 | `core/hooks/auto-recall.ts` 的 `searchMemories`（`:434`）及其 5 个返回点（`:499` nativeBm25 单路、`:509` keyword、`:515` embedding、`:528` nativeHybrid、`:787` 双路 RRF；另有 `:742` / `:791` 两个空结果直返）。**这批行号以 `Select-String` / node 口径为准：`Get-Content` 对本文件只数出 1,008 行（node 1,018）。漂移是累积的、不是常数——实测 `performAutoRecall` GC=85/node=92（+7）、`searchMemories(` GC=426/node=434（+8）、`nativeHybridSearch` GC=513/node=521（+8）、`formatMemoryLine` GC=814/node=824（+10）、`applyRecallBudget` GC=844/node=854（+10）。本行第一版就按 `Get-Content` 抄，整片偏了 8** | 把 `lines: string[]` 扩成带 record_id 的命中（或增平行数组 `recordIds`） | 三个分支各自已持有 FTS/向量结果（`r.record_id` 都在），是唯一还能拿回 id 的地方；再往上只剩格式化后的字符串 |
| 预算层 | `auto-recall.ts:854 function applyRecallBudget`（调用点在 `:190`） | 裁剪 `lines` 时同步裁剪平行的 `recordIds` / `scores` | 不裁就出现"注入 2 条、记账 5 条"，rank 与实际注入顺序错位 |
| 埋点层 | `auto-recall.ts:190` `applyRecallBudget(...)` 之后、`:193` `recalledL1Memories = memoryLines.map(...)` 处 | 调一次 `appendRecall`，与 `memory-search.ts` 共用还是分设日志要先定 | 唯一"已知最终注入顺序"的位置；它与 `memory-search.ts` 的埋点语义不同（注入 vs 返回给调用方），要不要合并进一个计数器属 §9 的遗留决策 |

**为什么本版不做**（三条，按重要性）：

1. **收益为 0**：本部署容器整个生命周期 auto-recall 0 次调用（§5.1，约 37 小时）。给一条不跑的路写代码是纯 YAGNI。
2. **改动面大**：5 个返回点 + 一个裁剪函数 + 一个接口；且这些返回点没有测试覆盖（基线工作副本 `*.test.ts` 计数为 0）。在没测试的树上做 5 点改动，风险与 B2 单点改动不是一个量级。
3. **会污染 B4 的延迟基线**：B4 要测"加日志前后 p99"，若同期又改了 auto-recall 返回结构，对照组含义就混了。

**建议时机**：等 B2 接线并跑够一周（B5 的观测窗口）。届时仍无 auto-recall 流量 → "是否纳入"记为"不需要，除非部署形态改变"；届时切了形态 → 按上表三层做，先用 §5.3 的离线交集脚本量出真值再决定。

## 6. 漏掉的部分（二）：不覆盖的后果，以及日志格式自带的两个坑

### 6.1 后果（按影响排序）

| 不覆盖的东西 | 直接后果 | 会不会咬人 |
|---|---|---|
| auto-recall（§5） | 若切到 in-core auto-recall 形态，注入的记忆不产生访问证据 → 看起来"从没被用过" → 冷启动门槛（`minTrackingCoverage = 0.1`）可能永远过不去，衰减等于没开 | **会**，但只在形态切换后。当前形态不咬（proxy 走已覆盖路径） |
| 零命中检索 | 不留日志行 → 日志行数 ≠ 检索次数 | 只在用行数反推检索量时咬（B5） |
| 三个早退（`:108 / :113 / :123`） | 同上 | 同上 |
| 降级检索（store 不可用） | 同上 | 同上 |
| rank > 10 的命中 | 被 `appendRecall` 丢弃（by design） | 不咬：第 11 名之后的"被用到"本就弱 |

### 6.2 两个坑，写给 B5 与 B3

1. **行数 ≠ 检索次数**：见上表。`foldAccessLog` 的 `linesRead` 是"有命中的检索次数"，不是"检索次数"。分母要用别的手段拿（`CALLED` 日志要求 DEBUG 开着；或加总计数）。
2. **一行里所有 record 是同 rank 语义**：一行 = 一次检索的前 N 条，折一次 = 每条 +1。`foldAccessLog` 已是这个语义（`src/recall.ts:89-101`）。B3 不要"顺手"改成按 rank 加权——`access_count` 的含义是"被返回过几次"，不是分数。

## 6.5 覆盖率爬升：合成日志下的门槛翻转与判读标准

> **本节由 B5（`b5-coverage-watch`）追加，2026-10-28。**数据是**合成的**：日志行由脚本生成，不是真实部署流量。凡是标注「合成」的数字，都只能证明「机制会这样动」，不能证明「真实部署会这样走」。本节不改动 §1–§6 与 §9 的任何结论。

§6.2 把「行数 ≠ 检索次数」列成了一条判读坑，但没有给出「知道这件事之后该看什么」。这一节补上：一条命令、一张翻转表、一份「症状 → 结论」清单。门槛值 `minTrackingCoverage = 0.10` 是 §9 之外的遗留问题——它是拍的，没有数据支撑，本节也不替它辩护。

### 6.5.1 命令

```console
$ node src/cli.ts coverage --db <copy>.db [--vectors l1_vec] [--json]
records            822
with access        96
coverage           0.1168
decay active       true   (threshold 0.10)
if decay on, reordered  top-10   6
probe              query "记忆"  channels lexical/45 fts/45 vector/45  candidates 45
```

五行是契约（`records` / `with access` / `coverage` / `decay active` / `reordered`），后两行是诊断。**只读**：默认只开读连接，唯一会写的是 `--fold-synthetic`。

| 行 | 口径 |
|---|---|
| `records` | `l1_records` 行数，不筛 state |
| `with access` | 带访问证据的记录数。判据是 `hasAccessSignal`（`src/scoring.ts:117`）：`access_count > 0` **或** `last_access_time` 非空——**被观测到的 0 也算证据**，这不是"access_count > 0 的记录数" |
| `coverage` | `with access / records`，即 `trackingCoverage` 本体 |
| `decay active` | `decayEnabled(coverage)`，即 `coverage >= 0.10`。**`--min-coverage` 改了阈值这一行跟着变** |
| `reordered` | 固定 query `记忆` 跑两遍 `rerankHits`：一遍 `decay:false`（纯 RRF），一遍 `decay:true`（带年龄项），**比较前 10 名的位置**，数出换位条数 |

关于 `reordered` 的三个必须知道的口径：

1. **它数的是位置，不是集合差**。「第 4 名换到第 7 名」算一次变化；集合差在这种情形下报 0，而用户看到的列表确实变了。
2. **它描述的是「门开着会怎样」，不是「门现在开着」**。命令**强制** `decay:true` 跑那一遍。若按 `decayActive` 传参，任何冷启动库都会打印 0——那正好是这块最没用的读数。
3. **它不是「衰减有效」的证据**。排序动了 ≠ 排序变好。质量归画布 D（参数校准），本节一个字都不下这个结论。

- **排序动了 ≠ 排序变好。** 见 §6.5.1 第 3 条。

### 6.5.3 判读标准（症状 → 结论）

写成「症状 → 结论」，不写「请自行观察」。

| # | 症状 | 结论 | 处置 |
|---|---|---|---|
| 1 | **覆盖率连续 3 天一点不动**，且 `records` 也没变 | **接线没生效**。配置门没开（`memory.recall.accessLog.enabled: false`）、日志路径父目录不存在（`appendFileSync` 不建目录，写失败静默返回 `false`，§3.2 不变式③）、或埋点根本没打进镜像。三种都是静默失败，检索本身不受影响 | 查 `[decay]` 之外先查是否有日志文件、文件是否在长。§3.2 的路径不变式③ 是最常见的一条 |
| 2 | **覆盖率连续 3 天不动，但 `records` 在涨**（新记忆在写） | **接线生效了，只是没有检索流量**。分母涨、分子不涨 = 有人在写、没人在查。不是缺陷 | 等流量。这是"部署太安静"，不是"接线坏了"——与症状 1 必须分开，两者的处置完全不同 |
| 3 | **覆盖率在涨，但 `reordered` 恒为 0**（连续 7 天、且 `coverage > 0.10`） | **衰减参数可疑**。门开着却不推动排序，三种可能：① 命中窗口（`maxRankCounted`）里的记录恰好都集中在同一段年龄，年龄项无区分度；② 半衰期相对语料年龄跨度过大（`halfLifeDays=30` 对一条 400 天的语料，所有记录都已接近地板 `0.3`，乘数几乎相同）；③ 衰减权重被使用项压住——被命中的记录同时拿到了 `usageFactor` 加成（`searchMultiplier` 的 `d + 0.5*u`），年龄的降权被抵消 | 先看 `channels` 行有没有 0（见症状 6）。再用 `--half-life` 扫一遍（如 7 / 30 / 90），`reordered` 对半衰期不敏感 = 参数不是主因，转画布 D |
| 4 | **覆盖率上去了、`reordered` 也非零，但检索质量没变好** | **本命令回答不了这个**。`reordered` 只说排序动了 | 进画布 D（参数校准），需要 ground truth；本节不含此结论 |
| 5 | **`with access` 比「按 fold 出的 `linesRead` 反推的检索量」少很多** | **正常，是 §6.2 第 1 条那个坑的量化形态**：零命中的检索不落行，`executeMemorySearch` 还有三个早退（`:108` 空 query / `:113` 无 vectorStore / `:123` 无可用检索通道），都不产生日志行。所以 `linesRead` 是**「有命中的检索次数」**，永远 `<=` 真实检索次数 | **不要**用 `linesRead` 反推检索量。分母要拿真实检索次数得靠 `CALLED` 日志（要求 DEBUG 开着）或加总计数（§6.2） |
| 6 | **`probe` 行里有通道是 0**（如 `fts/0` 或 `vector/0`） | **读数降级，`reordered` 不可比**。单通道时全部命中在 RRF 上同分（spread 约 1.6×，见下），融合顺序几乎完全由名次决定，年龄项赢不了——`reordered` 会系统性偏低甚至恒为 0，**看起来像症状 3，其实是探针的问题** | 检查 `l1_fts` 是否存在、`--vectors` 是否指对了 vec0 表。通道恢复前不要把 `reordered` 当证据 |

**判据的时间尺度取「3 天」而不是「一次读数」**：接线未生效与流量为零在单次读数上**完全同形**（覆盖率都是平的），必须靠「分母动不动」区分（症状 1 vs 2）。本部署实测的检索密度是 37 小时 15 次（§5.1），3 天足够让症状 1 和 2 分出彼此。

### 6.5.4 为什么 `reordered` 会先降后稳（**机制，实测**）

翻转表里 `reordered` 从 10 降到 8、最后稳定在 6。这不是衰减失效，是两股力量的比值：

- **融合分的跨度**：RRF 在 45 条候选池上给出的分是 `1/(60+1)` 到 `1/(60+45)`，比值约 **1.63×**。
- **乘数的跨度**：`searchMultiplier` 的年龄项落在 `[0.3, 1.0]`，再叠加使用项加成 `0.5*u`，上界 1.5；语料越"老"，年龄项越贴近地板，**可用的区分度越小**。

两股力量的量级接近（1.63× vs 1.5×），所以换位条数是**两个顺序不一致程度**的函数，而不是「衰减开没开」的函数。语料里带访问证据的记录越多，被命中的记录越容易同时拿到年龄与使用两项的加成，年龄的**相对**影响被稀释——`reordered` 于是下降并稳定。

**推论（对读者的警告）**：拿 `reordered` 的绝对值做「衰减强不强」的判据是不可靠的。**它只在两种情形下可下结论**：① 恒为 0 → 见症状 3/6；② 与上一次读数比较（同一语料、同一 query、同一参数）→ 看趋势。跨语料比较 `reordered` 没有意义。

**另一条实测**：把年龄与融合顺序**对齐**的语料上，`reordered` 会是 0。测试里构造过一个 40 条、单通道、年龄与名次同向的语料，换位条数 **0**；把年龄与名次反向后立刻变成 6。**换位的前提是「融合顺序与年龄顺序不一致」**——一个年轻语料本来就该读到低 `reordered`。
