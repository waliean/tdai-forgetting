# 业界遗忘机制调研（2026-10-26）

查证范围：GitHub 主流 agent memory 框架的遗忘、衰减、淘汰实现。目的是判断要不要自己造，以及能抄什么。

## 结论

1. **检索层软衰减已有成熟共识做法**，三家实现公式几乎一致，参数可直接借用，不必自研。
2. **自动遗忘流水线在开源界基本是空白**。唯一完整实现是 MemoryBear；MemOS 的维护模块是故意留空的 TODO；mem0 的核心实现闭源在云端。
3. **没有可直接安装到 tdai 的现成组件**。这些都是完整框架，换框架会丢掉 L0 白盒溯源和现有三元组隔离，成本高于给 tdai 加几列。
4. tdai 上游自己也没做：issue 明确把 "Bulk / policy-based forgetting" 列为 out of scope。

所以路线是：借算法，不借框架。

## 逐家记录

### mem0（★67.8k，Apache-2.0）

检索时对每条记忆乘一个缩放因子，范围 `0.3×`–`1.5×`。刚被召回的打强化，久未触碰的轻微压制，**永远不过滤候选**——最低只压到 0.3×，原本能出来的现在还能出来，只是排序变了。

实现细节（来自官方文档 `docs/platform/features/memory-decay.mdx`）：

1. 候选池放大到 `top_k × 3`，下限 50，给重排留空间。
2. 分数乘缩放因子。
3. 按未截断的乘积排序。
4. 对外 `score` 仍夹到 `[0,1]`，保持 API 契约。
5. 截断到请求的 top_k。
6. 给每条返回的记忆记一次 fire-and-forget 强化，访问历史只保留最近 20 次触碰。

老记忆没有访问历史时，用 `event_date` 当唯一一次触碰，没有就用 `updated_at`。

2026-05-04 上线，按项目开关，默认关，v3 检索才生效。

**关键发现**：开源仓库里搜不到实现。`mem0/memory/notices.py` 里只有 `DECAY_FEATURE_NOTICE_ID = "decay_stub"` 和 `DECAY_USAGE_STATE_KEY = "decay_usage"` 这类引导用户去用云端特性的提示。算法可以抄文档，代码抄不到。

### MemOS（MemTensor，★12.1k，Apache-2.0）

`packages/memos-core/src/recall/recency.ts`，全文 12 行不到：

```ts
decay(t) = 0.5 ^ (age_days / half_life)
final    = base_score * (alpha + (1 - alpha) * decay)
```

`alpha = 0.3` 是地板，保证又老又相关的结果不被归零；默认半衰期 14 天。注释写明依据是自家 PRD §5.3。

**A 档照这个抄**：TypeScript、Apache-2.0、逻辑完整、没有外部依赖。

同一个仓库的 `src/memos/dream/maintenance.py` 打开是一段空实现，原文：

> This module is intentionally left unimplemented as a contribution entry point.

注释里列了待实现的清理规则（STALE 长期未命中 / LOW USEFULNESS 命中但没用 / INVALIDATED 被反馈推翻），以及已经准备好的字段：`last_hit_at`、`hit_count`、`usefulness_score`、`invalidated_by_feedback`、`status`。连 ★12k 的项目都把这块挂着没人做。

### MemoryBear（★8.6k，Apache-2.0）

唯一把自动遗忘做完的开源实现，中文注释，架构清晰。

`api/app/core/memory/storage_services/forgetting_engine/forgetting_engine.py` 用改进的艾宾浩斯曲线：

```
R(t, S) = offset + (1 - offset) * exp(-lambda_time * t / (lambda_mem * S))
```

`offset` 是最低保持率，防完全遗忘；`S` 是记忆强度，越大越难忘。

`forget_service.py` 是配额驱动的软删除流水线，逻辑值得照搬：

1. 核心池活跃节点数不超过配额，直接返回。
2. 超配额时算预算 `budget = active - target`，`target = max(limit * (1 - lambda_mem), 50)`。
3. 第一优先级：删已经完全离散（无有效关系）的核心节点。
4. 第二优先级：按 `created_at` 分批清辅助池，每批之后重新找因端点失效而变成离散的核心节点。
5. 全程软删除，写审计日志（`ForgetLog`），落遗忘周期历史表，还有可视化模块。

配套文件：`forgetting_pipeline.py`（流水线编排）、`forgetting_scheduler.py`（调度）、`forgetting_cycle_history_model.py`（历史表）、`forgetting_visualizer.py`（可视化）。

**B 档架构照这个抄。**

### Graphiti（★32.2k，Apache-2.0）

双时间戳。边带 `valid_at` / `invalid_at` / `expired_at`，新事实推翻旧事实时把旧边标失效，不删。检索时按时间点过滤，可以查"某个时刻的事实是什么"。

`graphiti_core/utils/maintenance/edge_operations.py` 里有失效标记的落地逻辑。

专治"过时结论照样被召回"。**C 档照这个抄。**

### MemoryOS（BAI-LAB，★1.6k，Apache-2.0，EMNLP 2025 Oral）

三段式（短/中/长）分层，中件层带热度淘汰。`memoryos-pypi/mid_term.py`：

```python
H = alpha * N_visit + beta * L_interaction + gamma * R_recency
R_recency = time_decay(last_visit_time, now, tau_hours=24)
```

超容量（`max_capacity=2000`）触发 `evict_lfu()`，按访问频次最低淘汰；热度超阈值（`H_THRESHOLD = 5.0`）触发把中件记忆上提到用户画像。

比纯时间衰减多考虑了访问次数和交互长度。**B 档的判分公式用这个，比纯时间合理。**

### cognee（★32.8k，Apache-2.0）

`cognee/api/v1/forget/forget.py` 提供统一 `forget()`，四档：单条 `data_id`、整个 `dataset`、`everything`、`memory_only`（只删图与向量，保留原始文件以便重新处理）。

是**人工遗忘**的 API 设计，不解决自动化。但 `memory_only` 这个语义值得借鉴：删记忆保留原始数据，等于可重建。

### memoripy（★694，Apache-2.0）

证据优先的本地记忆，有 `forget()`、`correct()`，记录带 `valid_from` / `valid_to`，检索支持 `as_of` 时间旅行。还有 `audit()`、`feedback(outcome=...)` 和采纳策略（admission policies）。

小项目但生命周期设计完整，可以作为字段设计的参考。

### Letta / MemGPT（★25.3k）

不遗忘，靠分页：核心记忆（在上下文内）↔ 归档记忆（在外部），用工具调用在两边搬。所谓淘汰是"移出上下文"，不是删除。

思路可以借：遗忘首先应该是"移出可召回集"，物理删除是另一个决策。**本仓库的 `state` 分层直接来自这条。**

### FSRS / open-spaced-repetition

工业级遗忘曲线，幂律形式 `R = (1 + FACTOR * t / S) ^ DECAY`，配合间隔重复调度算法。比指数模型更贴合真实遗忘，但要维护 stability/difficulty 等状态，对我们的场景过重。作为未来可选。

## 抄什么、抄自哪

| 要做的事 | 抄谁 | 具体文件 |
|---|---|---|
| 检索层时间衰减 | MemOS | `packages/memos-core/src/recall/recency.ts` |
| 参数取值与边界 | mem0 | `docs/platform/features/memory-decay.mdx`（0.3 地板、候选池放大、访问历史 20 次） |
| 热度判分（含访问次数） | MemoryOS | `memoryos-pypi/mid_term.py` |
| 配额驱动软删除 + 审计 | MemoryBear | `forgetting_engine/` 整个目录 |
| 双时间戳失效 | Graphiti | `graphiti_core/utils/maintenance/edge_operations.py` |
| 人工遗忘 API 语义 | cognee | `cognee/api/v1/forget/forget.py` |
| "先移出召回集，再谈删除" | Letta / MemGPT | 分页架构本身 |

许可证全部 Apache-2.0，公式和架构层面移植没有障碍。

## 调研结论如何影响实现

不只是"抄哪个公式"，三条来自调研的判断改变了设计：

1. **mem0 宁可压到 0.3 也不过滤**，所以本实现的下限固定在地板而不是 0。第一版曾想把系数写成"低于阈值直接剔除"，被这条否决。
2. **Letta 的"移出上下文 ≠ 删除"**，所以 `state` 是四态而不是布尔 `deleted`。
3. **Graphiti 的双时间戳**在受控实验里完胜时间衰减（见实测报告实验三），所以方案把"显式失效"列为后续必做项，而不是当作可选项。

## 上游状态

tdai 仓库（`TencentCloud/TencentDB-Agent-Memory`）issue 里有一条明确记录：给 Pi adapter 加交互式 `/tdai-memory-forget` 命令，带打码预览和确认门。但明确写了 out of scope：

> - 修改 MemoryCore 删除语义
> - Bulk / policy-based forgetting (that's a separate design)

也就是说人工单条删除上游在做，**基于策略的自动遗忘上游没做，也没有排期**。

## 一句话

公式有人给，架构有人给，没人替我们装。tdai 这几列得自己加。
