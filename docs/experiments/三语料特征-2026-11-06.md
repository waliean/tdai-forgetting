# 三语料特征与长文本语料构造 — 2026-11-06

画布 D 的 D2。目的只有一个：让后面所有的参数扫描知道自己是在什么数据上做的，以及哪些结论换一份语料就会失效。

## 一、为什么要有第三份语料

`10%` 门槛、`30` 天半衰期、`0.6` Jaccard 这三个数是在短句语料上拍的。合成语料和真实快照都是 40–90 字一条的笔记，而 `shingles(content, 4)` 在短文本上产生的集合大小几乎等于字符数——两段改写过的事实仍然共享大部分集合，0.6 这条线在那类文本上有意义。

1200 字的文档不是这样。共享部分是固定的前缀，集合却随长度增长，Jaccard 被长度稀释。这是已知缺陷，D5 才决定怎么处理。D2 只负责把这种文本造出来，好让 D5 有东西可测。

## 二、三份语料对不上眼的地方

| 项 | snapshot（真实） | synthetic（合成） | longtext（合成） |
|---|---|---|---|
| 记录数 | 822 | 698 | 120（60 组 × 2 版） |
| 长度 min / p50 / p90 / max | 19 / 328 / 805 / 1739 | 59 / 70 / 77 / 86 | 540 / 570 / 1226 / 1251 |
| type 分布 | episodic 529（64.4%）、instruction 227（27.6%）、persona 66（8.0%） | episodic 477（68.3%）、instruction 221（31.7%） | episodic 86（71.7%）、instruction 34（28.3%） |
| pin 比例 | hard 170 + extended 40（25.5%） | hard 41 + extended 0（5.9%） | hard 2 + extended 0（1.7%） |

| 有访问数据 | 否（coverage 0%） | 是（coverage 30%） | 是（约 40%，gate 会开） |

三份语料的长度分布几乎不重叠：snapshot 的中位数 328 字，synthetic 的 70 字，longtext 的 brief 570 字、full 1226 字。

## 三、长文本语料是怎么造的

`bench/corpus-long.ts`，默认 60 组，每组两条：

- **brief**：5 句拼成，540 字上下。
- **full**：同一组的前 11 句，1200–1260 字。**full 以 brief 的正文开头**，不是复述、不是改写，就是同一段文字后面继续写。所以任何检测器都该把它们配对。

句子不是真实文档摘录，是五类短语槽的模板组合：主语 12 种、症状 12 种、原因 12 种、处置 12 种、结果 12 种，其中原因、处置、结果各再乘一个修饰短语（6 种），合起来 12⁵ × 6³ = 53,747,712 种句子。读起来像部署手册和事故复盘的句子，只保证长度和前缀结构，不保证语义连贯。

两个约束是刻意的，写在这里免得下次改坏：

1. **句子在整个语料内不重复。** 用 32 位 avalanche 混合把句子序号打散再取槽值。用线性步长试过一次，混合基数下会反复撞到同几个小基数槽，三份 full 互相相似到 0.62，直接产生了 3 个假重复组。线性步长和 8 种槽值的版本都试过并弃用，原因写在代码注释里。
2. **不同事实组之间不能过像。** 组间最像的两条 brief 相似度 0.385，两条 full 0.484，都在 0.6 以下，所以上面表里的「0 组」是干净的。

## 四、三个必须先知道的事实

### 1. 真实快照上 `decayOn` 恒为 `false`

`data/snapshot-20261026.db` 没有任何访问数据，`trackingCoverage` 是 0，`10%` 门槛永远不过。sweep 在这份语料上的每一行 `decayActive` 都是 `false`。

这不是缺陷。它意味着**在这份语料上扫描 `halfLifeDays`、`floor`、`minTrackingCoverage` 三个参数不会产生任何差异**——门关着，衰减项根本不参与排序。D3 拿 snapshot 扫这三个参数会得到一条平线，那不是"参数不敏感"，是"参数没被用上"。报告里必须这样写，不能把它当敏感度结论。

### 2. 长文本语料里 60 组同事实，默认检测器一组都没抓到

`findRedundancyClusters` 返回 0 组，而语料里确实有 60 组同一事实的长短两版。

原因不是简单的"Jaccard 被稀释到 0.6 以下"。实测同组 brief/full 的 Jaccard 在 **0.493–0.632** 之间，有几个组其实越过了 0.6。真正挡住它们的是更早的一道闸：

```
const lenRatio = min(len_a, len_b) / max(len_a, len_b);
if (lenRatio < opts.threshold) continue;   // 0.43 < 0.6，直接跳过，不算 Jaccard
```

brief 570 字、full 1226 字，长度比 0.46，小于 0.6，这一对在算相似度之前就被丢掉了。

所以准确的结论是：**长文本的重复检测失败有两层，长度预过滤先挡掉长短版，Jaccard 稀释再挡掉等长版本。** 只改阈值不解第一层。这个区分是 D5 要用的。

### 3. 真实快照在 0.6 阈值下只有 1 个重复组，"迁移副本多"的说法不成立

计划文档和 C 收口文档都写过真实语料"迁移副本多"。实测 822 条里只有 1 组（2 条）。

两种可能：要么副本实际不存在到那个程度，要么副本的相似度低于 0.6（迁移时改了头部字段，和合成语料里 `副本 N：` 前缀的效果一样）。**无论哪种，结论相同：0.6 这条线看不到它们。** 这是一个应该进 D3 的观察点，不是一个可以忽略的统计噪声。

## 五、复现

```bash
node bench/sweep.ts --describe --out .scratch/syn.csv
node bench/sweep.ts --corpus longtext --describe --out .scratch/lt.csv
node bench/sweep.ts --corpus snapshot --db data/snapshot-20261026.db --describe --out .scratch/snap.csv
```

`--describe` 把统计打到 stderr，CSV 只放参数与指标——语料特征是输入，指标是输出，混在一张表里列就没有确定含义了。

三份语料各跑一次最小网格都通过，耗时 219 / 176 / 1013 ms（snapshot 慢在 822 条的 O(n²) 聚类）。
