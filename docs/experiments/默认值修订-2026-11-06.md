# 默认值修订 — 2026-11-06

画布 D 的 D4。改的是三个文件里的默认值，依据是 D3 的扫描表，不是拍。

一句话结论：**`halfLifeDays` 30 → 10，`floor` 0.3 → 0.2，`clusterThreshold` 0.6 → 0.7；另外三个参数扫了没有更好的值，保持原值。**

## 一、改了什么

| 参数 | 旧值 | 新值 | 落点 | 依据 |
|---|---|---|---|---|
| `halfLifeDays` | 30 | **10** | `src/scoring.ts` `DEFAULT_DECAY`、`src/l1-decay.ts` `DEFAULT_DECAY_SETTINGS`、`patches/0103` | pinRecall 平台 5–14 天，中点约 9.5 |
| `floor` | 0.3 | **0.2** | 同上 | 稳定区 0.1–0.3，中点 0.2 |
| `clusterThreshold` | 0.6 | **0.7** | `src/redundancy.ts` `DEFAULT_CLUSTER_OPTIONS`、`bench/harness.ts` | 安全区间 0.6–0.8，中点 0.7；0.6 距悬崖只有 0.2 |
| `minTrackingCoverage` | 0.1 | 0.1（保持） | — | 0–0.2 无差异，中点是原值 |
| `archiveThreshold` | 0.45 | 0.45（保持） | — | 0.1–0.47 全平，没有更好的值 |
| `retireThreshold` | 0.25 | 0.25（保持） | — | 0.1–0.45 全平，中点是 0.25 |

三处必须同步改，少一处就漂移：引擎（`scoring.ts`）、补丁模块的仓库镜像（`l1-decay.ts`）、补丁本体（`patches/0103`）。`test/equivalence.test.ts` 就是为此存在的，改引擎不改补丁时它立刻报 `drift at age=1d: engine=0.946, patch=0.984`。

## 二、指标前后对照

`node bench/run-bench.ts --queries 24 --k 10 --no-embeddings`，同一台机器、同一份合成语料：

| configuration | precision@k | top1 | dupShare | pinRecall | avgScore |
|---|---|---|---|---|---|
| baseline（改前） | 0.396 | 1.000 | 0.271 | 0.333 | 0.4641 |
| baseline（改后） | 0.396 | 1.000 | **0.208** | 0.333 | 0.4641 |
| decay（改前） | 0.404 | 0.417 | 0.196 | 0.750 | 0.4258 |
| decay（改后） | **0.417** | 0.458 | 0.192 | **0.833** | **0.3182** |
| forgetting（改前） | 0.412 | 0.417 | 0.000 | 0.750 | 0.4271 |
| forgetting（改后） | **0.414** | 0.458 | 0.000 | **0.833** | **0.3238** |

三件事：

1. **pinRecall 0.750 → 0.833**，这是改半衰期的直接目的：默认值原来停在 pin 召回开始下滑的拐点上方。
2. **precision 0.412 → 0.414**，基本没动。这次不是拿精度换召回，是白捡的。
3. **avgScore 0.4271 → 0.3238 掉了 0.10**。这是 `floor` 0.3 → 0.2 的直接后果，不是退化：floor 就是这个分数的下界，下界降了 0.1，分布整体左移。任何拿 `avgScore` 做绝对比较的历史记录都不能和新数字直接比——**这是本轮唯一一条会让历史数字失效的改动**。`top1` 也从 0.417 升到 0.458，同理是重排的结果。

`baseline` 的 `dupShare` 0.271 → 0.208 来自 `clusterThreshold`：窗口内判重的阈值变严，被标为重复的槽位少了。

## 三、为什么选中点而不是最优点

D3 的表格里，synthetic 上的最优分别出现在 `halfLifeDays=90`（precision 0.470）、`floor=0.5`（precision 0.457）、`clusterThreshold=0.5`（precision 0.465）。三个都没选：

- `halfLifeDays=90` 的 pinRecall 是 **0.458**，比默认值还低。
- `floor=0.5` 的 pinRecall 是 **0.625**。
- `clusterThreshold=0.5` 的 evictedShare 是 **0.778**，把 78% 的语料归了档。

三个"最优点"都是靠牺牲另一个指标换来的 precision，而且都落在区间边缘——换一份语料就掉出去。选平台中点是在选"换语料后还站得住的那个"。

## 四、保持原值的三个，扫了但没找到更好的

- **`minTrackingCoverage` 0.1**：扫描范围 0 / 0.05 / 0.10 / 0.20 / 0.40。它不是连续参数，是开关：在语料 coverage 之上怎么调都不动，越过就一次翻转。synthetic（coverage 29.9%）和 longtext（33.3%）在 0–0.2 之间读数完全相同，snapshot（0%）在 0.05 起就已经关门。0.1 落在无差异区间的中点，没有数据支持挪动它。**这个值唯一被数据证明的价值是它挡住了 cold-start**：snapshot 上强制开门（`=0`）时 precision 从 0.2380 掉到 0.1588。
- **`archiveThreshold` 0.45**：当时扫描范围 0.1–0.5，0.1–0.47 是一整条平线，因为三份语料的分数下界（0.471 / 0.485 / 0.550）都比它高，Pass 1 零命中。**保持原值在当时是对的，但这条结论有后半截（见第七节）。**
- **`retireThreshold` 0.25**：扫描范围 0.1–0.6。0.1–0.45 平线，原因同上；0.5 起才有记录进入 retire 分类。0.25 落在这条平线的中间偏下，没有更好的位置。

## 五、两个连带修正（不是可选项）

改默认值揭出了两处隐藏的重复定义，不改就是留着一个假等价：

**1. `MIN_MULTIPLIER` 与 `floor` 是同一个概念。** `src/scoring.ts` 原先有个常量 `const MIN_MULTIPLIER = 0.3`，把 multiplier 夹在 `[0.3, 1.5]`；补丁里用的是 `cfg.floor`。`floor` 恰好等于 0.3 时两者一致，所以从没暴露。floor 改到 0.2 后，引擎夹在 0.3、补丁夹在 0.2，`equivalence` 报 `drift at age=90d: engine=0.3, patch=0.2016`。现在下界统一用 `cfg.floor`，`MIN_MULTIPLIER` 删除。

**2. `bench/harness.ts` 复制了阈值。** 它在 D1 里定义了 `DUPLICATE_THRESHOLD = 0.6`，而 `src/redundancy.ts` 的 `DEFAULT_CLUSTER_OPTIONS.threshold` 也是 0.6——两个 0.6 是巧合相等，不是同一个数。`clusterThreshold` 改到 0.7 后，`run-bench` 的 forgetting 行（用 harness 的 0.6）和 `sweep` 的默认行（用 redundancy 的 0.7）立刻读出不同的 precision（0.421 对 0.4137）。现在 `DUPLICATE_THRESHOLD` 是 `DEFAULT_CLUSTER_OPTIONS.threshold` 的别名。

**补丁本身只改了两个数字，没有加注释。** 试过在 `patches/0103` 的 `l1-decay.ts` 段里加三行说明，`git apply` 会因为 hunk 行数变化失败——补丁是 byte-exact 产物。改动后补丁仍是 640 行，与改动前一致。`0002-l1-decay-module.patch` 里的同一对数字**没有改**：它属于已退役的 0001–0004 系列，保留作历史证据，不在当前应用链上。

## 六、测试

`npm test` 全量 **230 / 230 通过**，`tsc --noEmit` 通过。改了期望值的 6 个文件：

| 文件 | 改了什么 |
|---|---|
| `test/scoring.test.ts` | multiplier 下界断言从字面量 `0.3` 改为 `DEFAULT_DECAY.floor` |
| `test/l1-decay.test.ts` | 六天龄记录的多重器从手写 `0.3 + 0.7 * 2^(-6/30)` 改为从 `DEFAULT_DECAY_SETTINGS` 计算 |
| `test/coverage-recall.test.ts` | `reordered` 测试显式用 `halfLifeDays: 30, floor: 0.3`（不是为掩盖失败，见下）；去掉我先前多加的"集合差必须为 0"这条过强断言 |
| `test/cli-coverage.test.ts` | `reordered` 从断言等于 0 改为断言是有效数字 + probe 非空 |
| `test/sweep.test.ts` | 默认点期望值 `30/0.3/0.1/0.6` → `10/0.2/0.1/0.7`；`--describe` 的阈值从字面量改为读常量 |
| `test/corpus-long.test.ts` | 同上，`duplicate groups at 0.6` 改为读常量 |

两处要单独说明，因为它们看起来像"改测试迁就代码"：

**`reordered` 从 0 变成 4。** 原测试注释里写得很清楚：断言非零曾经依赖巧合，canvas C 改 fixture 时就红过。断言**等于 0** 是同一类巧合——它成立的前提是 decay 因子在语料上严格单调、没有 tie。短半衰期 + 低 floor 让一批老记录的 multiplier 一起塌到 0.2 附近，tie 处顺序就会变。现在断言的是不变量：这个数字来自非空 probe。具体值属于参数，不属于代码。

**`coverage-recall` 的 `reordered` 测试显式钉住 `halfLifeDays: 30, floor: 0.3`。** 这个测试要证明的是"`reordered` 量的是位置移动，不是集合差"，需要构造"同样十条记录换了顺序"。用新默认值时这两条记录直接换人，集合差和位置移动恰好相等，测试会假通过。钉住一组能产生目标形状的参数是对的，注释里写了理由。

## 七、后续修正（同日重跑 D3 后补记）

**第四节说“两个绝对阈值都不起作用”，这句在改完 floor 之后只对了一半。**

floor 从 0.3 降到 0.2，把无 usage 信号的分数下界从 `(0.4×0.55 + 0.3×0.3)/0.7 = 0.471` 拉到了 `(0.4×0.55 + 0.3×0.2)/0.7 = 0.401`。`archiveThreshold` 0.45 本来在下界之上，现在落进了分数分布里：

| | 分数下界 | `archiveThreshold` 0.45 命中 |
|---|---|---|
| 改 floor 之前 | 0.471 | 0 条 |
| 改 floor 之后 | **0.401** | **83 条**（synthetic） |

所以当前代码下 `archiveThreshold` **是有效参数**：0.35–0.40 仍平（在下界下），0.45 起每 0.05 多归档 7–10 个点。重跑后的完整数据见 [参数敏感度](./参数敏感度-2026-11-06.md) 第零节与第五节。

`retireThreshold` 仍然无效（0.25 远低于 0.401），不受影响。

**这件事本身比那个数字重要：改一个参数会改变另一个参数是否生效。** 本轮的 OAT 扫描是“在其余参数取某一组值的前提下”的结论，D4 改了 floor，那些前提就变了。所以：

- 改任何默认值之后，**应该重跑一遍扫描**，而不是相信上一次的“这个参数没差异”；
- 本节的结论已按重跑数据修正，但**第四节里那两个“保持原值”的决定本身不需要改**：当时它们确实无效，保持是唯一有依据的选择。需要改的是理由的表述。

## 八、CI 闸门

`.github/workflows/ci.yml` 的 `bench-regression` 有两条闸门，**都没有改**：

- `forgetting.dupShare > 0.05` 判失败 → 实际 0.000
- `forgetting.pinRecall < baseline.pinRecall - 0.05` 判失败 → 实际 0.833 对 0.333，高出 0.500

新默认值让 pinRecall 更高、dupShare 仍为 0，闸门比改前更容易通过。**没有放宽任何标准，所以没有可解释的调整。** 如果将来有人为了过闸门去调这两个数，那时的对照表必须拿出来看——现在这一轮没有这个必要。

## 九、后续之二：`retireThreshold` 改为分位口径（同日）

第七节确认了 `retireThreshold` 是唯一仍然无效的参数。处置方式不是删掉它，是给 retire 加一条**分位口径**：`DEFAULT_EVICTION.retirePercentile = 0.1`，切点取语料自身分数的底部 10%，**只在 decay 门开时生效**。

为什么只在门开时：冷启动语料上分数只由 importance 决定，「底部十分之一」意味着「最不重要的十分之一」而不是「最没用的」——不该基于一个没人采集的信号去淘汰。门关时回退到 `retireThreshold`（默认 0.25），在那些语料上它不可达，所以淘汰 0 条——与以前一致。

行为变化（当前默认值）：

| 语料 | 改前（归档/退休） | 改后（归档/退休） | 合计 |
|---|---|---|---|
| synthetic | 237 / 0 | 169 / **68** | 237（不变） |
| longtext | 66 / 0 | 56 / **10** | 66（不变） |
| snapshot | 0 / 0 | 0 / 0 | 0（门关，走绝对值） |

**总量一条没变，变的是分类**：默认切点（0.441 / 0.428）在 `archiveThreshold` 0.45 以下，所以退休的是本也会归档的那批。这是有意为之——引入新机制不该让系统多删东西。

新旧参数的关系：

- `retirePercentile > 0` 且 decay 开着 → 用分位切点；
- 否则 → 用 `retireThreshold`（向后兼容的 fallback）。
- `plan` 的输出和渲染新增 `retire cut`，报实际生效的那个数——因为它不再等于配置里的 `retireThreshold`。

敏感度：`retirePercentile` 在 0–0.1 之间 `evictedShare` 完全不变，0.2 起开始上升（0.3968 / 0.5833），0.3 时 0.4570 / 0.6333。默认 0.1 落在平台右端（按使用者指定的 p10），离 0.2 的拐点还有两倍余量。

退化：分位切点取 `floor(p × (n−1))` 处的值、比较严格 `<`，所以「底部 10%」是「大约十分之一」而不是「正好十分之一」。

## 十、还剩什么问题

- `avgScore` 的量纲变了（下界降 0.1），历史绝对数值不可比。已在第二节标出。
- `retired` 的数量在 CSV 里看不到（`evictedShare` 合并了 archive 与 retire）。D3 报告里提过，本轮没动 CSV 格式。
- **分位口径只在 decay 开时生效**，所以一个从未采集过访问数据的部署永远不会 retire 任何东西，只会 archive。这符合设计（没有证据就不做更深一层的淘汰），但如果运维期望看到 retire 发生，得先把访问追踪接上。
