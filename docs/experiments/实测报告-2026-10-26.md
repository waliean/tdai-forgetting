# 实测报告（2026-10-26）

三个实验，回答三个不同的问题。全部用同一份真实快照（822 条 L1 原子记忆，519 条带 bge-m3 向量），全部可复现。

复现前提：本机 Ollama 加载 bge-m3，快照放在 `data/snapshot.db`（`.gitignore` 已排除，不入库——记忆库是个人数据，哪怕 schema 是公开的）。

## 实验一：检索质量（bench/eval-embedding.ts）

**问题**：加了衰减之后，检索变好还是变差？

**方法**：ground truth 用 embedding 余弦独立构建——对每个查询取 top-30 相似记录。这条路径与被测的两条检索路径（FTS 词面 + 向量）都不共享机制，所以 precision 不会被被测对象自己定义。

```bash
node bench/eval-embedding.ts --db data/snapshot.db --queries 20 --k 10 --truth-budget 30
```

**结果**：

| 配置 | precision@10 | recall@10 | pin 召回 |
|---|---|---|---|
| baseline（纯 RRF） | 0.955 | 0.955 | 1.000 |
| 衰减（门槛生效） | 0.955 | 0.955 | 1.000 |
| 衰减（强制开启） | 0.920 | 0.920 | 1.000 |

快照的访问覆盖率是 0%，门槛关闭了年龄项，所以"衰减"与 baseline 完全一致。强制开启则掉 3.5 个点——全部损失来自把年龄当作无用证据。

**结论**：在没有接入访问追踪之前，这套改动不会提升检索质量。它会提升可解释性和后续退化的空间，但短期内是零收益。这一点必须写在部署说明里。

## 实验二：三种访问数据来源（bench/experiments.ts）

**问题**：衰减的前提是"被召回过的记忆更有用"。这个前提在什么条件下成立？

**方法**：同一快照，三种访问数据来源，同一 ground truth。

- `cold-start`：完全没有访问数据（= 今天所有 tdai 部署的状态）
- `warm-random`：访问次数随机分配，即"被召回"与"相关"无关，前提被构造成假的
- `warm-recall`：真的跑 200 次检索，把返回的 top-5 记成访问，时间散布在过去 30 天

```bash
node bench/experiments.ts --db data/snapshot.db --queries 20 --k 10 --episodes 200
```

**结果**：

| 条件 | 覆盖率 | 门槛 | 纯 RRF | 强制衰减 | 按门槛 |
|---|---|---|---|---|---|
| cold-start | 0% | 关 | 0.955 | 0.920 | 0.955 |
| warm-random | 31% | 开 | 0.955 | 0.920 | 0.920 |
| warm-recall | 8% | 关 | 0.955 | 0.905 | 0.940 |

**读法**：

- 随机访问数据下，衰减同样掉 3.5 个点。这符合预期：前提是假的，公式再好也没用。只跑这个实验会得出"衰减有害"的错误结论。
- 真实召回数据下，衰减掉 1.5 个点，门槛把它减到 1.5（覆盖率 8% 仍低于 10%，门槛关闭年龄项，剩下的损失来自使用次数项）。
- 覆盖率 8% 这个数字本身值得注意：200 次检索只覆盖了 67 条记录。真实系统的覆盖率要靠长期积累，短期内门槛会一直是关的。

**结论**：衰减的收益取决于访问数据的真实性，而访问覆盖率决定门槛是否打开。这两件事都不在本仓库的控制范围内——它们取决于部署方是否接入 `src/recall.ts`。

## 实验三：过期结论（bench/supersede.ts）

**问题**：真实快照里没有可修的过期数据（近重复是同一天迁移副本，不是新旧结论）。那衰减在它**本来该解决问题**的语料上表现如何？

**方法**：构造受控语料——每个事实有三个复述版本，分别在 90/60/30 天前写入，措辞高度相似，只差版本标记。查询是该事实本身，正确答案是最新那版。

```bash
node bench/supersede.ts --facts 10 --k 3
```

**结果**（2026-11-04 复跑，真实 `invalid_at` 字段）：

| 配置 | 最新复述排第一 | 窗口内过期副本 |
|---|---|---|
| baseline | 0.000 | 2.00 |
| 衰减（强制） | 1.000 | 2.00 |
| 衰减（门槛关闭） | 0.000 | 2.00 |
| 衰减 + 冗余合并 | 1.000 | 2.00 |
| **失效标记（真实字段）** | **1.000** | **0.00** |

### 机制变更：从"手工模拟"到真实字段

这一列原来叫 `explicit-supersession`，实现方式是一个内存里的 `Set`：

```ts
// 旧：把"哪些是过期的"当已知条件直接喂给排序
const supersededIds = new Set(cases.flatMap((c) => c.records
  .filter((r) => r.record_id !== c.currentId).map((r) => r.record_id)));
configs["explicit-supersession"] = (c) => c.filter((h) => !supersededIds.has(h.record.record_id)).slice(0, k);
```

**那个 `Set` 是 ground truth，真实检索路径永远不会有。** 它证明了"显式标记有用"这个**概念**，但没有证明**机制**——因为填充 `Set` 的那行代码自己就是答案。

现在改成读真实字段（画布 C 的 `invalid_at` / `superseded_by`，就是 `supersede` 命令写的那个）：

```ts
// 语料构造：旧复述的 invalid_at 设为新复述落地时刻，superseded_by 指向它
invalid_at:    superseded ? currentStamp : null,
superseded_by: superseded ? currentId : null,

// 检索：过滤 invalid_at 非空者再取前 k，对应 C3 打进召回查询的那个谓词
configs["invalidation"] = (c) => c.filter((h) => !h.record.invalid_at).slice(0, k);
```

**过滤发生在 top-k 截断之前**，与查询侧一致（真实部署在 SQL 里丢掉失效行，窗口从有效候选回填，而不是截短）——这也顺带免掉了"先截断再过滤会少一条"的伪降级。

### 数字对照

| 列 | 机制变更前 | 机制变更后 | 差异 |
|---|---|---|---|
| baseline | 0.000 / 2.00 | **0.000 / 2.00** | 无——语料未被改动，这是"没动过语料"的证据 |
| 衰减（强制） | 1.000 / 2.00 | **1.000 / 2.00** | 无 |
| 失效标记 | 1.000 / 0.00（内存 Set） | **1.000 / 0.00**（真实 `invalid_at`） | 无 |

**换了机制，数字一模一样。** 这不是巧合也不是好消息的全部：它说明当初那列数字**是对的**，但也说明**它一直没有证明过机制**。现在证明了。

### 这一列是否真的有判别力（变异测试）

数字对得上不等于测试在干活。删掉过滤谓词、或让语料不写这个字段，该列立刻塌回 baseline：

| 变异 | 失效标记列 |
|---|---|
| 无（原样） | 1.000 / **0.00** |
| 过滤改成 `() => true`（不过滤） | 0.000 / **2.00** |
| 过滤改成按 `state === 'active'`（查错字段） | 0.000 / **2.00** |
| 语料的 `invalid_at` 恒为 `null` | 0.000 / **2.00** |

四种变异都已由 `test/supersede-bench.test.ts` 钉住（前三种改 bench 即挂，第四种挂两条）。**这一列现在会被"不再过滤"这件事弄红**，而不是悄悄绿着。

> 遗留：`decay-forced` 列 1.000 / 2.00 **不算"判别力不足"**——它本来就该是这个数（衰减只改排序）。这句话是提醒读者别把两件事混起来。

**读法**：

baseline 的最新版排第一概率是 0——不是因为排序随机，而是三个版本字面相似度完全一样，词面和向量都给不出偏好，于是按写入顺序返回，最老的先出来。这正是衰减要解决的场景。

衰减把概率拉到 1.000，做对了一件事：它能用时间戳区分新旧。但它**没有**把过期副本挤出窗口（仍是 2.00 条），因为衰减只改排序不改取舍。

显式 `invalid_at` 标记两件事都做到了。

**结论**：时间衰减是失效标记的代理。代理只在时间戳可信时有效，而且天生比标记弱——它改变排序，不改变取舍。字段能表达的事情，不要用启发式去猜。这也是为什么 `docs/design` 把双时间戳列为"未做，但值得做"。

**本画布的验收数字**：`stale-in-window` 从 **2.00 降到 0.00**，用的是真实字段而不是模拟——画布 C 的 C1（建列）+ C3（召回过滤）在受控语料上确实有效。

## 实验四：冗余合并（bench/run-bench.ts，合成语料）

**问题**：同一件事被不同迁移轮次写了多遍，合并副本能省多少坑位？

**方法**：合成语料（`bench/corpus.ts`，固定种子，可入库）。访问历史按"话题热度"生成——热门话题常被问、长尾从不被碰，而不是随机给记录发访问次数。随机给会让使用次数项测的是噪声，得出的结论在真实部署里不会发生。

```bash
node bench/run-bench.ts --queries 24 --k 10
```

**结果**（24 个查询，698 条记录，41 条 pin，访问覆盖率 30%）：

| 配置 | 主题 precision@10 | dupShare | pin 召回 |
|---|---|---|---|
| baseline | 0.396 | 0.271 | 0.333 |
| 衰减 | 0.404 | 0.212 | 0.583 |
| 衰减 + 冗余合并 | 0.420 | 0.000 | 0.583 |

**必须说明的口径问题**：这里的 precision 是按"同话题"判的，不是按"答得上"。top1 指标在合成语料上是退化的——查询就是从句内记录切出来的，融合一定先找到它，所以 top1 从 1.000 掉到 0.375 只说明"衰减把查询来源那条压下去了"，不是质量下降。**能引用的只有真实快照上的 embedding 口径**（实验一、二）。合成语料的用途是验证机制能跑通、能进 CI，不是证明效果。

## 实验五：pin 排序策略（bench/pin-policy.ts）

**问题**：pin 的检索系数该给多少？

初版把 hard pin 设成 1.5（上限），理由是"中性 1.0 会让近期被召回的记录爬到 pin 上面"。这个直觉值得单独测。

**方法**：三种策略在同一快照同一查询集上对比。

```bash
node bench/pin-policy.ts --db data/snapshot.db --queries 20 --k 10
```

**结果**（822 条记录，hard pin 占 21%、extended pin 占 5%，20 个查询）：

| 策略 | precision@10 | pin 召回 | 窗口内相关 pin 数 |
|---|---|---|---|
| neutral（1.0） | 0.920 | 1.000 | 7.90 |
| ceiling（1.5） | 0.885 | 1.000 | 8.50 |
| excluded（从候选池移除） | 0.780 | 0.850 | 1.95 |

**读法**：

- ceiling 比 neutral 多召回 0.6 条相关 pin，但代价是 precision 掉 3.5 个点——挤掉的相关命中比换来的 pin 更值钱。
- excluded 是最糟的：precision 掉 14 个点，pin 召回也掉到 0.85（连"永远保留"都没做到）。保护过头和取消保护一样有害。
- 采用 neutral：**"永不遗忘"是关于保留的承诺，不是关于排序的承诺**。一条被召回二十次的记录，应该压过一条从没被碰过的 pin。

这个结论已固化在 `test/scoring.test.ts` 与 `test/l1-decay.test.ts`：pin 的系数恒为 1.0，且一条高访问记录必须能超过它。

## 数据敏感性

快照来自真实工作记忆，包含人名、路径、课题名。仓库里不放：

- `data/` 整个目录（`.gitignore`）
- 任何记录正文
- 三元组 ID（team / agent / user）

bench 脚本对真实快照只输出聚合数字，不打印内容。合成语料完全构造，可以公开。
