**遇到的问题**

1. **提示词里那版回退 SQL 会静默改错记录。** 演练主路径是单次 apply，所以照抄能过（52 条都恢复）；但重放旧回退会把后续 run 的归档一起撤销，回退一个无效 run 会复活它根本没归档的记录——两者都不报错。已改成指纹版并留下真实 run 的对照数据（步骤 2）。这是本次演练最值钱的发现，也是最典型的"静默"缺陷。
2. **提示词给 `state <> 'active'` 的理由不成立。** 它挡不住误复活（被后续 run 归档的记录本来就不是 active，有没有这个条件都会被改）；它真正保护的是"别人恢复过、但留了 `forget_reason` 的行"不被顺手清掉。条件该留，但理由得改，否则下一个人会以为误复活问题已经解决了。
3. **`applier.ts` 对没改成的行也写审计。** 这不是 bug（审计要完整记录"计划决定了什么"），但它让 `run_id` + `to_state` 不足以判断"这条记录现在是不是这个 run 留下的"。指纹正是为此而加。
4. **容器起停的耗时不稳定，必须先等 healthy 再发请求。** 同一台机器、同一镜像，把容器起健康的耗时在两次完整演练里差了整整一倍（5.10 s vs 10.08 s）。第一版脚本起完容器立刻 search 也成功过，但 A4 在同一套环境里见过 500 `disk I/O error`（堆栈落在 `PRAGMA journal_mode = WAL`）。脚本因此改成轮询 `State.Health.Status` 到 `healthy` 才继续；"刚 start 就 search 会不会失败"本次没有专门做对照，只有一个反例和若干次成功。
5. **`.ps1` 里的中文注释让 Windows PowerShell 5.1 解析失败。** 报错位置和真实原因（编码）完全对不上：`Unexpected token '}'`、`字符串缺少终止符`。文件改存 UTF-8 带 BOM 后正常。写脚本的辅助函数时踩到，已记进「已知陷阱」。
6. **`node -e` 在 pwsh 下不可用**，同上（A4 已记录，本次复核仍然复现）。所有 SQL 都走 here-string 管道给 `node --input-type=module`。
7. **镜像只对补丁树负责。** 这个镜像里 `store/sqlite.ts` 是文件式布局，生产在跑的是 `store/sqlite/` 目录式布局的更新一代代码。版本号区分不了（见文首）。所以本文的耗时与行为是补丁树的，搬回生产前需要一次同样口径的演练。

## 二、指纹口径：对后续脚本的硬规定（2026-10-27 追加）

本格的产物（`scripts/rollback-forgetting.mjs`、`scripts/snapshot-check.ps1`）都不计算、也不记录审计指纹，所以这条落成规定而不是代码：

**后续任何脚本要计算审计指纹，必须用指南第五节钉死的口径**——`score` 用 `printf('%.6f')` 或 `toFixed(6)`（**不能**让它裸拼进串：那是 SQLite 隐式的 17 位 dtoa，与 JS 的最短往返表示不同）、`ORDER BY audit_id` 必须写进 SQL（靠结果集自然顺序不算口径）、字段值里的分隔符不转义；**任何写日志或输出的地方，必须连 run id + 行数 + 排序键一起记，不许只记哈希**——`84A061EC192D5613` 就是这么变成一个查不到源的孤值的。

**现存的两个演练脚本仍是旧口径，下次真跑会产出旧值。** `.scratch/a5-drill/drill.ps1` 与 `.scratch/a5-drill/runbook-drill.ps1` 都把 `score` 裸拼进串（等于 SQLite 隐式转文本）。同一批 52 行，旧口径给 `36EBD622230E94D3`、第五节口径给 `DABDF7C8CBA226D2`，52 行里 24 行文本不同。这两个脚本在 `.scratch/` 下、不进版本库，这一格改不到它们——下次照它们跑，日志里留下的仍是旧值，与指南第五节那张表对不上，而且**对不上时没有任何东西会报错**。要消掉这个差异只有两条路：改那两个 `.ps1`，或者把它们算出的指纹当"已知旧口径"读。

## 三、复现清单

**先说清楚这句话的边界：在一台已备齐下表四项前置产物的机器上，把下面这几个文件落成文件——指南第二节的 `vacuum.mjs`、已经进了仓库的 `scripts/rollback-forgetting.mjs`（指南附录 A；演练当时叫 `rollback-run.mjs`）、指南附录 B 的 `runbook-lib.ps1`、本文附录 C 的 `20-baseline-load.mts`、本文附录 D 的 `drill-search.mjs` 与 `drill-compare.mjs`，下面的命令就能从头跑到尾。** 换机器时不能只搬这六个文件：下面这张表里的东西不在版本库，`src/` 是仓库自己的代码（命令里写的 `node src/cli.ts` 就是它），`node_modules/` 只在跑第五节的 tsx 那条路时才需要。

#### 取快照：两种取法与原样输出

这一小节是给第一行产物用的，独立于下面 0–9 的命令。**目标只有一个：拿到一份不带"静默缺数据"的库。**

**做法 ①：`VACUUM INTO`（推荐）。** 让 SQLite 自己把 `-wal` 里已提交的事务合进新文件，产出单文件、无旁文件、`journal_mode=delete`。前提写清楚：执行的那一刻源库要能被**只读打开**，且**没有别的写者持着写事务**——有写者时 `VACUUM INTO` 会等锁，等到 `busy_timeout` 就失败退出，不会给你半份数据。生产容器在跑时也能做（本节实测就是在生产 core 容器 Up 10 hours 的状态下做的），因为它只读源库。

**做法 ②：按目录整体拷。** `vectors.db`、`vectors.db-wal`、`vectors.db-shm` 三件一起复制到同一个目标目录，中间不要让别的进程写源库。**少拷 `-wal` 就是错的**：WAL 模式下已提交但尚未 checkpoint 的事务只在 `-wal` 里，主库文件仍停在旧页；只拷主库得到的是一份"能打开、`integrity_check` 还是 ok、大小也对"的旧快照。

**做法 ③（不要用）：只拷 `vectors.db`。** 2026-10-27 在 `D:/ZCodeData/tdai-data/core` 上做了两份只读拷贝，源目录当时是 `vectors.db` 26,005,504 B / `vectors.db-wal` 4,260,112 B / `vectors.db-shm` 32,768 B：

```
MAIN_ONLY（只拷 vectors.db）      : 829 条 / MAX(updated_time) 2026-10-26T13:33:08.587Z / integrity ok
WITH_WAL （三件一起拷）           : 833 条 / MAX(updated_time) 2026-10-26T17:59:15.172Z / integrity ok
两份主文件 SHA256 完全相同         : CE694CBCE3C6C121D8EFFD9FE4EB8731AD125B84AB38F2EE58647D85FAF8BEAB
少的 4 条只存在于 4.26 MB 的 -wal 里
```

**这就是这条要防的坏法**：三个自查信号——"拷过来了"、"大小对"、`integrity ok`——在只拷主库时会**同时为真**，而数据少了 4 条。所以判据不能只写 822 / 519，也不能只信 `integrity_check`。

**先划清这条自查能回答什么。** 它回答的是一个问题：**这份副本和那个源库，计数一样吗**。答「一样」才叫没丢数据；答「不一样」就是丢了（或少拷了）；两个都答不了时，它必须说「不知道」，不能默认 OK。

下面这个 `Show-Snapshot`（全文在 `scripts/snapshot-check.ps1`）用两层硬判据，外加一道归属判断：

| 层 | 判据 | 能回答 | 不能回答 |
|---|---|---|---|
| 计数（硬） | 给了 `-SourceDbPath` 时，对源库三件的一次性只读副本跑三项 `COUNT(*)`，与副本逐项比对：`l1_records` / `forgetting_audit` / `l1_records` 里 `state` 不是 `active` 的行数 | 副本少了哪一类行（含**只少状态变更、行数不变**的情形） | 具体少了哪几行、内容对不对 |
| 归属（硬） | 拷贝**前**用 `Get-SnapshotStamp` 取一次源库的 `(main size, main mtime, -wal size, -wal mtime)`，拷贝后函数再取一次；两次相同即源在拷贝期间没动 | 计数差是谁的错：源没动 → 差只能来自拷贝（`MISMATCH` / `reject`）；源动了 → 这次读数分不开（`OLDER` / `recheck`） | 拷贝之前源库动过什么 |
| 结构（最软） | `PRAGMA integrity_check` | 文件结构坏没坏 | 是不是最新的、全不全 |

判据里**没有**「副本比源旧多少秒」这一条。`copy_lag_seconds_vs_wal` 仍然打在 JSON 里，但只是给人看的参考值，不参与任何分支。

**为什么时间轴不能再当判据（REV-005 的 P1）。** 那个数是「源 `-wal` 的 mtime」减「副本的 `MAX(updated_time)`」：前者跟最后一次**写入**，后者跟最后一次**入库写**。而 `src/applier.ts:88–92` 的 UPDATE 只写 `state` / `forget_reason` / `forgotten_time`，**不动 `updated_time`**——所以 apply 之后的任何一份副本，lag 都停在「最后一次入库写」到「最后一次写」的距离上，小时级，跟拷贝有多新毫无关系。三步实测（夹具在 `.scratch/rev6/A/`，脚本从本文抽出来跑）：

1. 拿演练库（822 行，`MAX(updated_time)` 2026-10-26T11:24:13.426Z，5 行按 `applier` 的形状归档过）**现做**一份三件齐全、刚拷完的副本：`copy_lag_seconds_vs_wal 50015`。lag 与「拷贝时刻」无关。
2. 同一份库**只拷主库**（丢掉 `-wal` 里 5 条已提交状态写，源库全程零写入）：计数差 `not_active -5`，旧口径判 `OLDER … re-copy and re-run inside the window` / `action recheck` / 退出码 0——**一份真丢了内容的副本，脚本侧只看得见 0**。
3. 照旧口径说的「重拷重跑」做两次：两次 `action` 都是 `recheck`。`-wal` 的 mtime 不因重拷而变，所以那个出口物理上不可达；而 apply 之后、停容器之后恰好都是这种状态，也就是回退前最常跑这次自查的时刻。

「副本自己的年龄」这条退路也是关着的：`Copy-Item` 与 `copyFileSync` 都保留源 mtime（实测两侧同为 `2026-10-27T01:17:48.8765571Z`），副本 mtime 不是拷贝时刻，拿它当年龄只会读到源的年龄。

**为什么零行副本仍判 `UNUSABLE`。** `Date.parse(null)` 得 `NaN`，旧口径里 `NaN > 60` 为 `false`，「比源旧」的分支不成立，空表直接落进 `OK`（旧版实测 `l1_rows 0` / `max_updated_time null` / `verdict "OK (copy has caught up)"`）。现在判值不判比较：`max_updated_time` 为空或 `l1_rows` 为 0，一律 `UNUSABLE`。

**为什么只有「源动了」才允许 `recheck`。** `recheck` 的意思是「这次读数无效，重拷一次就能定」，不是「回头再说」。源在拷贝期间没动时，计数差只能来自拷贝，重拷只会拿到第二次 `MISMATCH`——把这种情形放进 `recheck`，等于给静默放行留门。所以三个出口这样分：源没动 + 计数差 → `MISMATCH` / `reject`；源动了 + 计数差 → `OLDER` / `recheck`；没测出源动没动 + 计数差 → `UNVERIFIED` / `reject`（不知道也**不是**放行）。

**源库只被 stat，不再被打开（REV-005 的 P2）。** 只读打开一个 WAL 库也会在它旁边建出 `-shm`，`-wal` 被 truncate 过时还会建出一个 0 字节 `-wal`。旧版是在源目录里直接连库跑 `COUNT(*)`，于是「跑一次自查」会改变下一次读到的数字（同一夹具两次运行 `source_wal_present` 从 `false` 翻成 `true`，目录里多出 `-shm` 与 0 字节 `-wal`），也会让之后「三件一起拷」把这个 0 字节 `-wal` 一起带走。现在源侧只做两件不产生副作用的事：`stat` 取大小与 mtime，以及按字节把主库与 `-wal` 拷到 `%TEMP%`；SQLite 连接只开在那份一次性副本上，跑完连目录一起删。实测同一夹具连跑三次，`source_wal_present` 三次都是 `false`，源目录三次都只有 `vectors.db` 一个文件（跑之前也只有它）。

**stamp 怎么读，两条容易踩的规则。**

1. **比的是 `(size, mtimeMs)`，不是秒级的 mtime，另给 5 秒容差。** `Copy-Item` 与 `copyFileSync` 都保留到亚毫秒，所以同一台机器上「源没动」这个判断是精确的；但 exFAT 分区和某些 SMB 共享只存到秒甚至两秒，落在那里的副本可能读起来比源略旧，5 秒容差就是为了不把这种时间戳精度问题误判成「源动过」——那会重新造出一个永远 `recheck` 的循环，正是这一轮要消掉的东西。
2. **副本比 stamp 还旧，就按「源动过」处理。** 一份几小时前做的副本，配上刚刚取的 stamp，两次读数当然不同；但真正的原因是这份副本根本不是这次拷贝的——它拍的是更早的源库状态，计数差可能是这段时间源库长出来的。这条规则让「拿历史快照去比活源」稳定落在 `OLDER` / `recheck`，而不是被 `MISMATCH` / `reject` 冤枉。反过来，判断「这份副本是不是拷完就测的」也只看这一点，不看 `copy_lag`。

**`-SourceWalPath` 打错字不再被读成「源库没有 `-wal`」。** 旧版用 `existsSync` 判，打错一个字符就落到「源库没在写」那个分支：`UNVERIFIED … the source has no -wal` / `action use` / exit 0，把人的手误说成源库的状态。现在给了路径却不存在，直接 `BAD ARGUMENT` 抛错；「源确实没有 `-wal`」要靠**不传** `-SourceWalPath`（按 `<SourceDbPath>-wal` 自动探测）来表达。

下面是可直接粘贴的 PowerShell 段。**源侧只 stat 与拷贝字节，不打开库**；被只读打开的两个库是副本本身与 `%TEMP%` 下的那份源库副本，跑完都不在源目录留任何文件：

**A 现在是 `reject`，不是 `recheck`。** 拷的时候源库没动（前后两次 stamp 相同），那 4 条差值不可能是「源库又长了」，只能是没拷 `-wal`。上一版这一条是 `recheck` + 退出码 0：判据挂在一个与拷贝新旧无关的数字上，最该拦住的那类副本反而从最宽松的出口出去了。

**三项计数在真实生产源上只比得出一项，这不是函数坏了。** `D:/ZCodeData/tdai-data/core` 那份库还没跑过补丁迁移：没有 `forgetting_audit` 表、`l1_records` 也没有 `state` 列。函数对「两侧都没有」的项记 `not compared (absent on both sides)` 而不是 0，所以 `count_deltas` 里只有 `l1_records` 是真比过的。等补丁上线、库里有了这两样，另外两项自动加入比对；`l1_records` 这一项无论如何都在。**这也是为什么三项要分开列**：合成一个「总数相等」会把这个差别藏起来。

读法四条：

1. `action` 是 `reject` 就别往下走。`UNUSABLE`（空表/结构坏）、`MISMATCH`（计数差且源没动，或副本多出行）、`UNVERIFIED … stillness was never established`（计数差且没测出源动没动）三种都归它。`recheck` 只表示「拷贝之后源又写了，这次读数无效，重拷一次就能定」。`use` 才可继续。
2. 副本与源的 `l1_rows` 差 4（829 vs 833）、`vec_rows` 差 4（526 vs 530），而 `integrity_check` 两份都是 `ok`——**integrity ok 只说明文件自身结构没坏，不说明它是最新的、更不说明它是全的**。
3. `VACUUM INTO` 那份与前两份的差别不止行数：`journal_mode` 从 `wal` 变成 `delete`、文件小 93,208 B、没有 `-wal` 残留。这是「合并过 WAL」的正面证据；做法 ② 的副本 `journal_mode` 仍是 `wal`，下次一打开就会回放 `-wal`，**所以三件必须落在同一个目录、`-wal` 不能被单独丢掉**。
4. `wal_files_present` 按 `-wal` 的**字节数**算（`copy_wal_bytes` 大于 0），不按文件存不存在：WAL 模式的库被只读打开一次就会在旁边留下 0 字节的 `-wal`，按存在性判断会在第二次运行时翻成 `true`。源侧的 `source_wal_present` 同理，只是它连打开都不做了。

**边界再强调一次**：拿本仓库那份固定快照 `data/snapshot-20261026.db`（`VACUUM INTO` 产物、25,657,344 B、822 行、519 条向量、`journal_mode delete`）跑同一条自查，只给 `-DbPath` 时结论是 `UNVERIFIED (no -SourceDbPath and no -SourceWalPath given)` / `action unknown`；拿它去比当前生产源（拷贝前取 stamp），结论是 `OLDER`（实测 lag 23,702 秒、`count_deltas{l1_records -11}`、`source_moved true`）/ `action recheck`。**这两种都不是「副本坏了」**——它本来就是 10-26 那份历史快照，对活源必然旧、计数也必然不等。

#### `action` 是唯一入口，退出码不是 API

先看清退出码是哪一层的，别混着记。实测矩阵（Windows PowerShell 5.1，Node v24.18.0）：

| 层 | 值 | 触发条件 |
|---|---|---|
| `node` 层（`$LASTEXITCODE` 紧跟调用） | 2 | `action` 是 `reject`：`UNUSABLE`、`MISMATCH`、或计数差但没测出源动没动 |
| | 0 | 其余情形（`use` / `recheck` / `unknown`） |
| 外层 PowerShell | 1 | 未捕获的 throw：`reject`（函数抛 `DO NOT USE THIS COPY -- …`）或 `BAD ARGUMENT`（路径打错） |
| | 0 | throw 被 `try/catch` 接住且脚本正常结束——**这是第三个 `0`** |
| | 0 | `-ActionOnly` 正常返回（它从不抛） |
| | 2 | 你自己写了 `exit 2` |

实测的几条：`action use` 两种层都是 0；`action reject` 未捕获时 node 2 / outer 1，捕获后 outer 0；`-SourceWalPath` 打错一个字，`BAD ARGUMENT` 未捕获 outer 1、捕获后 outer 0；显式 `exit 2` 是 2。

**所以「0」同时覆盖三种处境：真的比对通过、`recheck`（这次判不了）、以及 throw 被 catch 住。** 只看得见退出码的调度器（cron、CI）分不开这三者，而其中两种不是「可以继续」。不必把退出码统一成一个数——1 表示脚本崩了、2 表示数据不一致，这个区分对人有用——但要给脚本一个可靠入口：

```powershell
# 脚本只认 action，不认 exit。这一行只输出一个词：use / recheck / reject / unknown。
$action = Show-Snapshot -DbPath 'D:\tmp\three\vectors.db' -SourceDbPath 'D:/ZCodeData/tdai-data/core/vectors.db' -SourceStampBefore $stamp -ActionOnly
if ($action -ne 'use') { throw "snapshot not usable: $action" }
```

`-ActionOnly` 不抛异常、只输出那个词，所以「判不了」和「脚本崩了」在调度器眼里是两回事。**别用 `$LASTEXITCODE -eq 0` 当放行条件**：它会把 `recheck` 和「throw 被 catch」一起当成通过。

2. `limit5_scores_identical true`——五条分数也逐条相同（差异阈值 1e-9）。
