# 可召回性验证 — 2026-11-06

补上 E2 评审留下的那条缺口："回退后能被检索到"。结论是**验不了，而且原因比缺口本身严重**。

## 一、做了什么

复制生产数据卷到 `.scratch/drill2/core`，起隔离容器 `tdai-drill2`（宿主 18421 → 容器 8420），生产容器全程未停、未挂载。

四步：

1. **基线**：在未改动的副本上搜索，确认检索通道正常（`CUMCM A题 湿物料干燥` 返回 3 条）；
2. **只 migrate 不改数据**：`migrate` 加 schema，重启容器，检索仍返回 1 条 —— 加列本身不影响检索；
3. **归档一条有向量的记录**：`m_1789135078654_cb920d49` 从 `active` 改为 `archived`，`l1_recallable` 视图正确排除它（查询返回 0）；
4. **重启容器再搜**：**它仍然出现在结果里，分数一模一样（0.0323）。**

第 4 步是决定性的。

## 二、根因：生产容器跑的是没有打过补丁的镜像

```bash
docker exec tdai-memory-core sh -c "grep -rl invalid_at /app/src"     # 空
docker exec tdai-memory-core sh -c "grep -rl forget_reason /app/src"  # 空
docker exec tdai-memory-core sh -c "grep -rl l1_recallable /app/src"  # 空
```

镜像 `agentmemory/memory-core:latest` 构建于 `2026-10-26T09:56:43Z`，版本 `1.0.2-beta.1`，代码里没有任何忘记机制的痕迹：

- 没有 `invalid_at` / `superseded_by` / `forget_reason` / `state` 的读取；
- 没有 `l1_recallable` 视图的引用；
- 检索直接走 `l1_records` + `l1_vec`，**完全不看 `state`**。

所以「归档」在这个容器里只是一个数据列的值，没有任何代码读它。这解释了为什么第 4 步的分数一模一样。

## 三、这推翻了什么

**E2 的 acceptance 第 2 条在当前环境里不可验证，而且不是"演练没做"，是"前提不存在"。**

原话是「回退的 2 条恢复可召回，未回退的仍不可召回」。这句隐含了一个前提：`state` 会影响召回。但在生产镜像上：

- 归档的记录**仍然可召回**（实测，分数不变）；
- 所以"未回退的仍不可召回"这句话没有对应现象；
- "恢复可召回"也无从证明，因为恢复与否检索结果都一样。

**更要紧的是它暴露了一个此前没有被记录的事实：0101–0105 这五份补丁从来没有部署到生产容器。**

计划文档、README、各收口报告都在讨论"上线前要做什么"，但生产跑的一直是未打补丁的上游镜像。之前 A4 的冒烟、A5 的回退演练、本轮 E2 的容器演练，用的都是**打过补丁的树或副本**，没有一次是在真正服务的那个容器上。

数据库层的账是对的，这轮又验证了一次：

## 五、要做什么才能补上

按顺序，前两步之前做不了第三步：

1. **把补丁打上生产树并重建镜像。** 0101 → 0102 → 0103 → 0104 → 0105 依序 `git apply`，`npm run build`，`docker build`。这一步本身就是"上线"。
2. **确认新镜像的检索路径真的过滤了 `state`。** 最直接的验证：`grep -rl l1_recallable /app/src` 应当非空；再跑一次本轮的归档实验，归档的记录应当从结果里消失。
3. **然后才是 E2 的原验证**：回退 → 检索 → 确认恢复。这时的"可召回"才有意义。

在 1、2 完成之前，E2 的那半句只能记为**阻塞**，不是"待办"。

## 七、一个操作上的二次确认

演练中途有一次「回退后仍搜不到」的假信号：那是查错了记录——`m_1788454323598_1f4267bf` 在 `l1_vec_rowids` 里**没有向量**（854 条 active 里只有 556 条有向量），向量检索天然看不到它。

**所以选验证对象必须先确认它在向量索引里。** 这一点写进流程：`SELECT COUNT(*) FROM l1_vec_rowids WHERE id = ?` 非 0 才有资格当"可召回性"的样本。
