# 访问追踪延迟实测：一次 `appendRecall` 在检索路径上的代价

- 日期：2026-10-26（实验执行 2026-10-28）
- 归属：画布 B / block `b4-latency#impl`
- 数据源：`data/snapshot-20261026.db`（只读）
- 工件：`bench/latency.ts`、`.scratch/b4-latency-round1.json`、`.scratch/b4-latency-round2.json`

## 结论

**p99 差值没有超过 5ms 阈值。维持同步写（`appendFileSync`），不需要改成批量异步写。**

两轮独立实验的 p99 差值分别是 **+0.076ms** 和 **−0.041ms**：符号相反，量级都在噪声里，
距离 5ms 阈值有 30–65 倍余量。判定依据是计划里定好的阈值本身，不是「看起来很快」。

但「没超阈值」不等于「没有代价」。配对分析显示接线后**在 84.5% / 81.0% 的配对样本上确实更慢**，
系统性的平均代价是 **+0.139ms**（两轮几乎完全一致：+0.1394 / +0.1392ms）。
这个数字真实且可复现，只是它远在阈值之下——见下文「代价是真的，只是小」一节。

## 先厘清：测的是什么

任务书点名最容易做错的一条：要测的是**加了日志之后的检索耗时**，不是 `appendRecall` 本身耗时。
本实验严格按这个口径执行——计时窗口包住整条检索链：

```
候选生成（lexical + FTS5 bm25 + 向量余弦） → RRF 融合 → rerankHits → 取 top-10
                                                                                    ↓
                                                         [on] appendRecall(...)  ← 计时窗口内
```

一个便宜的 append 仍然可能拖慢整条检索：同步写会把文件弄脏，下一次写要扩容它；
Windows 上实时扫描器（Defender）会在两次写之间走一遍目录。只给 append 单独计时会绕开这个风险。

## 缓存状态：热（WARM）

任务书要求缓存状态必须声明并保证。本次取**热缓存**，且两模式共享同一套热状态：

| 缓存对象 | 状态 | 怎么保证两模式一致 |
|---|---|---|
| 语料 + 倒排索引 | 内存常驻、构建一次、实验期间只读 | 计时开始前构建完毕；两模式读同一个对象，无写入 |
| sqlite 页缓存 | 热 | 只读连接**只开一次**，`RetrievalIndex` 持有它；两模式复用同一连接，不重开 |
| 向量矩阵（`l1_vec`） | 热 | `loadVectorIndex()` 在计时前一次性载入 `Float32Array` |
| embedding（Ollama bge-m3） | 热 | 12 条 query 用到的 **7 个前缀**在计时前全部预取，两个模式都只读 `Map`，命中率 100%（missing 0） |

这一点是刻意设计的：如果 embedding 懒惰求值，**先跑的那个模式会吸收全部缺失**，
差值测的就是缓存冷热而不是遥测代价——这是这块最容易做错的地方之一。

代价：冷启动的第一次检索要付一次 embedding 调用，本实验不测它。所以下表是稳态下限，不是冷启动数字。

## 数据与检索链（真实组装，非空转）

本仓库没有真实检索器（那在上游），所以「一次检索」按任务书要求自行组装，但每一环都读真实数据：

| 环节 | 实现 | 真实数据源 |
|---|---|---|
| 语料 | `loadRecords(dbPath)` | `l1_records`，**822 条** |
| 通道 1：词法 | 倒排索引 token 重叠计数 | 由 `content` + `scene_name` + `type` 构建（CJK 二元组 + ASCII 词） |
| 通道 2：FTS | `l1_fts MATCH ? ORDER BY bm25(...)` | SQLite FTS5 真实虚拟表 |
| 通道 3：向量 | 余弦相似度 | `l1_vec` vec0 影子表，**519 行 × 1024 维 float32** |
| 融合 | RRF（`k=60`） | 与上游 `l1-candidate-recall` 同形 |
| 打分/排序 | `rerankHits` / `searchMultiplier` / `trackingCoverage` | `src/scoring.ts` 原样调用 |
| 落 hit | `RecallHit[] = [{record_id, rank}]`，rank 1..10 | 与 `executeMemorySearch` 交给 `appendRecall` 同形状 |

注意 `searchMultiplier` 通过 `rerankHits` 内部调用，未单独直调；这符合任务书「排序用 rerankHits / searchMultiplier /
trackingCoverage」的口径——`rerankHits` 本身就是 `searchMultiplier` 的唯一调用者。

语料规模：`trackingCoverage = 0.0000`（0/822 有访问信号），低于 `minTrackingCoverage = 0.1`，
因此 `decayEnabled = false`，两模式都跑 `decay: false` 分支。这是**同一个值**，不影响可比性，
但意味着本实验测的检索链不含衰减项——记在残余风险里。

### query 集（12 条，覆盖三种形态）

| 形态 | 条数 | 例子 |
|---|---|---|
| 单 token | 3 | `RRS` / `JFPE` / `LongCat` |
| 多 token | 5 | `JFPE 论文 盲审 意见 整改` / `tdai 复刻 部署 记忆库 备份 容器` |
| 长句 | 4 | `我在和JFPE论文研究者用户把全自动取点成果存为永久记忆…` |

全部内容无关（query 只出现主题词，不打印任何 record 正文）。200 次迭代按 `i % 12` 轮转，
12 不能整除 200，所以每个 query 的请求次数略有差异（16 或 17 次）——两模式轮转顺序**完全相同**，
这一点由下的命中指纹比对钉死。

## 可比性证据：除一次 `appendRecall` 外路径逐字相同

两个模式共用 `runPipeline()` **同一个函数**，差异只有函数末尾那一个 `if`：

```ts
// bench/latency.ts:243-270
function runPipeline(index, spec, queryVec, mode, logPath, decayOn, now): SearchResult {
  // ---- shared region: identical source for both modes ----   (L252)
  const fused = fuse([index.lexicalChannel(spec.text), index.ftsChannel(spec.text), index.vectorChannel(queryVec)]);
  const scored = fused.map(...).filter(...);
  const ranked = rerankHits(scored, DEFAULT_DECAY, now, { limit: RETURN_N, decay: decayOn });
  const trimmed = ranked.slice(0, RESULT_LIMIT);
  const hits: RecallHit[] = trimmed.map((r, i) => ({ record_id: r.record.record_id, rank: i + 1 }));
  const total = trimmed.length;
  // ---- end shared region ----                                (L264)

  if (mode === "on" && logPath) {        // (L266) ← 唯一的差异
    appendRecall(logPath, hits, now);     // (L267)
  }
  return { hits, total };
}
```

**结构性保证**（不是口头声明）：

1. 函数体内**没有**更早的 `if (telemetry)` / `if (mode)` 分支——`mode` 在 L266 之前只作为参数存在，未被读取。
2. 不存在第二份实现：没有 `runPipelineOff()` / `runPipelineOn()`，没有复制粘贴的两条链。
3. 上游输入在计时前冻结：语料、索引、向量矩阵、embedding `Map` 都是常量，两模式读同一对象。

**运行时验证**（强于静态断言）：每次迭代记录返回的 `record_id` 序列，两模式逐条比对。
若两模式走了不同代码路径，排序结果迟早分叉。结果：

```
round1  comparability  identical hit sequences in both modes = true  (200 off / 200 on)
round2  comparability  identical hit sequences in both modes = true  (200 off / 200 on)
```

两轮共 400 对指纹全部一致。这是「测的是同一条路径的日志代价」的硬证据。

## 判定：p99 差值未超过 5ms

计划定的阈值是 **p99 增加超过 5ms 就改成批量异步写**。实测：

| 轮次 | p99 差值 | 阈值 | 余量 | 判定 |
|---|---|---|---|---|
| 第 1 轮 | +0.0760 ms | 5 ms | 65.8× | 未超 |
| 第 2 轮 | −0.0410 ms | 5 ms | —（负值） | 未超 |
| 第 3 轮（**Lead 独立复跑**，另一个进程、同一台机） | +0.0471 ms | 5 ms | 106× | 未超 |

**结论：维持同步写 `appendFileSync`，不引入批量异步写。**

因为未超阈值，任务书不要求给出改造方案。但把「如果将来超了该改哪儿」写在这里，免得下一轮重新推导：

- 要动的接口是 `src/recall.ts` 的 **`appendRecall(logPath, hits, now, opts)`**。
- 它当前的契约是「同步写一行、永不抛异常、返回 boolean、进程退出前数据已落盘」。
- 异步化会打破第三条：需要缓冲 + 定时 flush + 进程退出 flush（`process.on("exit")` + `beforeExit`），
  并且崩溃时会丢最后一批——那正是 `recall.ts` 头部注释里「survives a crash mid-search」这句所承诺的反面。
- 所以真到那一步，正确做法不是偷偷改这一行，而是走画布重规划：这是**可观测的可靠性降级**，不是性能微调。

## 两轮稳定性：结论稳定，但 p99 这个统计量本身不稳

任务书强调「至少 2 轮独立实验再下判定」。两轮独立进程（各 200 次 × 2 模式）结果对比：

| 观察 | 第 1 轮 | 第 2 轮 | 读数 |
|---|---|---|---|
| p99 差值 | +0.0760 | −0.0410 | 符号翻转 → 边际分布 p99 由偶发离群主导，测不出遥测效应 |
| mean 差值 | +0.1394 | +0.1392 | 差 0.0002ms，高度可复现 |
| p50 差值 | +0.1513 | +0.1374 | 同号，量级一致 |
| p90 差值 | +0.1220 | +0.1446 | 同号，量级一致 |
| 可比性 | true | true | 400 对指纹全一致 |
| 日志字节 | 65730 | 65730 | 逐字节相同 |

**两种判定都不受 p99 抖动影响**：即便取较不利的那一轮（+0.0760ms），也距 5ms 阈值 65 倍。
所以「未超阈值」这个结论对轮次选择不敏感——这是它稳的原因。

### 代价是真的，只是小（配对分析）

边际分布的 p99 会掩盖真实效应，因为 p99 位置主要由机器层面的偶发离群（GC、调度、Defender 巡检）决定。
把两模式**同一迭代序号**配对（同一序号 = 同一条 query，轮转顺序一致）：

```
round1 paired deltas (on-off, same query): n=200 min=-1.1522 p50=0.1297 p90=0.3986 p99=0.7665 max=0.9775 mean=0.1394 sd=0.2425
   on slower in 169/200 pairs (84.5%)
round2 paired deltas (on-off, same query): n=200 min=-0.5924 p50=0.1341 p90=0.3931 p99=0.6199 max=0.7314 mean=0.1392 sd=0.2075
   on slower in 162/200 pairs (81.0%)
```

读法：

- 配对后 on 在 **84.5% / 81.0%** 的样本上更慢——不是抛硬币，是系统性代价。
- 配对均值 **+0.1394 / +0.1392ms**，两轮几乎重合，说明这个效应真实且可复现。
- 配对 p99 是 **+0.7665 / +0.6199ms**，同样远低于 5ms。

也就是说任务书点名的担忧（「文件系统抖动、Defender 扫目录会放大差值」）在本机**有限度地成立**：
它确实把单次代价推到了 ~0.14ms（是检索基线 ~1.02ms 的约 13.6%），但离 5ms 阈值还差一个数量级以上。

## 残余风险

1. **日志与库不同卷**：日志写 `%TEMP%`（C:），生产落在 data dir（与库同卷 E:）。
   跨卷写不触发同卷的目录竞争，本实验的数字**偏乐观**。同卷复测会略高——但按 65 倍余量，
   不足以翻转判定。未测。
2. **衰减分支未覆盖**：语料 `trackingCoverage = 0.0000`，两模式都跑 `decay: false`。
   含衰减项的路径未计时。考虑到遥测 delta 与衰减计算互不耦合（append 在排序之后），
   预期影响可忽略，但**未实测**。
3. **冷缓存未测**：本实验是稳态热缓存数字。冷启动第一次检索要付一次 embedding 调用（数十毫秒级），
   远大于遥测代价，但因为不测所以不知道确切叠加值。
4. **非生产检索器**：本仓库没有上游真实检索器，检索链是按任务书要求自行组装的真实链条
   （822 条真实记录 / 519 条真实向量 / 真实 FTS5）。绝对耗时可迁移性弱，
   **但差值不可迁移性更弱**——append 的代价是文件系统层面的，与检索器实现基本无关。
5. **本机特有**：Windows + Defender + NVMe。Linux 生产容器上 `appendFileSync` 的代价通常更低，
   所以本机数字应视为**上界**。
6. **p99 统计量本身不稳**（两轮符号翻转）。判定不依赖它，但若将来有人只跑一轮看 p99 就下结论，
   会得到误导性读数——这正是任务书要求两轮的原因。
7. **query 集 12 条轮转 200 次**，每条被请求 16–17 次。样本量对均值充分，对单 query 的 p99 不充分；
   本报告的 p99 是**跨 query 合并**的 p99，不是单 query 的。
