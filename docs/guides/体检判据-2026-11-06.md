# 体检判据 — 2026-11-06

`scripts/healthcheck.ts`。只读，输出一屏，退出码给调度器看。

```bash
node scripts/healthcheck.ts --db data/work.db
```

## 一、四项指标

### coverage

**算法**：`trackingCoverage(loadRecords(db))` —— 有访问证据（`access_count > 0` 或 `last_access_time` 非空）的记录占比。

**判据**：低于 10% 且已有 ≥3 次 run 记录 → `WARN`；不足 3 次 → `SKIP`。

**为什么要求 ≥3 次**：新部署的冷启动本来就没有访问数据，第一次就警告等于让这个指标在第一天被静音。要求三次是"有个趋势再说话"，不是统计学。

**越界含义**：接线断了。`accessLog.enabled` 被关掉、折叠命令没跑、或者补丁没叠上去——三种都表现为 coverage 归零而不报错。

**建议动作**：先看 `fold` 有没有在跑（`node src/cli.ts coverage --db <path>` 会显示 tracked 数），再看 `memory.recall.accessLog.enabled` 的配置值。不要先改阈值——90% 的覆盖率掉到 0 不是"阈值太严"。

### evictionRate

**算法**：最近一次 run 的 `(archived + retired) / total`。

**判据**：> 10% → `WARN`；> 30% → `FAIL`。

**越界含义**：阈值配错了，或者冗余聚类塌了。D3 的扫描里，`clusterThreshold` 从 0.7 降到 0.4 会让淘汰率从 35.8% 跳到 93.6% —— 这就是 30% 那条线想拦的东西。

**建议动作**：`node src/cli.ts audit` 看 `by reason`。如果集中在 `quota`，是配额导致的，正常；如果集中在 `score ... < archive`，是 `archiveThreshold` 被调高了；如果集中在 `redundant with`，是 `clusterThreshold` 被调低了。

### pinIntact

**算法**：`applyPins` 判出的 hard pin 里，`state != 'active'` 的条数。

**判据**：> 0 → `FAIL`。没有阈值，这是硬约束。

**越界含义**：有人绕过了引擎写库，或者 pin 规则在归档之后才生效。planner 的 Pass 0 保护硬 pin，所以正常路径下这个数永远是 0。

**建议动作**：先停掉定时 apply，再查这几条记录是谁改的（`forgetting_audit` 里没有它们的归档行，说明不是本引擎干的）。**不要直接改回 active** —— 先搞清楚是谁写的，否则下次还会发生。

### auditGaps

**算法**：最近一次 run 在 `forgetting_audit` 里的行数，对比 `forgetting_runs` 里 `archived + retired`。

**判据**：两者不等 → `FAIL`。

**越界含义**：审计表不再完整。可能是 apply 写到一半崩了，或者有人删了审计行。审计是这个项目唯一的纠错手段，缺口意味着"哪些记录该回退"这个问题答不上来。

**建议动作**：先看该 run 的 `status` 字段。如果是 `failed`，这是中断的正常痕迹，重跑一次 apply 即可；如果是 `completed` 却缺行，按 [生产回退 runbook](./生产回退-2026-11-06.md) 处理，不要删表重建。

## 二、为什么不做自动修复

体检脚本会自动"修复"的话，它就是一个在无人看管时能改生产数据的程序。上面四项里没有一项的修复是安全的：

- coverage 归零的修复是"打开追踪开关"，但在没确认补丁是否生效之前打开它，可能把错误的数据写进日志；
- 淘汰率过高的修复是"把阈值调回默认"，但默认值未必适合这份语料（D4 的结论就是每个语料要重扫）；
- pinIntact 的修复是"把记录改回 active"，那会掩盖掉"谁绕过了引擎"这个更重要的问题。

人能做的三件事（看审计、认语料、拍板回退）脚本一件都做不了。它只负责**在无人看的时候发现异常，然后把人叫来**。

## 三、调度

第一版不自动安装调度。要装的话：

**Linux / macOS（cron，每天 09:00）**

```bash
crontab -e
# 追加一行
0 9 * * * cd /path/to/tdai-forgetting && node scripts/healthcheck.ts --db /path/to/work.db >> /var/log/tdai-health.log 2>&1
```

**Windows（计划任务）**

```powershell
schtasks /Create /SC DAILY /ST 09:00 /TN "tdai-health" /TR "node E:\tdai-forgetting\scripts\healthcheck.ts --db E:\tdai-forgetting\data\work.db"
```

**卸载**

```bash
crontab -e        # 删掉那一行
schtasks /Delete /TN "tdai-health" /F    # Windows
```

**只看退出码的 CI 用法**：`node scripts/healthcheck.ts --db <path> || exit 1`。退出码 1 表示至少一项 FAIL；WARN 不影响退出码，因为"覆盖率低"之类的信号需要人判断，不该让流水线替人做决定。

## 四、边界

- **不会发现"记忆变差"**。这四项都是结构性指标。语义质量下降（召回不再命中）只有人能用真实检索发现，见 [生产回退 runbook](./生产回退-2026-11-06.md)。
- **coverage 的 10% 与淘汰率的 10% / 30% 都是从 D 的扫描里取的**，换语料后这些线也该重扫。它们不是通用常数，是这份语料上的判据。
- **`auditGaps` 只查最近一次 run**。历史缺口不会报——历史 run 的 status 已经是 `failed` 的话，重跑比事后补齐更可靠。
