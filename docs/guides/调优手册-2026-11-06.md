# 调优手册 — 2026-11-06

先看症状，再决定改哪个数。参数说明放最后，因为"这个参数是什么"从来不是问题，"我现在该动哪个"才是。

**每一个建议都带副作用。** 只说"调大就好"的手册会把人推到另一个极端。

参数区间的数字全部来自 [参数敏感度](../experiments/参数敏感度-2026-11-06.md)，标注了节号。那份数据跑在 D4 改默认值、D5 改长文本算法**之前**，所以看区间可以，别拿它当当前代码的绝对读数。

---

## 症状一：召回结果里重复太多

同一条笔记被不同轮迁移写了五遍，五条一起占坑。

**确认**

```bash
node src/cli.ts plan --db <copy>.db | grep -A6 "redundancy"
```

看 `clusters` 的组数与最大成员数。如果最大组 > 3，说明聚类在正常工作但没合并掉；如果组数是 0 而有重复，说明阈值太高。

**改什么**：`DEFAULT_CLUSTER_OPTIONS.threshold`，默认 0.7。

- 往小调（0.6）：合并更多，`evictedShare` 从 26% 涨到 36%（D3 §四）。
- 往大调（0.8）：合并更少，`evictedShare` 降到 19%（D3 §四）。

**副作用**：0.5 以下会把不同事实并成一组，`evictedShare` 跳到 78%；**0.4 时是 93.6%**——基本等于把语料清空（D3 §四，这是六个参数里唯一会真删掉大部分数据的）。0.6 距离悬崖只有 0.2。

**回退**：改回 0.7。已经归档的记录用 `node scripts/rollback-forgetting.mjs <run_id> <db> --records <ids>` 恢复（见 [生产回退](./生产回退-2026-11-06.md)）。

## 症状二：该记住的搜不到了

用户说"上周还搜得到的东西现在没了"，且那条确实重要。

**确认**

先分清是被淘汰了还是被降权了：

```bash
node src/cli.ts plan --db <copy>.db | grep <record_id>
```

- `decision: archive` / `retire` → 被淘汰，按 [生产回退](./生产回退-2026-11-06.md) 处理；
- `decision: keep` 但检索排在后面 → 被降权，看下一条。

降权的确认：

```bash
node src/cli.ts coverage --db <copy>.db
```

看 `if decay on, reordered top-10`。这个数大说明衰减在改变排序。

**改什么**：`DEFAULT_DECAY.halfLifeDays`（默认 10）或 `floor`（默认 0.2）。

- `halfLifeDays` 在 **5–14 天之间 pinRecall 不变**（synthetic 0.833），越过 30 天后一路下滑，90 天时 0.458（D3 §一）。默认 10 已经在这个平台的中间，**再往下调不会更好**。
- `floor` 在 **0.1–0.3 之间指标基本不动**（D3 §二）。调低到 0.1 会让老记录更容易沉底。

**副作用**：把 `halfLifeDays` 抬到 60–90 会让 precision 上升（0.412 → 0.470）但 pinRecall 腰斩——那是拿"用户明确说要留的"去换精度，不是变好。`floor` 抬到 0.5 有同样的交换（D3 §二）。

**回退**：改回默认值。注意 `avgScore` 会跟着变（floor 就是这个分数的下界），拿它和历史比会误判。

## 症状三：库涨得太快，磁盘要满

**确认**

```bash
node src/cli.ts coverage --db <copy>.db
node scripts/healthcheck.ts --db <copy>.db
```

看 `active` / `archived` / `retired` 三个计数。如果 `archived` 远大于 `active`，问题在归档没有到退休。

**改什么**：`DEFAULT_EVICTION.quota`（默认 0 = 不启用），或 `archiveThreshold`（0.45）。

- 开配额是最直接的手段：`quota` 设成目标保留数，`minRetain` 是硬下限。
- **不要指望 `archiveThreshold` 能解决这个问题。** 三份语料的分数下界是 0.471 / 0.485 / 0.550，全部高于默认 0.45，所以这个参数**当前根本不生效**（D3 §零、§五）。要让它生效得调到 0.48 以上，那时每 0.05 多归档 5–7 个点。

**副作用**：配额会挤掉"低分但独一无二"的记录。planner 已经保证冗余先于配额，但配额本身不分好坏——它只看分数。开配额前先确认 `clusters` 已经处理过重复。

**回退**：`quota` 设回 0，已经归档的按 run 回退。

## 症状四：老结论压在新结论上面

两条记忆说的是同一件事，但一条是去年的结论、一条是上周推翻它的。检索把老的排在前面。

**这条不改参数。** 调 `halfLifeDays` 或 `floor` 只是让老记录"因为老"而沉下去——但一份被推翻的结论不是"不够新"，是**不再成立**。它应该被标记为失效，而不是被时间压下去。

**确认**

```bash
node src/cli.ts plan --db <copy>.db | grep -A4 "invalidated"
```

`Pass 0.5` 会列出被 `invalid_at` 标记的记录。如果这条老结论不在里面，就是**没被标记**，不是参数不够。

**改什么**：用失效标记命令，不是参数。

```bash
node src/cli.ts supersede --db <db> --old <老记录 id> --by <新记录 id>
```

`applySupersede` 只动 `invalid_at` 与 `superseded_by` 两列，不碰 `state`——所以它是可撤销的，而归档/退休不是。

批量场景（LLM 判据）有独立的影子/apply 隔离与误标率门禁，见 [LLM 判据实测](../experiments/LLM判据实测-2026-11-04.md)。

**副作用**：失效标记会让记录从 `l1_recallable` 视图消失，等于"不可召回"。**判错了就是真的搜不到了**，而且不会有报错。C 收口实测过：两位标注者对"是否构成取代"的一致率只有 72%、κ = 0.268，**这个判断本身噪声就很大**。所以先影子跑、看误标率，再 apply。

**回退**：`UPDATE l1_records SET invalid_at = NULL, superseded_by = NULL WHERE record_id = ?`。没有专门的撤销命令，因为这条路径本来就应该谨慎。

## 症状五：覆盖率一直是 0，衰减像是没生效

`[decay]` 日志写着 `decay=off (cold start)`，或者体检的 `coverage` 一直报低。

**确认**

```bash
node src/cli.ts coverage --db <copy>.db
node scripts/healthcheck.ts --db <copy>.db
```

**改什么**：**先别改 `minTrackingCoverage`。** 这个参数是开关不是旋钮（D3 §三）：在语料 coverage 之上怎么调都不动，越过就一次翻转。coverage 是 0，说明没有人记录访问，不是门槛太高。

要查的是接线：`memory.recall.accessLog.enabled` 是否为 true、`fold` 有没有在跑、补丁 0101–0104 是不是都叠上了。这三种断法都表现为覆盖率归零而不报错。

**副作用**：把 `minTrackingCoverage` 调到 0（强制开门）在冷启动语料上实测 **precision 掉 7.9 个点**（0.2380 → 0.1588，D3 §三）。那是拿噪声换"看起来在工作"。

**回退**：改回 0.1。

## 不要动什么

三样东西调错之后不可逆程度最高：

### 1. pin 规则

`src/pin.ts` 的 `PERMANENCE_PATTERN` 与 `PinOptions`。硬 pin 是"用户明确说不要忘"的唯一表达，放宽它等于允许引擎删掉用户点名要留的东西。

要改的话，先跑 `unprotectedPermanence()` 看会漏掉哪些记录。这个函数存在的意义就是"改规则前先看漏了什么"。

### 2. 审计表

`forgetting_audit` 只增不删。**任何 `DELETE` 或 `UPDATE` 都是禁止的**，包括"清理过期的审计行"这种听起来合理的操作。

理由：审计是回退的唯一依据。指纹机制（`state` + `forget_reason` + `forgotten_time` 三元组）依赖审计行保持原样，改一行就会让对应的记录变成"永远无法安全回退"。回退脚本自己也是新写 `rollback` 行，不改旧行。

### 3. 物理删除

没有 `DELETE FROM l1_records`，没有 `DROP`，没有 `VACUUM INTO` 之外的任何瘦身操作。

"遗忘"在本项目里的定义是**离开可召回集**（`state` 变化 + 视图过滤），不是删字节。审计行里记着 `from_state` / `to_state`，物理删除之后这些记录指向不存在的行，回退就没有终点。

要瘦身只能走 `retired` → 人工确认 → 归档文件，不能是数据库内的 `DELETE`。

## 参数速查

| 参数 | 默认 | 落点 | 实测区间（D3） | 一句话 |
|---|---|---|---|---|
| `halfLifeDays` | 10 | `DEFAULT_DECAY` | 5–14 平台；30 后 pinRecall 下滑 | 调大换精度丢 pin，别超过 14 |
| `floor` | 0.2 | `DEFAULT_DECAY` | 0.1–0.3 平台；0.4 起交换开始 | 调整体的分数下界 |
| `minTrackingCoverage` | 0.1 | `DEFAULT_DECAY` | 开关，不是区间 | 别拿它治"coverage 低" |
| `clusterThreshold` | 0.7 | `DEFAULT_CLUSTER_OPTIONS` | 0.6–0.8 安全；0.4 是悬崖 | 最脆的参数，错了会清空语料 |
| `archiveThreshold` | 0.45 | `DEFAULT_EVICTION` | 0.1–0.47 平线 | **当前不生效**，分数下界比它高 |
| `retireThreshold` | 0.25 | `DEFAULT_EVICTION` | 0.1–0.45 平线 | 同上，且 `evictedShare` 盖住了它的作用 |

`archiveThreshold` / `retireThreshold` 那两行的"不生效"不是 bug，是当前语料的分数分布造成的。要让它们参与决策，得先让分数下探到 0.5 以下——那是换语料或者重新设计阈值语义的事，不是调数。

改任何默认值之前先看 [默认值修订](../experiments/默认值修订-2026-11-06.md)：那一轮改的三个数都是"平台中点"，不是"最优点"。
