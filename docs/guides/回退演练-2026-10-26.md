# 回退演练（2026-10-26）

软删除的全部价值是"能反悔"。在这份文档之前，"能反悔"只是设计上的说法：`apply` 写的是 `l1_records.state`，理论上一条 UPDATE 就能恢复，但没有人从头到尾走过一遍，也没有人量过要多久。

这份文档是那次走查的产物，只留**现在怎么回退**：一至六节是任何人任何时候照着做都能用的步骤。照它做两遍的实测结果、复现清单与取证材料在姊妹文件 [`docs/experiments/回退演练记录-2026-10-26.md`](../experiments/回退演练记录-2026-10-26.md)，那份绑在 2026-10-26 的快照与具体 run id 上。**副本上实测总耗时 6.5 秒与 13.9 秒（差异全在容器起停），召回恢复到与归档前逐条一致**——数字与逐条比对都在那份文件的一、三节。

范围声明：演练在 `VACUUM INTO` 出来的副本 + 换端口的临时容器里做，生产容器与生产数据卷全程没碰（见[回退演练记录](../experiments/回退演练记录-2026-10-26.md)的「生产未触碰（逐项核对）」一节）。补丁目标树是文件式布局的 `store/sqlite.ts`，而生产在跑的是目录式布局 `store/sqlite/` 那一代代码——**两者不是同一份代码，但 `package.json` 里的版本号区分不出来**（`v2.0.0`/`v2.0.0-beta.1`/`v2.0.1*` 写 `2.0.0-beta.1`，`v2.0.2` 之后反而全写 `1.0.2-beta.1`）。判断代码代数只能看文件布局，不能看版本号。所以本文所有数字描述的是**补丁树**的行为，不是生产现网的行为。

## 一、什么时候该回退

命中下面任意一条，就按本文回退，不要在现场调参数：

1. **该记住的东西召不回来了。** 用户或评审指出某条明确该被召回的记录，在归档后查不到，而它在归档前能查到。
2. **召回质量掉了，且能归因到这次 `apply`。** 同一批 query 的命中集合在 `apply` 前后对比出现系统性变差（不是单条波动）。
3. **归档量明显不对。** `forgetting_runs` 里 `archived + retired` 的数量与计划不符，或者远超预期。
4. **数据库不变量报了错。** `PRAGMA integrity_check` 非 ok，或走索引的 `COUNT` 与全表扫的 `COUNT` 不一致（见第三节）。这种情况先按本文把状态改回去，再单独排查写库路径。
5. **计划本身选错了记录。** 阈值、配额、pin 规则配错，导致一批不该动的记录被归档。

反过来说，下面这些**不是**回退理由：单条记录的分数变化（RRF 名次分随候选集变化，同一 query 在归档前后不必同分）；召回条数从 5 变 4 但候选池还有余量（那是过滤生效，不是塌窗）；`forgetting_audit` 里有记录而你不记得跑过（先查 `forgetting_runs` 的 `actor` 再决定）。

## 二、前置：先留一份退路

**回退本身也可能出错。** 所以在改任何东西之前，先对当前库做一份 `VACUUM INTO` 副本。源库只读打开，副本是独立文件，出问题直接换回去。

写成脚本而不是 `node -e`：PowerShell 下带嵌套双引号的单行命令，Node 收到的往往是语法错误的源码（A4 实测 `SyntaxError: Expected ',', got '<eof'>`），而且不会有明显提示——库文件根本不会生成。

```js
// vacuum.mjs
import { DatabaseSync } from "node:sqlite";
import { existsSync, mkdirSync, rmSync, statSync } from "node:fs";
import { dirname } from "node:path";

const SRC = "data/snapshot-20261026.db";
const OUT = process.argv[2] ?? ".scratch/a5-drill/data/vectors.db";

// VACUUM INTO 只管写文件：它既不建父目录，也拒绝覆盖已存在的文件。所以先建目录，
// 再把目标连同 -wal / -shm 旁文件一起删掉——只删主库，上一次的 WAL 会留给新库。
mkdirSync(dirname(OUT), { recursive: true });
for (const f of [OUT, `${OUT}-wal`, `${OUT}-shm`]) rmSync(f, { force: true });

const src = new DatabaseSync(SRC, { readOnly: true });
src.exec(`VACUUM INTO '${OUT}'`);
src.close();

const rep = new DatabaseSync(OUT, { readOnly: true });
const one = (sql) => rep.prepare(sql).get();
console.log("src_bytes", statSync(SRC).size);
console.log("dst_bytes", statSync(OUT).size);
console.log("total_l1", one("SELECT COUNT(*) AS c FROM l1_records").c);
console.log("has_state_column", one("SELECT COUNT(*) AS c FROM pragma_table_info('l1_records') WHERE name='state'").c > 0);
console.log("integrity", JSON.stringify(one("PRAGMA integrity_check")));
rep.close();
console.log("wal_files_present", existsSync(`${OUT}-wal`));
```

```powershell
# 放在仓库根目录执行；要换输出路径就接一个参数：node .\vacuum.mjs D:\tmp\vectors.db
node .\vacuum.mjs
```

**这个文件要落盘到仓库根目录，文件名就叫 `vacuum.mjs`。** 它不是"读文档时顺手跑一下"的片段：复现清单第 0 步就是 `node .\vacuum.mjs`，落地位置表把它列为第一行，而那份复现清单现在在 `docs/experiments/回退演练记录-2026-10-26.md` 的第三节。漏了它，复现清单第一句就 `MODULE_NOT_FOUND`（2026-10-27 实测）。

**`mkdirSync` 与「先删目标」这两行不是装饰，各有一条实测失败垫底。** 把这两行拿掉，就会退回到 FE-002 指出的状态：干净目录上 `unable to open database: <路径>`（`errcode 14`，exit 1，`VACUUM INTO` 不建父目录），已有副本上 `output file already exists`（exit 1，目标文件 mtime 不变）。补回之后两种机器状态各跑一次，都是 exit 0、`total_l1 822`、`integrity {"integrity_check":"ok"}`、`wal_files_present false`——`-wal` / `-shm` 旁文件也不再残留。

演练用的副本路径是 `.scratch/a5-drill/data/vectors.db`（脚本的默认值；换库时把路径作为第一个参数传进去），源库 `data/snapshot-20261026.db` 25,657,344 字节，SHA256 `58EC4F20…DB375B`，822 条 L1、519 条向量、**没有 `state` 列**（所以第一次起容器时顺带跑了在线迁移）。源库本身从哪来，见复现清单开头的「前置产物」表（docs/experiments/回退演练记录-2026-10-26.md）——它刻意不进版本库。

## 三、硬前提：写库之前必须停容器

这不是谨慎，是实测踩出来的。

2026-10-26 的容器冒烟里，容器持着库、宿主机就地 `UPDATE l1_records SET state='archived'`：`changes: 1`，宿主机读回也确实变成 archived，然后同一 query 跑了 5 条，那条"已归档"的记录还在第 1 名。查下去发现数据库已经不干净：

```
state='active'（走索引）            : 822      ← 错
state='active' AND NOT INDEXED      : 821      ← 对
group by（走索引）                  : active=822                          ← 错
group by NOT INDEXED                : active=821, archived=1             ← 对
l1_recallable 视图条数              : 822      ← 错，视图仍在返回归档行
按主键单条查                        : archived ← 对
PRAGMA integrity_check              : row 696 missing from index idx_l1_state
PRAGMA quick_check                  : ok       ← 只信这个会漏
```

同一个错误在第二个容器上表现成 HTTP 500 `disk I/O error`，堆栈落在 `PRAGMA journal_mode = WAL` 那一行。最可能的原因是 Windows 宿主进程与 Linux 容器进程同时写同一个 bind mount 上的 WAL 库，跨 OS 的文件锁不可靠——这一条是推断，没有做机制级隔离验证。

**所以：每一次写库，都必须先 `docker stop`，写完在容器仍停着的状态下 checkpoint + 复查不变量，然后才起容器。** 不要用 `busy_timeout` 顶。`busy_timeout` 解决的是锁等待超时，解决不了跨 OS 的 WAL 一致性；UPDATE 能过，不代表索引是对的。

每次写库之后，必须复查两条不变量；checkpoint 的 `busy` 也要一起看（它是第三条，见步骤 4）。`TdaiCheck` 现在三条一起判定：

```powershell
# 容器必须是 stopped 状态
docker inspect -f '{{.State.Status}}' <容器名>
```

```powershell
# runbook-lib.ps1 是本文附录 B，先把它存到当前目录
. .\runbook-lib.ps1
TdaiCheck -DbPath 'E:\tdai-forgetting\.scratch\a5-drill\data\vectors.db'
# 等价于手工跑下面那四条 SQL + PRAGMA，最后一行打印 INDEX_CONSISTENT / INTEGRITY_OK / CHECKPOINT_OK
# 三项都判：任一项 false 就 exitCode 2 并抛错，不是只打印
```

任何一次回退脚本跑完也会自己打印这三条、并自己判定（见步骤 4 与步骤 6）。手工核对的最小 SQL 是：

```sql
SELECT COUNT(*) FROM l1_records WHERE state='active';                  -- 走 idx_l1_state
SELECT COUNT(*) FROM l1_records NOT INDEXED WHERE state='active';      -- 强制全表扫
SELECT COUNT(*) FROM l1_recallable;                                    -- 视图
PRAGMA integrity_check;
```

三个数必须相等，`integrity_check` 必须是 `ok`。**`quick_check` 不能替代 `integrity_check`**：上面那个坏掉的库，`quick_check` 报的就是 ok。

## 四、回退步骤

下面六步覆盖一次完整回退：查审计、改状态、补审计、验不变量、起容器验召回，最后给一条能一次跑完的脚本。第 2 步的 SQL 有两版，先看差异再选，别直接抄短的那版。

**步骤 2 与步骤 3 绑在同一个事务里，不能拆开粘贴。** 理由在步骤 3 开头：指纹结果集必须赶在 UPDATE 之前物化，而 `TdaiSql` 一次只 `prepare()` 一条语句、每次调用还是新连接，事务跨不过两次调用——所以这两步的可粘贴形式是附录 A 的脚本，不是两条独立 SQL。

### 步骤 1：查这次 run 动了哪些记录

```sql
-- ? 换成真实的 run id；下面步骤都用同一个值
SELECT record_id, action, from_state, to_state, score, reason
  FROM forgetting_audit WHERE run_id = ?;
```

直接粘贴的写法（`runbook-lib.ps1` 的 `TdaiSql`，附录 B）：

```powershell
$db  = 'E:\tdai-forgetting\.scratch\a5-drill\data\vectors.db'
$run = 'run-2026-10-26T15-20-39-415Z-f7c298bbfd4f'    # 换成你要回退的那次（这里是定稿版那一遍）

TdaiSql -DbPath $db -Sql "SELECT record_id, action, from_state, to_state, score, reason FROM forgetting_audit WHERE run_id = '$run'"
```

演练里这一句返回 52 行，前三行：

```json
{"record_id":"m_1788957474892_3445a8f1","action":"archive","from_state":"active","to_state":"archived","score":0.55,"reason":"quota 600: bottom-ranked (1/52)"}
{"record_id":"m_1787982803163_9c17f102","action":"archive","from_state":"active","to_state":"archived","score":0.60,"reason":"quota 600: bottom-ranked (2/52)"}
{"record_id":"m_1787986981707_6f9c23b9","action":"archive","from_state":"active","to_state":"archived","score":0.60,"reason":"quota 600: bottom-ranked (3/52)"}
```

`reason` 里带的是决策当时的理由和分数，所以回退不用重跑策略——决策依据就在这一行里。

### 步骤 2：按 run 回退

提示词给的版本：

```sql
UPDATE l1_records
   SET state='active', forget_reason=NULL, forgotten_time=NULL
 WHERE record_id IN (
   SELECT record_id FROM forgetting_audit
    WHERE run_id = ? AND to_state <> 'active')
   AND state <> 'active';
```

这个版本在演练主路径（一次 apply、一次回退）上是对的，52 条全部恢复。但它有两处需要说清楚，都不在提示词里。

**第一处：`state <> 'active'` 的实际作用，和提示词写的理由不一致。**

提示词说这个条件防的是"把之后被别的 run 归档的记录一起复活"。实测不支持这个说法：被后续 run 归档的记录**当前状态就不是 active**，无论有没有这个条件，它们都落进 `IN (...)` 且都会被改成 active。对着真实 applier run 量：

```
run A 归档 52 条 → 回退 A → run C 又归档同样 52 条 → 重放 A 的回退
  带 state 条件   : archivedBefore 52 → changes 52 → archivedAfter 0
  不带 state 条件 : archivedBefore 52 → changes 52 → archivedAfter 0
```

两种写法结果一模一样，都被后续 run 的归档撤掉了。**这个条件挡不住"重放旧回退"。**

它真正挡的是另一件事：**已经 active 的行被顺手清空 `forget_reason` / `forgotten_time`**。构造一批"手工恢复过、但 `forget_reason` 还留着"的行来量：

```
人工恢复 5 条（state='active'，forget_reason='kept by an operator'），再对其余 47 条回退
  带 state 条件   : changes 47，那 5 条的 forget_reason 保留
  不带 state 条件 : changes 52，那 5 条的 forget_reason 被清成 NULL
```

也就是说，这个条件的价值是**保护别人留下的痕迹**，不是防止误复活。条件本身该留——回退工具不该去改它没有归档过的行的元数据——但理由要写对，否则下一个人会以为误复活问题已经被它解决了，而实际上没有。

**第二处：它完全挡不住"回退一个无效 run"。**

`applier.ts` 对**每个计划目标**都写审计行，包括它实际上没能改的行（`reason` 会追加 `" (row not active; state unchanged)"`）。同一份 plan 文件跑两次，第二次那 52 行审计全是无效记录，但那 52 个 `record_id` 摆在表里，状态也确实不是 active——所以带上 `state <> 'active'` 一样会命中：

```
run N1 归档 52 条；run N2 重放同一份 plan（52 行审计全是 no-op）
回退 N2：带 state 条件 changes 52 → archivedAfter 0    ← 复活了它根本没归档的 52 条
```

这里 `state <> 'active'` 帮不上忙，因为那些记录确实不是 active——只是不是 N2 弄成那样的。

**所以要加一道指纹。** `applier.ts` 改一条记录时，在同一个事务里同时写两处：

- `l1_records.forget_reason = <这条审计行的 reason>`
- `l1_records.forgotten_time = <这条审计行的 decided_at>`

于是 `(state, forget_reason, forgotten_time)` 与 `(to_state, reason, decided_at)` 相等，当且仅当"这个 run 归档它之后没有人再动过它"。后来的 run、手工改过的行、无效审计行，都对不上指纹。

回退用这个版本：

```sql
UPDATE l1_records
   SET state='active', forget_reason=NULL, forgotten_time=NULL
 WHERE record_id IN (
   SELECT a.record_id
     FROM forgetting_audit a
     JOIN l1_records r ON r.record_id = a.record_id
    WHERE a.run_id = ?
      AND a.action <> 'rollback'
      AND a.to_state <> 'active'
      AND r.state = a.to_state
      AND r.forget_reason = a.reason
      AND r.forgotten_time = a.decided_at)
   AND state <> 'active';
```

全部用真实 applier run 量的对照：

| 场景 | 提示词版（`run_id + to_state + state<>'active'`） | 指纹版 |
|---|---|---|
| 单次 apply 后回退（演练主路径） | changes 52，恢复 52 | changes 52，恢复 52 |
| 重放旧回退（后续 run 已重新归档同批） | changes 52，**把后续 run 的工作撤了** | changes 0，后续 run 保持 |
| 回退一个无效（no-op）run | changes 52，**复活 52 条它没归档的记录** | changes 0 |
| 行已被别处恢复成 active（留着 `forget_reason`） | changes 47，那 5 行不动 | changes 47，那 5 行不动 |
| 同上但把 `state <> 'active'` 去掉（反例） | changes 52，5 行的 `forget_reason` 被清成 NULL | — |
| 对同一个 run 连跑两次 | 第二次 changes 0 | 第二次 changes 0 |

两版在最后一列都能通过的两处（单次回退、连跑两次），差异为零；差异集中在"这次 run 的审计行还准不准"这一类场景上。

指纹版多一个 JOIN，但代价量不出来：同一份库上两条 SQL 各跑 200 次（每次都重建 52 行的归档状态再回退），提示词版均值 1.81 ms、指纹版 1.79 ms，差异在噪声里。**建议固定用指纹版**——多出来的安全边际不花时间。

演练主路径是单次 apply，两个版本结果一样（都是 52 条），所以[回退演练记录](../experiments/回退演练记录-2026-10-26.md)里的数字两个版本都成立。

**指纹依赖 applier 的写入行为，这是它的前提条件。** 整套判定挂在 `src/applier.ts:88–117`：同一个事务里 `forget_reason = <审计行的 reason>`、`forgotten_time = <审计行的 decided_at>`。applier 哪天改了这两处（比如换写成别的格式、或者只写一处），指纹就对不上了，回退会恢复 0 条。方向是保守的——不会误改——但没人会发现，所以这条不变式现在有测试钉着：`test/applier.test.ts` 的 `archiving writes (state, forget_reason, forgotten_time) that match the audit row`，逐行断言 `(state, forget_reason, forgotten_time) == (to_state, reason, decided_at)`。改 applier 的这两处会让它红。反过来，这条测试红了就别信本文的指纹。

**指纹对不上就跳过，这是保守方向，不是失败。宁可少恢复，不可错恢复。**

- 漏恢复一条，它还躺在库里、审计也还在，换个时间补就是；错恢复一条，它的 `forget_reason` / `forgotten_time` 被清空，指纹随之消失，事后没法证明它原本属于哪次 run，也没法区分"这次回退真的改了它"和"它本来就 active"。两种错的代价不对称，所以默认选前一种。
- 所以脚本在 `targets_fingerprint_matched` 小于审计行数时不报错、不动那些行，只把差额打进 `skipped_changed_since`。**0 是合法输出，不是故障**——它只说明"这个 run 的审计行现在一条都对不上库里的状态"。
- 恢复 0 条时**先别改库**，按下面的诊断把原因查清楚再决定：是回退错了 run，还是这些记录本来就该保持现状。直接 `UPDATE` 或"照着审计行补一遍"会把假记录写进审计（见步骤 3）。

**恢复 0 条或只恢复了一部分时，先别改库。** 拿不准就先跑诊断，三条只读 SQL，不改任何东西。

**第 0 条先确认 run id 本身存在。** 少了这一步，`$run` 写错时下面两条会返回一个「看起来正常」的空结果。实测把 run id 末尾加一个 `-TYPO`，改动前那版（`SUM` 没套 `COALESCE`）的第一条给出 `{"audit_targets":0,"fingerprint_matched":null}`，第二条给出空数组 `[]`，和「这个 run 确实没有可恢复的行」长得一模一样。诊断工具不该有这种静默面，所以这一版补了两道：**先查 run 存在性**，再给 `SUM` 套 `COALESCE`。

```powershell
# 先确认 $run 没写错；run_check 不是 ok 就停下，别读下面两条的数字
TdaiSql -DbPath $db -Sql "SELECT CASE WHEN COUNT(*) > 0 THEN 'ok' ELSE 'not-found' END AS run_check, COUNT(*) AS run_exists FROM forgetting_runs WHERE run_id = '$run'"
```

写对时打印 `{"run_check":"ok","run_exists":1}`；写错时打印 `{"run_check":"not-found","run_exists":0}`——**看到 `not-found` 就别往下读了**：run id 敲错了，或者这个库不是那次演练的库。（判定写成 ASCII 的 `ok`/`not-found`，不写中文提示：这条要在 PowerShell 管道里被 `ConvertFrom-Json` 读、也可能被 `Select-String` 匹配，取值一旦掺进控制台代码页就不可靠了——实测中文提示在 936 代码页下打印成乱码。）

第 1 条给分母。`SUM` 外面套了 `COALESCE(..., 0)`：`SUM` 在没有匹配行时返回的是 `null`，和 `audit_targets = 0` 并列着读容易被当成"没有可恢复的行"——套上之后最坏也只是 `0/0`，配上第 0 条就不会误读：

```powershell
# 审计行共多少、指纹命中多少（下面所有 SQL 都用同一个 $run）
TdaiSql -DbPath $db -Sql "SELECT COUNT(*) AS audit_targets, COALESCE(SUM(CASE WHEN r.state IS a.to_state AND r.forget_reason IS a.reason AND r.forgotten_time IS a.decided_at THEN 1 ELSE 0 END), 0) AS fingerprint_matched FROM forgetting_audit a JOIN l1_records r ON r.record_id = a.record_id WHERE a.run_id = '$run' AND a.action <> 'rollback' AND a.to_state <> 'active'"
```

**读这条的两个前提：** `audit_targets = 0` 先回头查第 0 条（`run_check` 是不是 `ok`），别直接下"没有可恢复的行"的结论；`audit_targets > 0` 而 `fingerprint_matched = 0` 才是真正的"指纹全对不上"，往第 2 条查原因。

第 2 条把对不上的行逐字段打出来，并给一个粗分类的 `cause`：

```powershell
TdaiSql -DbPath $db -Sql "SELECT a.record_id, a.to_state AS audit_to_state, r.state AS row_state, a.reason AS audit_reason, r.forget_reason AS row_forget_reason, a.decided_at AS audit_decided_at, r.forgotten_time AS row_forgotten_time, CASE WHEN r.state = 'active' THEN 'already-active' WHEN a.reason LIKE '%(row not active; state unchanged)' THEN 'noop-audit-row' WHEN r.state = a.to_state AND r.forgotten_time IS NOT a.decided_at THEN 're-archived-by-later-run' WHEN r.forget_reason IS NOT a.reason THEN 'reason-edited-by-hand' ELSE 'other' END AS cause FROM forgetting_audit a JOIN l1_records r ON r.record_id = a.record_id WHERE a.run_id = '$run' AND a.action <> 'rollback' AND a.to_state <> 'active' AND NOT (r.state IS a.to_state AND r.forget_reason IS a.reason AND r.forgotten_time IS a.decided_at) ORDER BY a.record_id LIMIT 20"
```

（用 `IS` 而不是 `=`，是为了 NULL 也能比对：某个字段被人工清成 NULL 时，`=` 会让整行从结果里掉出去，看起来像"对上了"。）

三种典型对不上，各自的实测输出与处置：

**1. 后续 run 重新归档了同一批（`re-archived-by-later-run`）。** 状态和 reason 都对，只有 `forgotten_time` 变成后来的时间：

```json
{"record_id":"m_1787982023556_0ee0532f","audit_to_state":"archived","row_state":"archived","audit_reason":"quota 600: bottom-ranked (9/52)","row_forget_reason":"quota 600: bottom-ranked (9/52)","audit_decided_at":"2026-10-26T16:33:43.561Z","row_forgotten_time":"2026-10-26T16:38:23.722Z","cause":"re-archived-by-later-run"}
```

处置：**按新的那次 run 回退，不要回退旧的。** 旧 run 的工作已经被撤销又被重做，回退它等于把新 run 的归档一起撤掉——这正是指纹要挡的。先 `SELECT run_id, started_at, mode FROM forgetting_runs ORDER BY started_at DESC`，确认哪一次是当前有效的那次。

**2. no-op 审计行（`noop-audit-row`）。** 状态对得上（都还是 archived），但审计行的 `reason` 末尾带 `" (row not active; state unchanged)"`，`decided_at` 也换成这一遍的时间：

```json
{"record_id":"m_1787982023556_0ee0532f","audit_to_state":"archived","row_state":"archived","audit_reason":"quota 600: bottom-ranked (9/52) (row not active; state unchanged)","row_forget_reason":"quota 600: bottom-ranked (9/52)","audit_decided_at":"2026-10-26T16:38:23.597Z","row_forgotten_time":"2026-10-26T16:33:43.561Z","cause":"noop-audit-row"}
```

处置：**这个 run 没有改过任何东西，回退它没有意义。** 找它上一层的 run（同一份 plan 的更早一次）去回退；找不到就说明这批记录是被别的 run 归档的。

**3. 有人手工恢复过（`already-active`）。** 状态已经是 active，reason 和 time 还是归档时的值：

```json
{"record_id":"m_1787982023556_0ee0532f","audit_to_state":"archived","row_state":"active","audit_reason":"quota 600: bottom-ranked (9/52)","row_forget_reason":"quota 600: bottom-ranked (9/52)","audit_decided_at":"2026-10-26T16:33:43.561Z","row_forgotten_time":"2026-10-26T16:33:43.561Z","cause":"already-active"}
```

处置：**不用管。** 那条记录已经恢复，回退再改它一次也只是把它的 `forget_reason` 清掉——丢掉别人留下的痕迹。剩下的行照常回退，结果就是 47/47，不是 52/52。这时候别去"凑满 52"：把那 5 行也算进去，只能靠按审计行写出 5 行假审计（见步骤 3）。

第 4 种 `reason-edited-by-hand`（状态对上、时间对上、只有 reason 被改）本次没有造出来量，代码里保留了这个分支，判据与上面第三条同向：不要动它。

### 步骤 3：另起一行审计

回退本身也是一次状态变更，要留痕。但**不能改原 run 的行**：那一行记的是"当时发生了什么"，事后改写等于销毁证据。做法是新增：

- `forgetting_runs` 插入一行，`mode='rollback'`，`run_id = 'rb-' || <原 run_id>`，`policy_json` 里写 `{"rollback_of": "<原 run_id>"}`；
- `forgetting_audit` 插入 `action='rollback'` 的行，`from_state` 取原行的 `to_state`，`to_state='active'`，`score` 沿用原分数（它是决策依据，不是当前状态），`reason` 写 `'rollback of <原 run>: <原 reason>'`。

原 `forgetting_runs` 那行的 `status` 不动——它确实 completed 了，回退是另一件事，靠新的 run 行表达。

**这一步的源数据是「指纹结果集」，不是「这个 run 的审计行」。** 审计行说的是这个 run *决定*了什么，不是它*改成了*什么；`applier` 对没改成的行也写审计（步骤 2 第二处），所以按审计行写回退记录会凭空写出"某时把某条从 archived 改成 active"，而那条根本没动。演练的早期版本就是这么写的，no-op run 上写 52 行、手工恢复 5 条后写 52 行——`integrity_check` 照样 ok，事后分不清哪 47 行是真的。

**正确的 SELECT 条件只有指纹结果集给得出，而它在步骤 2 的 UPDATE 之后就没了**（改成 active、两个字段清空，指纹随之消失）。所以顺序是死的：先把指纹集物化成 TEMP 表 → 再 UPDATE → 再从 TEMP 表插入审计。同一连接、同一事务。这样的东西不是一条能粘贴的 SQL，是附录 A 的脚本；下面四段与附录 A 的对应段落一致（语句、表、列、`WHERE` 条件、`ON CONFLICT`、`NOT EXISTS` 全部相同），差别只在占位符：正文为了读得懂写成 `<runId>` / `<rbRunId>` / `<policyJson>` / `<targets>`，附录 A 里分别是模板字符串 `'${runId.replace(/'/g, "''")}'` 与三个 `?` 绑定参数。**所以别把下面四段逐字粘进数据库**——它们不是可执行文本（每段开头的 `//` 只是阅读用的注释，不是 SQL 语法；`<runId>` 之类是占位符），可执行的那份在仓库里：`scripts/rollback-forgetting.mjs`（附录 A 只讲用法差异，不再放全文）：

```sql
// 1) 指纹结果集（UPDATE 之前物化，事务内 TEMP 表）
CREATE TEMP TABLE a5_rb AS
  SELECT a.record_id AS record_id, a.run_id AS source_run, a.to_state AS from_state,
         a.score AS score, a.reason AS reason, a.decided_at AS decided_at
    FROM forgetting_audit a
    JOIN l1_records r ON r.record_id = a.record_id
   WHERE a.run_id = '<runId>'
     AND a.action <> 'rollback'
     AND a.to_state <> 'active'
     AND r.state = a.to_state
     AND r.forget_reason = a.reason
     AND r.forgotten_time = a.decided_at

// 2) 只改指纹命中的行
UPDATE l1_records SET state='active', forget_reason=NULL, forgotten_time=NULL
 WHERE record_id IN (SELECT record_id FROM a5_rb) AND state <> 'active'

// 3) 回退 run 行：total = 指纹命中数（= 将要恢复的条数）
INSERT INTO forgetting_runs (run_id, started_at, finished_at, mode, actor, policy_json, total, pinned, archived, retired, kept, status, notes)
VALUES (<rbRunId>, strftime('%Y-%m-%dT%H:%M:%fZ','now'), strftime('%Y-%m-%dT%H:%M:%fZ','now'), 'rollback', 'scripts/rollback-forgetting.mjs', <policyJson>, <targets>, 0, 0, 0, 0, 'completed',
        'rollback: restore recall for one apply run') ON CONFLICT(run_id) DO NOTHING

// 4) 每个被恢复的行一行 rollback 审计；来源是 a5_rb，不是审计表
INSERT INTO forgetting_audit (audit_id, run_id, record_id, action, from_state, to_state, score, reason, decided_at, decided_at_ms)
SELECT lower(hex(randomblob(16))), ?, record_id, 'rollback', from_state, 'active', score,
       'rollback of ' || source_run || ': ' || reason,
       strftime('%Y-%m-%dT%H:%M:%fZ','now'), CAST(strftime('%s','now') AS INTEGER) * 1000
  FROM a5_rb rb
 WHERE NOT EXISTS (SELECT 1 FROM forgetting_audit c WHERE c.run_id = ? AND c.record_id = rb.record_id AND c.action = 'rollback')
```

粘贴执行就是附录 A 那一行：`node scripts/rollback-forgetting.mjs $run $db`（见步骤 6。不再需要先点源 `runbook-lib.ps1`——这一段靠脚本自己的事务，不靠 `TdaiSql`）。**不要在 PowerShell 里用 `TdaiSql` 把这几段逐条发出去**：`TdaiSql` 每次调用起一个新连接，TEMP 表与事务都留不下来，第 1 段的 `a5_rb` 到第 4 段已经不存在，只能退回按审计表插入——就是上面那个写法。

**断言：rollback 审计行数必须等于 `records_restored`。** 脚本里是硬断言，不是期望值。下面是 `scripts/rollback-forgetting.mjs:173–177` 的原文，不是示意：

```js
if (Number(aud.changes) !== Number(upd.changes)) {
  console.error("wrote " + aud.changes + " rollback audit rows for " + upd.changes + " restored records");
  db.exec("ROLLBACK");
  return EXIT_COUNT_MISMATCH;
}
```

注意它既不是 `throw`、也不是 `process.exit(5)`。`throw` 只对看得见 stderr 的人有意义，退出码才对脚本调用方有意义；而 `process.exit()` 会把刚打印出来的计数截断（脚本第 18–20 行的注释说的就是这两件事）。所以 `main()` 返回 `EXIT_COUNT_MISMATCH`，由顶层 `process.exitCode = main(...)` 交给 Node：输出先落地，退出码随后生效。本文这一段以前写成 `process.exit(5)`，与真脚本不符——FE-005 的 P3 指的就是那处漂移。

三种场景的实测（同一份 `VACUUM INTO` 副本、同一次 apply `run-2026-10-26T16-33-43-546Z-f7c298bbfd4f`，只在 `a5_rb` 之后走这四段）：

```
场景                                    records_restored  rollback_audit_rows  指向未改动记录的 rollback 行
单次 apply 后回退（演练主路径）                    52                  52                0
手工恢复 5 条后再回退                              47                  47                0
no-op run 回退（恢复 0 条）                         0                   0                0
```

"手工恢复 5 条"是把 5 行状态改成 active、保留归档时写下的 `forget_reason`/`forgotten_time`。三种场景跑完，`integrity_check` 都是 ok，`active_indexed = active_fullscan = recallable_view` 也都成立：主路径与部分恢复都是 822/822/822，no-op 是 770/770/770（它没有恢复任何东西，52 条仍在 archived）。

对照组是旧写法（来源换成 `forgetting_audit` +`NOT EXISTS`）：主路径 52（所以演练没暴露）、手工恢复 5 条 52（多 5 行假记录）、no-op run 52（52 行全部指向仍然 archived 的记录）。

还有一种"看起来对"的折中——在旧写法上加 `AND EXISTS (SELECT 1 FROM l1_records r WHERE r.record_id = a.record_id AND r.state = 'active')`。主路径和 no-op 都能过，但手工恢复 5 条那种场景仍旧写 52 行：那 5 行确实已经 active，`EXISTS` 拦不住它们，而它们不是这次回退改的。**判据是"这一行是不是这次回退改的"，只有指纹结果集回答得了。**

### 步骤 4：checkpoint + 两条不变量（容器仍然是停的；三条都要判定）

改完库、还没起容器的时候做这一步。**顺序不能反**：起了容器再 checkpoint，就又变成"两个进程同时碰一个 WAL 库"。

```powershell
. .\runbook-lib.ps1
TdaiCheck -DbPath 'E:\tdai-forgetting\.scratch\a5-drill\data\vectors.db'
```

期望 `checkpoint` 的 `busy` 为 0、三个 COUNT 相等、`integrity_check` 为 ok、`INDEX_CONSISTENT True`、`CHECKPOINT_OK True`。**`busy` 是要判定的，不是要打印的**：不为 0 说明还有连接持着库，已提交的帧留在 `-wal` 里没进主库；这时`-wal` 没被截断，而「只拷主库」取副本会静默少数据（第六节第一行）。

**`TdaiCheck` 从 2026-10-27 起也判这一条**（此前只打印、靠眼睛看，与仓库脚本两套标准——照附录 B 跑一遍拿到 exit 0 会让人以为验过 checkpoint 了）。现在它和 `scripts/rollback-forgetting.mjs` 同口径：`busy !== 0`（或 WAL 下 `checkpointed < log`）即 `CHECKPOINT_OK false`、`process.exitCode = 2`、外层 PowerShell `throw`。两种状态的实测：

```
# 不持读事务
checkpoint {"busy":0,"log":0,"checkpointed":0}
INDEX_CONSISTENT true INTEGRITY_OK true CHECKPOINT_OK true
→ 正常返回，$LASTEXITCODE 0

# 另一个连接持着读事务（`-wal` 里有 6 帧，只 checkpoint 掉 3 帧）
checkpoint {"busy":1,"log":6,"checkpointed":3}
INDEX_CONSISTENT true INTEGRITY_OK true CHECKPOINT_OK false
→ throw: 不变量检查失败（exit 2），$LASTEXITCODE 2
```

夹具是自建的 60 行小库（50 active / 10 archived，WAL），不碰任何真实数据。同一夹具上旧版 `TdaiCheck` 在第二种状态打印完照样 exit 0——这正是要修的那一处。

**非 WAL 库不会误报**：`VACUUM INTO` 出来的副本是回滚日志模式，`wal_checkpoint` 返回 `{"busy":0,"log":-1,"checkpointed":-1}`，那两个 `-1` 是"没有 WAL 可截断"而不是"截断失败"，所以判定写成 `log < 0 || checkpointed >= log`。实测同一份非 WAL 副本：`CHECKPOINT_OK true`、正常返回、`$LASTEXITCODE 0`。写成 `checkpointed >= log` 而不带 `log < 0` 那半个条件，这份库会被误判成失败。

任一不满足就停下，不要起容器——带着坏索引起容器，症状会是"回退没生效"或 500 `disk I/O error`，而不是数据库坏了。

### 步骤 6：一次跑完（脚本版）

上面五步手工做容易漏掉 checkpoint 或某个不变量。打包成脚本之后是一条命令。

注意两者的分工：**演练的分段计时来自上面五步的逐步执行**（`runbook-drill.ps1`，停容器、查审计、UPDATE、写审计、验指纹、跑不变量、起容器、检索，每段各自计时）；**脚本版另外在独立副本上验过行为一致**（52 条全恢复、`INDEX_CONSISTENT true`、对旧 run 恢复 0 条），做的是同一组 SQL，但没有在容器里再量一遍召回。下面"实测输出"两段就是那两次独立副本的原始打印。

脚本在附录 A（仓库里的 `scripts/rollback-forgetting.mjs`）与附录 B，落盘后：


## 五、明确不做的事

### 不删列

加的那五列（`state` / `access_count` / `last_access_time` / `forget_reason` / `forgotten_time`）回退后留着。理由两条，都要说清楚。

**第一条：旧代码看不见新列，所以留着无害——这一条实测过。** 用未打补丁的读取路径（`.scratch/baseline/MemoryCore`，`sqlite.ts` 里 `l1_recallable` 命中 0 次、`ADD COLUMN state` 命中 0 次；作为对照，打过补丁的 `.scratch/applytest4` 树是 3 次）加载已迁移的副本：

```

degraded false
count_l1 822
queryL1Records_rows 822
first_row_keys agent_id,content,created_time,metadata_json,priority,record_id,scene_name,session_id,session_key,task_id,team_id,timestamp_end,timestamp_start,timestamp_str,type,updated_time,user_id,version
```

全 `active` 的副本（822 条）和已归档 52 条的副本（770 active / 52 archived）都跑了，两次都是 exit 0，`row_has_state_column false`——旧代码压根不知道 `state` 存在，行为与迁移前完全一样。跑完再查不变量仍是 `integrity ok` + 索引一致，说明旧代码打开并关闭这个库没有留下任何东西。

**第二条：删列比加列贵。** SQLite 3.53.1 有 `ALTER TABLE DROP COLUMN`，但在这个 schema 上：

```

  → error in index idx_l1_state after drop column: no such column: state
DROP INDEX idx_l1_state; 再试
  → error in view l1_recallable after drop column: no such column: state

  → OK（5 ms）
```

也就是说，要删必须先拆索引、拆视图，然后那五列没了，`src/applier.ts` 的 UPDATE、`src/cli.ts` 的 stats/plan、整个遗忘引擎全部失效——等于把这次落地的代码一起回退。而"删掉再需要时加回来"是又一次 `ALTER`，加回来时 822 行的默认值还要重写一遍。留列的成本是三条索引的维护开销、加上每行多五个字段；删列的成本是拆索引 + 拆视图 + 代码回退 + 未来的二次迁移。

**结论：不删列。** 这条写在这里，是为了下一个人不用再问一遍、也不用再量一遍。

### 不改历史审计

`forgetting_audit` 里属于原 run 的行，一条都不改、一条都不删。演练把这件事做成了断言而不是纪律：回退前后对原 run 的审计行做 SHA256 指纹，两次一致才算通过。

**指纹只有配上序列化口径才可复算。** 下面七项任意一项换了，同样 52 行就会算出另一个哈希——所以口径钉死在这里。换语言复算时照抄这张表，别自己挑一种"看起来一样"的拼法。

| 口径项 | 取值 |
|---|---|
| 覆盖范围 | `WHERE run_id = '<原 run>'`（52 行；不是全表 104 行，理由见下） |
| 字段与顺序 | `audit_id`、`record_id`、`action`、`from_state`、`to_state`、`score`、`reason`（七个字段，次序即拼接次序） |
| 分隔符 | 字段之间是竖线（U+007C），两行之间是分号（U+003B），**行尾不加**任何分隔符 |
| 字段值里的分隔符 | **不转义、不引号、原样拼**。字段值里出现竖线（U+007C）或分号（U+003B）时照原字符拼进去，不做任何 escape。依据是实测：`.scratch/a5-drill/data/` 下 12 个库、1,347 行审计里，`reason` 带分号的 **312 行**（`doc-step3.db` 104、`guard-truth.db` 104、`guard-effect.db` 52、`replay-resurrect.db` 52，全是 `… (row not active; state unchanged)` 后缀；定稿版那 52 行里为 0），带竖线 **0 行**。这个岔路真的会让哈希变：同一份 `guard-truth.db` 全表 208 行，原样拼 `E0336C9255A5B465…`，把 `;` 转义成 `\;` 后 `A5DFEFF0D2CBDC3B…`（拼接串 30,123 → 30,227 字节）；`doc-step3.db` 同理 `3A87E8585D3BE78B…` → `EE97BFC445436CF4…`。只转义竖线则三个库一个字节都不变（因为 0 行带竖线） |
| 行序 | `ORDER BY audit_id`（**必须写进 SQL**；靠结果集自然顺序不算口径） |
| `score` 这个 REAL | 定点六位小数。SQL 侧 `printf('%.6f', score)` 与 JS 侧 `score.toFixed(6)` 在 30,766 个 [0,1] double 上**逐字节相同**（0 处差异）。Python 的 `format(x, '.6f')` 有 2 处不同：它按四舍六入五成双（banker's rounding），SQL 与 JS 按四舍五入，**只在恰好落在 0.5×10⁻⁶ 上的值**分歧（实测 `0.0078125` → SQL/JS 给 `0.007813`、Python 给 `0.007812`）。用 Python 复算时按本节 SQL 走，或改用 `Decimal` 的 ROUND_HALF_UP；本快照 7 个分值都不落在半值上，三种写法得同一个哈希 |
| NULL | 六个文本字段 `COALESCE(x,'')`；`score` 用 `CASE WHEN score IS NULL THEN '' END` |
| 编码与哈希 | 拼接串按 **UTF-8** 编码后算 SHA256，取大写十六进制 |

**为什么 `score` 必须显式格式化，不能让它"自然"进字符串。** 这是最容易绕过去的一处：SQLite 把 REAL 转文本用的是它自己的 dtoa（`score || ''`、`CAST(score AS TEXT)`、`quote(score)` 三者完全一致，等于 `printf('%!.17g', score)` 的 17 位有效数字），JS 用最短往返表示。同一批 52 行、同一条拼接配方，只换 `score` 的写法：

```
SQLite 隐式  score || ''            -> 0.69999999999999985    （52 行里 24 行与 JS 不同）
JS 侧        String(score)           -> 0.6999999999999998
本文口径      printf('%.6f', score)  -> 0.700000
```

前两个文本 `Number()` 回读是同一个 double（不是精度损失），但字节不同、指纹就不同：同一份库上只差这一处，分别拼出 `36EBD622230E94D3` 与 `3B7085929DC62FF4`，52 行里 24 行的 `score` 文本不一致。所以口径要选一个**两边都能逐字节复现**的写法；本文选定点六位小数，代价是放弃 1e-6 以下的分数差异（本快照 7 个不同分值映射到 7 个不同文本，无碰撞）。

可直接粘贴的那条 SQL（本节所有哈希都是它跑出来的）：

```sql
SELECT group_concat(
         COALESCE(audit_id,'')   || '|' || COALESCE(record_id,'')  || '|' ||
         COALESCE(action,'')     || '|' || COALESCE(from_state,'') || '|' ||
         COALESCE(to_state,'')   || '|' ||
         CASE WHEN score IS NULL THEN '' ELSE printf('%.6f', score) END || '|' ||
         COALESCE(reason,''), ';') AS fp
  FROM (SELECT * FROM forgetting_audit
         WHERE run_id = '<原 run>'
         ORDER BY audit_id);
```

配套的 PowerShell 段（`TdaiSql` 来自附录 B；它把 fp 原样吐成一个 JSON 字段，再对 UTF-8 字节算 SHA256）——**这一段的输出就是本节表格里的哈希**：

```powershell
. .\runbook-lib.ps1
$db  = 'E:\tdai-forgetting\.scratch\a5-drill\data\vectors.db'
$run = 'run-2026-10-26T15-20-39-415Z-f7c298bbfd4f'   # 换成你的 run
$sql = @"
SELECT group_concat(
         COALESCE(audit_id,'')   || '|' || COALESCE(record_id,'')  || '|' ||
         COALESCE(action,'')     || '|' || COALESCE(from_state,'') || '|' ||
         COALESCE(to_state,'')   || '|' ||
         CASE WHEN score IS NULL THEN '' ELSE printf('%.6f', score) END || '|' ||
         COALESCE(reason,''), ';') AS fp
  FROM (SELECT * FROM forgetting_audit
         WHERE run_id = '$run'
         ORDER BY audit_id)
"@
$fp = (TdaiSql -DbPath $db -Sql $sql | ConvertFrom-Json).fp
Write-Output ('fp_len=' + $fp.Length)
[BitConverter]::ToString([Security.Cryptography.SHA256]::Create().ComputeHash(
  [Text.Encoding]::UTF8.GetBytes($fp))).Replace('-','')
```

**换语言复算的实测（都以定稿版这 52 行为准）**：JS 版（`toFixed(6)` + 同一拼接次序）拼出的串与 SQL 逐字节相等（`fp === jsJoin` 为 `true`），Python 版（`format(score, '.6f')` + `str()` 处理文本字段）独立算出的也是同一个哈希，三者同为 `DABDF7C8CBA226D2D0988A952BF9A868F53E05C9399B711FD728F723B82F79B5`（拼接串长度都是 6,646 字节）。两个坑写在前面：从 SQL 取 `score` 时先确认拿到的是 number 而不是字符串（`node:sqlite` 映射成 number，换驱动可能给字符串，那就 `Number()`）；Python 的 `format` 在半值上的舍入方向与 SQL/JS 相反，见上表。

实测（定稿版，`run-2026-10-26T15-20-39-415Z-f7c298bbfd4f`，从 `.scratch/a5-drill/logs/drill-run.txt` 原样摘录）：

```
[步骤2] 查审计  rows=52  0.13s
    审计指纹(归档行) 36EBD622230E94D3
[步骤5] 历史审计未被改写  unchanged=True  sha256=36EBD622230E94D3  n=52
```

**这两行是旧口径跑出来的，和上面那张表的数字对不上不是矛盾。** 演练当时的脚本把 `score` 直接拼进串（等于 SQLite 隐式转文本），所以留下的是 `36EBD622230E94D3`；按本文定下的 `printf('%.6f')` 口径复算，同一份副本、同一个 run 是 `DABDF7C8CBA226D2`。两列并排给出来，是为了让手上只有旧值的人能对上号：

| 覆盖范围 | 行数 | 本文口径 `printf('%.6f', score)` | 旧口径（隐式 `score`） |
|---|---|---|---|
| `run_id = 原 run`，`ORDER BY audit_id` | 52 | `DABDF7C8CBA226D2` | `36EBD622230E94D3` |
| 同上但 `ORDER BY record_id` | 52 | `7E43B8272B6CA421` | `4CFA08E3E54289AC` |
| 全表（原 run 52 + rollback 52） | 104 | `1E64F9812916542B` | `2BBB4C45F38B1045` |

上表六个数都是 2026-10-27 在 `.scratch/a5-drill/data/vectors.db` 上现算的，SQL 与 PowerShell 段就是本节给的那两段；整串哈希（不是前缀）分别是 `DABDF7C8CBA226D2D0988A952BF9A868F53E05C9399B711FD728F723B82F79B5`、`7E43B8272B6CA42106BEEA99BE19E590B2CC5C015686F94C7233B0BC9FF80D88`、`1E64F9812916542B037D1E39D47A834D6E0F3C527921D13369E63A1FA77B7E81`。

第二行同时说明排序键也是口径的一部分：指纹必须把排序写死在 SQL 里（`ORDER BY audit_id`），否则同样 52 行会算出别的哈希——两种排序差出的是行序，不是行集。

回退后表里有 104 行审计：52 行 `archive`（原 run）+ 52 行 `rollback`（新 run）。两条时间线都在，谁在什么时候把什么改成了什么，读得出来。

**关于早先印在这里的 `84A061EC192D5613`：** 这个值现在复算不出来，也找不到它属于哪次 run——改这一稿时重跑了下面这些：

- 现存唯一带指纹的日志是 `.scratch/a5-drill/logs/drill-run.txt`（23:20:30 起那一遍，即定稿版），里面两处都是 `36EBD622230E94D3`；
- 第一遍（22:50 起）的日志 `.scratch/a5-drill/logs/rollback-drill.txt` 里根本没有指纹那两行——它出自指纹断言加进脚本之前的版本；
- `.scratch/a5-drill/data/` 与本次复核用的 `.scratch/fe1/` 下共 43 个 `.db`，每个库的全表 / 每个 run / 非 rollback 子集 / 仅 rollback 子集共 190 个口径，各配 4 种排序键与 3 种分隔符，算出 2280 个哈希，没有一个是 `84A0…`；
- 每一遍演练开头都跑 `01-vacuum.mjs`（第二节 `vacuum.mjs` 的原型，多一个「把 `data/` 下所有文件删掉重建」的动作：`for (const f of readdirSync(DIR)) rmSync(join(DIR, f), …)`），所以第一遍的库文件不在了，那个值也无法追溯。

结论：`84A0…` 属于演练过程中的某一遍、哪一遍已经查不出来，**本文不再引用它**——更准确的说法是，**当时报告里的那个数字没有可复算的证据支撑**，不是「查不到源」这么轻。上面三行的数字是今天在定稿版副本上用本文的 SQL 复算的，可以自己跑一遍核对。这个教训进「已知陷阱」：指纹要连 run id 一起记。

### 不物理删除

"遗忘"在这个仓库里始终是 `state` 字段的取值变化，不是删字节。回退尤其不能靠"删掉再重灌"——那会同时丢掉审计和 FTS/向量索引里的历史行。演练结束时表里的行数没变：

```
l1_records 822   l1_fts 822   l1_vec_rowids 519   l1_recallable 822
```

`l1_fts` 和 `l1_vec` 里那 52 条一直没被删过，归档只是让 `l1_recallable` 视图和检索路径的 JOIN 把它们过滤掉。这也是回退能这么快的原因：不需要重建任何索引。

## 六、已知陷阱汇总

| 陷阱 | 症状 | 处置 |
|---|---|---|
| 容器持库时从宿主机写 | `integrity_check` 报 `row N missing from index`，视图仍返回归档行；或第二个容器直接 500 `disk I/O error` | 写之前 `docker stop`；写完 checkpoint（`busy` 必须为 0）+ 两条不变量，三条都要判定，不能只打印。`TdaiCheck` 与 `scripts/rollback-forgetting.mjs` 现在都判（前者 `exitCode 2`、后者 `4`） |
| `TdaiCheck` 只打印 checkpoint（2026-10-27 前） | 另一连接持着读事务时它打印 `{"busy":1,...}` 然后照样 exit 0，而仓库脚本在同一夹具上 exit 4——同一个仓库两套标准 | 已改：`busy` 并入 `ok` 并 `exitCode = 2`；两种状态实测见步骤 4 |
| 把「缺 `forgetting_*` 表」也记在码 `4` 名下 | 读码的人以为缺表也会先写再报，实际它在写入之前就抛 | 码 `4` 只留「缺 `l1_recallable` 视图」（收尾段、COMMIT 之后）；缺表落 `1`、什么都没做。四个 DROP 实测见第四节「用法说明」 |
| 拿 `--dry-run` 直接对生产库目录跑 | 只读打开 WAL 库会在旁边留 `-shm` 与 0 字节 `-wal`；之后「按目录整体拷三件」会把它们带走，也让"源目录只有 `vectors.db`"的断言误报 | 先拷一份再对副本 `--dry-run`；或接受这两个旁文件并知晓它们会被拷走 |
| 把退出码 `1` 当"写错了" | 另一连接持写锁时 `BEGIN IMMEDIATE` 抛 `database is locked`，落 `1`——**没写任何东西**，但 `1` 的定义是"用法错" | 调用方认输出里的 `action`；退出码 `1` 单独不足以判因 |
| 只信 `quick_check` | 报 ok，但索引已经不一致 | 固定用 `integrity_check`，并比对索引 COUNT 与全表扫 COUNT |
| 回退只按 `run_id + to_state` | 重放旧回退会撤销新 run 的归档；回退无效 run 会复活 52 条；都不报错 | 用指纹版——**可执行的那份是 `scripts/rollback-forgetting.mjs`**，步骤 2 里那两段 SQL 只用来读懂判定逻辑，不是能粘贴执行的脚本 |
| 按审计行写 rollback 记录 | 主路径看不出问题（52 行），no-op run 与部分恢复场景各写出 52 行"没发生过的回退"，`integrity_check` 照样 ok | 从指纹结果集插入，并断言 `rollback_audit_rows == records_restored`（步骤 3） |
| 审计指纹不带 run id | 两遍演练的哈希混在一起，事后分不清哪个值属于哪次 run，也没法复算（`.scratch/a5-drill/data/` 每次演练开头被清空重建） | 指纹与 run id、行数、排序键一起记（第五节） |
| 用 `TdaiSql` 逐条粘贴步骤 2/3 | 每次调用是一个新连接，TEMP 表与事务都不在，`a5_rb` 到第 4 段已经不存在 | 步骤 2+3 走附录 A 的脚本，一次事务 |
| 以为 `state <> 'active'` 能防误复活 | 提示词就是这么写的，但它挡不住：被后续 run 归档的行本来就不是 active | 它防的是清掉别人留的 `forget_reason`；防误复活要靠指纹 |
| PowerShell 下 `node -e "..."` | 嵌套双引号被吃掉 → Node 收到语法错误的源码，库文件不生成 | 写成 `.mjs` 文件，或用 here-string 管道给 `node --input-type=module` |
| `.ps1` 里有中文注释 | Windows PowerShell 5.1 按 ANSI 读，报 `Unexpected token` / `字符串缺少终止符` | 文件存成 UTF-8 **带 BOM** |
| 用 `Out-File` 写补丁或脚本 | 写入 CRLF，git 逐字节比对全部不匹配 | 用 `[IO.File]::WriteAllText` 或 Node `writeFileSync`，显式 LF |
| 挂单文件而不是目录 | `-wal` / `-shm` 落到容器可写层，与主库分居两个文件系统 | 挂目录（**未做 A/B 对照**，只有 2026-10-26 那次单文件挂载下 WAL 文件位置异常的观察） |

回退脚本不再内嵌在文档里，它是仓库里的可执行文件 **`scripts/rollback-forgetting.mjs`**，全文只有那一份。文档里再放一份可执行全文，正是"A7 之前每一次评审都要有人把附录抽出来、跟演练时真正跑的那份逐字节比对"的成因——那个流程能抓住漂移，但只在有人愿意重做一遍的时候才有效。

用法（与演练当场那份 `rollback-run.mjs` 有四处差异：db 必填、`--dry-run`、计数不符走退出码 5、db 路径必须已存在）：

```powershell
# db 必填（第二个参数），或走 $TDAI_DB；两者都没有就打印用法、退出码 1
node scripts/rollback-forgetting.mjs <run_id> <db 路径>

$env:TDAI_DB = '<db 路径>'
node scripts/rollback-forgetting.mjs <run_id>

# 只诊断、不写库：打印指纹匹配数、跳过数与将被恢复的 record_id 列表，退出码 0
node scripts/rollback-forgetting.mjs <run_id> <db 路径> --dry-run
```

1. **没有默认 db 路径了。** 演练版默认 `.scratch/a5-drill/data/vectors.db`；进仓库后删掉——运维脚本猜一个相对路径默认值，等于在生产机上随机挑一个库写进去。现在 db 取第二个参数或环境变量 `TDAI_DB`，两者都没有就打印用法、退出码 1。
2. **新增 `--dry-run`。** 走完指纹匹配与跳过统计后打印 `targets_fingerprint_matched` / `skipped_changed_since` / `would_restore_ids`，跑在**只读连接**上、不开写事务（不是"开了再回滚"），退出码 0。它存在的理由只有一个：步骤 2 那条「恢复 0 条先别改库」的诊断需要一个不改库的入口。
3. **`restored != matched` 从 `throw` 变成退出码 5。** `throw` 只对看得见 stderr 的人有意义，退出码才对脚本调用方有意义；"rollback 审计行数 != 恢复数"那条断言同样走退出码 5，两条都在提交事务之前触发、事务回滚。
4. **db 路径必须已经存在。** 非 dry-run 打开 `DatabaseSync` 默认会建文件，演练版（以及仓库版的第一稿）会在打错的路径上留下一个 0 字节库再报错。现在先 `existsSync`，不存在就打印 `no such database`、退出码 1、不建文件。

退出码一览：

| 码 | 含义 | 落在这个码上的具体条件 |
|---|---|---|
| `0` | 成功 | 写已提交，**且**三条收尾判定全部成立（见下一段） |
| `1` | 用法错，什么都没做 | 缺 run_id 或缺 db；**或 db 路径不存在**（新加：旧版会先在该路径建一个 0 字节文件再报错，见下）；**或库被别的连接写锁住**（`BEGIN IMMEDIATE` 抛 `database is locked`，见下文「用法说明」第二条）；**或缺 `forgetting_runs` / `forgetting_audit` 两张表**（在写入之前抛，什么都没做，见下文「缺表与缺视图的方向不一样」） |
| `2` | run 不存在 | `forgetting_runs` 里查不到这个 run_id |
| `3` | mode 不是 `apply` | 例如拿 rollback run 再回退 |
| `4` | 不变量失败（写已提交） | 三条任一不成立：**checkpoint 的 `busy != 0`**（有别的连接持着库，帧没落进主库、`-wal` 没被截断）或 WAL 下 `checkpointed < log`；`active_indexed` / `active_fullscan` / `recallable_view` 三者不等；`integrity_check != ok`。**收尾段读不出来也只归这里一种情况：缺 `l1_recallable` 视图**（那时 COMMIT 已过，报 1「什么都没做」正好把事实说反）。缺 `forgetting_*` 表**不在**这一行——它在写入之前就抛，落 `1`，见下文「缺表与缺视图的方向不一样」 |
| `5` | 计数不对（写未提交，已回滚） | 恢复数 != 指纹匹配数，或 rollback 审计行数 != 恢复数 |

**三条收尾判定，三条都定退出码。** 顺序是三个 COUNT（走索引 / 全表扫 / 视图）→ checkpoint → `integrity_check`，脚本打印 `checkpoint {"busy":…}` 与 `INDEX_CONSISTENT … INTEGRITY_OK … CHECKPOINT_OK …`。checkpoint 这一条以前只打印不判定（FE-005 的 P1）：另一个连接持着读事务时，`wal_checkpoint(TRUNCATE)` 返回 `{"busy":1,"log":87,"checkpointed":77}`，10 帧已提交事务留在 `-wal` 里没进主库，脚本却照样 exit 0、对外宣布成功——接着「只拷主库」取副本就会静默少数据，正是第六节第一行那个陷阱。`log` / `checkpointed` 在非 WAL 库上是 `-1`（没有东西可截断、也没有帧被钉住），所以那种库只比 `busy`。

**db 路径打错不再建空库。** 非 dry-run 打开 `DatabaseSync` 默认会创建文件，于是 `node scripts/rollback-forgetting.mjs <run> C:\…\typo.db` 以前会留下一个 0 字节的 `typo.db` 再退出 1。现在先 `existsSync` 判一下，不存在就走 1、**不建文件**——运维脚本不该在生产机上随机挑一个路径写进去，这与「没有默认 db 路径」是同一条理由。

**三条用法说明（都是实测，不是推断）。**

**1. 码 `4` 不是数据坏了：停掉别的连接重跑一次即可，写入是幂等的。** `4` 只说明写已提交、但三条收尾判定有一条没过。实测：另一个进程持着读事务、`-wal` 有 75 帧时跑一次，`records_restored 52`、`checkpoint {"busy":1,"log":75,"checkpointed":4}`、`CHECKPOINT_OK false`、退出码 `4`；等那个连接退出后原样再跑一次，`targets_fingerprint_matched 0`、`records_restored 0`、`rollback_audit_rows 0`、`checkpoint {"busy":0,...}`、`CHECKPOINT_OK true`、退出码 `0`。第二遍没有重复恢复、也没有重复写审计——指纹把已经恢复的行挡在外面（这正是"重跑得 0 恢复"的意思）。

**2. 写锁场景落 `1` 是语义混淆：fail-safe（没写）但码不对。** `1` 的定义是"用法错"，而"库被别的连接写锁住"是运行期状态，两者混在同一个码上。实测：另一个连接持着 `BEGIN IMMEDIATE` 时跑，`archived_now 52 active_now 770` 之后在 `BEGIN IMMEDIATE` 处抛 `database is locked`（`errcode 5`），退出码 `1`，库的状态分布**一点没变**（还是 770/52）。方向是安全的（没写），但调用方只看退出码会把"库忙"读成"命令写错了"。**调用方应该认输出里的 `action` 而不是只看码**；脚本本身没改这一处（改它会动退出码契约，属于另一件事）。

**3. `--dry-run` 只读打开 WAL 库会留 `-shm` 与 0 字节 `-wal`。** 实测：把一份 WAL 库的旁文件删干净（`-wal` / `-shm` 都不存在）后跑 `--dry-run`，退出码 `0`、`dry_run_no_changes true`，但目录里多出 `drywalk.db-shm`（32768 字节）与 `drywalk.db-wal`（**0 字节**）。对副本无害；**在生产目录上要注意**：这两个文件会被"按目录整体拷三件"的取快照流程带走，也会让"源目录应该只有 `vectors.db`"这类断言误报。真要只读诊断生产库，先拷一份再对它跑。

**为什么不用显而易见的 SQL —— 这段解释在代码注释里也有一份，因为它唯一的记忆就是那一段。** `applier.ts` 对**每个计划目标**都写审计行，包括它实际没能改的行（`reason` 尾部追加 `" (row not active; state unchanged)"`）。所以按 `run_id` + `to_state` 回退会信任这些假审计：no-op 重放同一份 plan 之后再回退，52 条全被复活；后续 run 重新归档之后回退旧 run，又把新 run 的工作撤掉。判定必须用指纹 `(state, forget_reason, forgotten_time) == (to_state, reason, decided_at)`，对不上就跳过——**少恢复不是错恢复**：漏恢复的还躺在库里、审计也还在，错恢复会把 `forget_reason` / `forgotten_time` 清空、指纹随之消失。完整推导、对照数字与三种诊断场景在第四节步骤 2 与步骤 3，审计指纹的序列化口径在第五节。

### 缺表与缺视图的方向不一样（旧口径在这里错过）

**缺 `forgetting_*` 表落 `1`，缺 `l1_recallable` 视图落 `4`——这是本轮实测把旧口径纠正过来的那一处。** 旧版文档把四种缺失（视图 + 两张表）都写在码 `4` 名下。实测（同一份 822 行夹具的三个独立副本，各 `DROP` 一次后原样跑脚本）：

```
A 基线（不删任何东西）  records_restored 52  rollback_audit_rows 52  INDEX_CONSISTENT true INTEGRITY_OK true CHECKPOINT_OK true  exit=0
B DROP VIEW   l1_recallable   records_restored 52  rollback_audit_rows 52  然后 stderr:
                              invariant checks could not finish after COMMIT: 52 records restored and 52 rollback
                              audit rows are already committed; ... Cause: no such table: l1_recallable          exit=4
C DROP TABLE  forgetting_runs  stderr: Error: no such table: forgetting_runs（第 98 行，查 run 那一步）  exit=1
                              库的状态分布未变：active 770 / archived 52，审计行 156 未增
D DROP TABLE  forgetting_audit stderr: Error: no such table: forgetting_audit（第 116 行，建指纹 TEMP 表那一步）  exit=1
                              库的状态分布未变：active 770 / archived 52
```

读法：**视图是收尾段才查的，那时 `COMMIT` 已经过了，所以只能是 `4`（写已提交）**；**两张表一开场就要查（`forgetting_runs` 验 run、`forgetting_audit` 建指纹集），都在写事务之前就抛，所以是 `1` 且没写任何东西**。两者不能混在同一行里，否则读码的人会以为缺表也会先写后报。

**测试钉住了它。** `test/rollback-script.test.ts` 覆盖：正常回退 52/52、no-op run **0/0（不是 0/52）**、部分场景 47/47（且指向仍 archived 记录的 rollback 行 = 0、操作员留下的 5 条 `forget_reason` 不被清）、指纹不符跳过、`--dry-run` 不写库（跑前跑后 `forgetting_audit` 行数与 state 分布都断言不变）、非 apply run 退出码 3、run 不存在退出码 2、缺 db 退出码 1、`TDAI_DB` 可用；另外几条钉住退出码本身：恢复数与审计行数对不上时退出码 5 且事务回滚（真回滚，state 分布与审计行数都断言不变）；视图与计数不一致时退出码 4；**第二个连接持着读事务、checkpoint 被挡住时退出码 4 而不是 0**（FE-005 的 P1，同一夹具下 `checkpoint {"busy":1,…}` + `CHECKPOINT_OK false`）；**缺 `l1_recallable` 视图时退出码 4，且 stderr 明说写已提交**（P2——它以前落到 1，而 1 是「用法错、什么都没做」）；**db 路径不存在时退出码 1 且不创建文件**（P3）。期望值全是硬编码常数（52、47、3、0），不从实现里读出来再比对。该文件 14 条用例，全仓 `npm test` 现在 118 条（104 + 原 FE 轮新增的 11 + 本轮的 3）。

**附录 B / C / D 为什么不进 `scripts/`。** 附录 B（`runbook-lib.ps1`）留在本文第八节：两个 PowerShell 函数（`TdaiSql` 跑一条 SQL、`TdaiCheck` 做 checkpoint + 两条不变量），是 Windows 演练现场的辅助；跨平台仓库不该带 PowerShell 依赖，而回退脚本自己已经把 checkpoint 与两条不变量这三条都做完、并且**三条都参与退出码判定**了。（`TdaiCheck` 那一版在 2026-10-27 之前只打印 checkpoint、不判定 busy——P1 在文档侧的来源就是这里；现在它已按同一口径判定并 `exitCode = 2`，见步骤 4。）B 现在只服务步骤 1/2 的只读诊断与步骤 4 的第二意见。附录 C（`20-baseline-load.mts`）不进仓库：它 import 的是未打补丁的旧代码树（`.scratch/baseline/MemoryCore`），是"证明加列对旧代码无害"那一次用的验证工具，不是产品工具。附录 D 的两个检索探针靠"召回恢复了吗"这个问题活着，而它们的调用步（2/5/7）全在复现清单里，所以跟着复现清单一并搬走，不单独留。三份全文现在都在 `docs/experiments/回退演练记录-2026-10-26.md`（附录 C、D 各占一节），读者不会以为漏了。

**本格的产物不计算审计指纹。** 回退脚本只打印计数与 id，快照脚本也不写日志，所以第五节那套口径在这里落成一条对后续脚本的硬规定，写在 `docs/experiments/回退演练记录-2026-10-26.md` 的「指纹口径」一节——连同"现存两个 `.ps1` 仍是旧口径、下次真跑会产出旧值"那句提醒。


## 八、附录 B：`runbook-lib.ps1`

PowerShell 的两个辅助函数：`TdaiSql`（执行一条 SQL，默认只读）和 `TdaiCheck`（checkpoint + 两条不变量）。

**这两个函数留在文档里、不进 `scripts/`。** 它们是 Windows 演练现场的辅助，跨平台仓库不该带 PowerShell 依赖；回退脚本（`scripts/rollback-forgetting.mjs`）自己已经把 checkpoint 与两条不变量这三条都做了、而且三条都判定（`CHECKPOINT_OK` 与另两项一起进 `ok`），`TdaiCheck` 现在只是给步骤 4 手工复核用的第二意见。

**但它从 2026-10-27 起也是判定的，不再是"只打印"**：`busy !== 0`（或 WAL 下 `checkpointed < log`）会让 `CHECKPOINT_OK` 变 `false`、`process.exitCode` 变 `2`，外层 `if ($LASTEXITCODE -ne 0) { throw ... }` 随即抛错。改之前同一个仓库里两套标准——脚本判 `busy`、附录 B 只打印——照附录 B 跑一遍拿到 exit 0 会让人以为 checkpoint 验过了。两种状态的实测输出在步骤 4。反过来的那个例子是 `Show-Snapshot`：它确实进了仓库（`scripts/snapshot-check.ps1`），理由不是跨平台，而是它的**键清单必须与脚本输出一致**——手抄的清单已经错过两次（一个根本不存在的 `wal_present`、四个被写成条件输出的 wal 键），搬成脚本之后这个漂移结构性消失。

**存成 UTF-8 带 BOM。** Windows PowerShell 5.1 按 ANSI 读没有 BOM 的文件，中文注释会变成乱码并被当成代码解析，报出 `Unexpected token '}'` 这类与真实原因无关的错（本次演练踩过）。

```powershell
# ---- 回退 runbook 的两个辅助函数（整段粘贴到 PowerShell） ----
# 为什么不是一行 node -e：pwsh 会把嵌套双引号吃掉，Node 收到的是语法错误的源码
# （A4 实测 SyntaxError）。here-string 交给 node --input-type=module 没有转义问题。
function TdaiSql {
  param([Parameter(Mandatory)][string]$Sql, [string]$DbPath = 'E:\tdai-forgetting\.scratch\a5-drill\data\vectors.db', [switch]$Write)
  $env:TDAI_DB = $DbPath
  $env:TDAI_SQL = $Sql
  $env:TDAI_RO = if ($Write) { '0' } else { '1' }
  @'
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync(process.env.TDAI_DB, { readOnly: process.env.TDAI_RO === "1" });
db.exec("PRAGMA busy_timeout = 10000");
const stmt = db.prepare(process.env.TDAI_SQL.trim().replace(/;+$/, ""));
if (stmt.columns().length > 0) console.log(JSON.stringify(stmt.all(), null, 2));
else console.log(JSON.stringify({ changes: stmt.run().changes }));
db.close();
'@ | node --input-type=module
  if ($LASTEXITCODE -ne 0) { throw "SQL failed (exit $LASTEXITCODE)" }
}

function TdaiCheck {
  param([string]$DbPath = 'E:\tdai-forgetting\.scratch\a5-drill\data\vectors.db')
  $env:TDAI_DB = $DbPath
  @'
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync(process.env.TDAI_DB);
db.exec("PRAGMA busy_timeout = 10000");
const one = (s) => db.prepare(s).get();
const all = (s) => db.prepare(s).all();
// Shortened before the checkpoint for the same reason the rollback script does it: the
// 10 s timeout above exists so the write path can wait out a writer, but for the
// checkpoint it would only turn "another process holds the file" into a ten-second
// pause followed by the same verdict.
db.exec("PRAGMA busy_timeout = 1000");
const checkpoint = one("PRAGMA wal_checkpoint(TRUNCATE)");
console.log("checkpoint", JSON.stringify(checkpoint));
const idx = one("SELECT COUNT(*) AS c FROM l1_records WHERE state='active'").c;
const full = one("SELECT COUNT(*) AS c FROM l1_records NOT INDEXED WHERE state='active'").c;
const view = one("SELECT COUNT(*) AS c FROM l1_recallable").c;
console.log("states_indexed", JSON.stringify(all("SELECT state, COUNT(*) AS c FROM l1_records GROUP BY state ORDER BY state")));
console.log("states_fullscan", JSON.stringify(all("SELECT state, COUNT(*) AS c FROM l1_records NOT INDEXED GROUP BY state ORDER BY state")));
console.log("active_indexed", idx, "active_fullscan", full, "recallable_view", view);
const integrity = String(one("PRAGMA integrity_check").integrity_check);
console.log("integrity", integrity);
console.log("quick_check", JSON.stringify(one("PRAGMA quick_check")));
// busy != 0 means another connection still pins frames: committed transactions stay in
// -wal and a copy that takes only the main file is silently short. Printed-but-not-judged
// is how that shipped once (see step 4), so it decides the exit code here too -- same
// three judgements, same order, same verdict as scripts/rollback-forgetting.mjs.
const checkpointLog = Number(checkpoint.log);
const checkpointed = Number(checkpoint.checkpointed);
const checkpointOk = Number(checkpoint.busy) === 0 && (checkpointLog < 0 || checkpointed >= checkpointLog);
const consistent = idx === full && view === full;
const ok = consistent && integrity === "ok" && checkpointOk;
console.log("INDEX_CONSISTENT", consistent, "INTEGRITY_OK", integrity === "ok", "CHECKPOINT_OK", checkpointOk);
db.close();
process.exitCode = ok ? 0 : 2;
'@ | node --input-type=module
  if ($LASTEXITCODE -ne 0) { throw "不变量检查失败（exit $LASTEXITCODE）" }
}
```
