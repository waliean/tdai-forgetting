# 生产回退 runbook — 2026-11-06

## 〇、与 A5 那份的关系

[回退演练](./回退演练-2026-10-26.md)（A5）证明的是**技术上能不能退**：停容器 → 改库 → checkpoint → 起容器，耗时与召回逐条对比都在那里面。

这份是另一半：**怎么发现该退**，以及**只退该退的**。

两份并存时：操作步骤（停容器、checkpoint、验证 SQL）以 A5 为准，本文只补"识别"和"部分回退"两部分，不重复 A5 已写过的命令。冲突时以 A5 为准，因为它是演练过的那份。

## 一、识别信号（三种，各有确认命令）

误判几乎不报错。下面三条是最常见的表现，每条都有一个不用改库就能查的命令。

### 信号 1：该记住的搜不到了

人给的信号。具体表现是"上周我还搜得到 X，现在搜不到了"。

确认（在**副本**上跑，不要动生产库）：

```bash
node scripts/rollback-forgetting.mjs <run_id> data/<copy>.db --dry-run
```

`--dry-run` 会列出该 run 归档、且**此后没被人碰过**的记录 id。如果用户说的那条在列表里，它就是被这个 run 归档的。

再用真实检索确认（见第四节），不要只看 `state` 字段。

### 信号 2：一条记录同时被标成失效和被 pin 保护

`plan` 的 `pinInvalidConflicts` 会列出来。plan 阶段就能看到：

```bash
node src/cli.ts plan --db data/<copy>.db | grep -A3 "pinned.*invalid"
```

这类冲突不是"引擎错了"，是两条指令打架，需要人决定保留哪一条。**不要直接回退**——先看是哪两句话。

### 信号 3：体检脚本报 FAIL

```bash
node scripts/healthcheck.ts --db data/<copy>.db
```

- `pinIntact` FAIL：硬 pin 离开了 `active`。这不是正常路径能产生的状态，说明有人绕过了引擎写库。先查是谁写的（审计里没有它的归档行），再看要不要回退。
- `auditGaps` FAIL：审计行数与 run 计数对不上。如果 run 的 `status` 是 `failed`，这是中断的正常痕迹，重跑 apply 即可；如果是 `completed`，按本文走。

### 不该当信号的两件事

- **单次淘汰率高**：一次 run 归档 8% 是正常的。连续三次都高才是阈值错了。
- **`avgScore` 变化**：D4 把 floor 从 0.3 降到 0.2，这个分数的量纲整体下移了 0.1。拿它和旧记录比会得出"质量下降"的错误结论。

## 二、确认范围

在副本上跑 dry-run，得到两个数：`targets_fingerprint_matched` 和 `skipped_changed_since`。

- 前者是能安全回退的条数；
- 后者是**这个 run 动过、但此后有人改过**的条数——这些不会被回退，因为改了它们就抹掉了"哪次 run 归档的"这个证据。

然后逐条判断：这 N 条里，哪几条是误判。

```bash
node scripts/rollback-forgetting.mjs <run_id> data/<copy>.db --dry-run
# would_restore_ids ["m_001","m_002",...]
```

对照用户反馈和检索结果，圈出真正误判的 id。

## 三、全量回退（用得少）

```bash
node scripts/rollback-forgetting.mjs <run_id> data/<copy>.db
```

只在"这个 run 整个都是错的"时用。比如阈值配错导致误归档，整批都不该走。

## 四、部分回退（生产上最常见）

一个 run 动了 40 条，可能只有 3 条误判。全量回退会把正确的 37 条也捞回来，等于这次 apply 白做，而且要重新打分再淘汰一遍。

```bash
node scripts/rollback-forgetting.mjs <run_id> data/<copy>.db --records m_001,m_007,m_022
```

输出里三个数：

```
partial_requested 3 partial_fingerprint_usable 3
records_restored 3
rollback_audit_rows 3
```

- `partial_requested` 是你要的条数；
- `partial_fingerprint_usable` 是通过指纹校验、实际会被恢复的条数。**比 requested 小就说明有记录在归档后被人改过**，那些不会恢复；
- 回退本身也写审计行（`action = 'rollback'`），历史审计行一条不动。

先 `--dry-run --records ...` 看一遍，再写。

## 五、生产库在容器里，怎么不撞 WAL 锁

生产库在 `tdai-memory-core` 容器里，挂载点是 `D:/ZCodeData/tdai-data/core`。

**运行中直接 `UPDATE` 会撞 WAL 锁**，而且更糟的情况是写成功了一半。三种做法，按推荐顺序：

1. **停容器再改**（A5 未验证的做法，最稳）

   ```bash
   docker stop tdai-memory-core
   # 此时数据库文件不再被占用
   node scripts/rollback-forgetting.mjs <run_id> /path/to/mounted/core.db --records ...
   docker start tdai-memory-core
   ```

2. **只读连接确认**（`--dry-run` 已经这么做）：脚本在 dry-run 模式下用只读连接打开，不会创建文件、不会加写锁。先用它看清楚再决定。

3. **在副本上改完再换文件**：把库文件复制出来，在副本上完成回退并验证，停容器后替换。这是 A5 演练用的路径，耗时最长但可回滚。

不要在生产库上直接跑不带 `--dry-run` 的脚本——除非容器已经停了。

## 六、验证：走真实检索，不看 `state`

A3 已经证明"库里对"不等于"能召回"。回退后必须用真实检索确认：

```bash
# 方式一：MCP 工具
#   memory_search 查询用户报的那句话
# 方式二：HTTP
curl -s http://127.0.0.1:8420/v3/atomic/search -H 'content-type: application/json' \
  -d '{"query":"用户报的原话","limit":5}'
```

判定：

- 被回退的记录必须出现在结果里（`partial` 场景下逐条确认）；
- 未被回退的记录必须仍然不出现；
- 如果被回退的出现了但排序很靠后，那是正常的——回退只把 `state` 改回来，不重算分数。

## 七、补写审计

回退脚本会自己写 `action = 'rollback'` 的审计行，历史行不动。但有三件脚本写不了、必须人工补的：

1. **为什么要退**。在 runbook 的复盘记录里写（见第八节），不是写进数据库。
2. **`forgetting_runs` 里那次 apply 的 `notes`**。如果那次 apply 的 notes 是空的，现在补一句"其中 N 条于 <日期> 回退"，否则下次看 run 表会以为一切正常。

   ```sql
   UPDATE forgetting_runs SET notes = COALESCE(notes,'') || ' | 3 of 40 rolled back 2026-11-06'
    WHERE run_id = '<run_id>';
   ```

3. **如果整批都被回退**，`archived` / `retired` 计数仍然是当时的数字，不要改——它们是"那次 run 做了什么"的记录，不是"现在库里是什么样"。

## 八、复盘模板

```markdown
## 回退复盘 <日期>

- 触发信号：          （三种信号里的哪一种，谁报的）
- 涉及的 run：        <run_id>（<日期>，动过 N 条）
- 判定误判：          M 条（列出 id）
- 回退方式：          部分（--records）/ 全量
- 回退前后检索验证：  被回退的 M 条已可召回；其余 N-M 条仍未召回
- 根因：              （阈值配错 / pin 规则失效 / 引擎 bug / 人为改库）
- 是否可预防：        （哪条体检判据本该先报出来；如果没有对应的，记下需要新加什么）
```

根因这一栏不要写"配置问题"四个字就完。要么给出具体是哪个参数从多少改到多少，要么写"没查出来"。
