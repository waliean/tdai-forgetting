## 三条值得单独记住的结论

### 1. dedup 不算访问，而且「不能下沉」

`084bed45` 上 dedup 已经和检索共用同一个共享函数 `l1-candidate-recall.ts:43 recallL1Candidates`。实测 dedup 在 37 小时窗口里驱动了 20 次候选召回，而显式检索只有 15 次——下沉埋点会被写入路径放大 **+133%**。这是「埋点必须留在 `executeMemorySearch`」的第二个硬理由（第一个是 rank 语义）。

### 2. 只报 p99 会漏掉一半答案（B4）

衰减/遥测的代价在 p99 上**测不出来**：三轮独立实验的 p99 差值符号翻转（+0.0760 / −0.0410 / +0.0471 ms）。但配对分析（同迭代序号 = 同 query）显示接线后在 **81.0%–84.5%** 的样本上更慢，配对均值 **+0.1394 / +0.1392 ms**——两轮几乎完全重合。

完整答案：**代价是真的（约 +0.14ms，约为基线 1.02ms 的 13.6%），但远在 5ms 阈值之下。**

### 3. `reordered` 不是「衰减开没开」的函数（B5）

`reordered` 量的是「融合顺序与年龄顺序的不一致程度」。RRF 在 45 个候选上跨度约 1.63×，乘数跨度约 1.5×，两者方向一致时互相抵消。所以翻转表里 `reordered` 从 10 降到 6 再降到 0，是**年龄项被稀释**，不是衰减失效。

**推论**：拿 `reordered` 的绝对值判「衰减强不强」不可靠；只能 ①看它是否恒为 0（查症状）②与自己上一次的读数比趋势。**跨语料比较无意义。**

## 五条环境坑（命令都返回 0，损害落在别处）

1. **PowerShell 的 `git diff > file` 产出 UTF-16LE 且 exit=0。** B2 实现者踩到；正式产物一律改走 Node `writeFileSync`。
2. **`Get-Content` 与 `Select-String`/node 对同一个 `.ts` 文件报的行号不一致。** `auto-recall.ts` 上 `Get-Content` 数出 1008 行、node 1018 行；偏移是**累积**的（+7 → +8 → +10）而非常数。取行号一律用 `Select-String` 或 node。
3. **`git apply` 在非 git 目录里静默不落盘。** 本轮实际踩到：把上游 `MemoryCore` 子树拷进 `%TEMP%` 后 `git apply 0104`，`--verbose` 逐个报 `Skipped patch '...'`、`exit=0`，而文件一个都没写；同样一棵树在 `git init` + 一次 `git add` 之后行为立刻正常（`--check` 全过、文件按预期生成）。要在临时树上验证补丁，先 `git init`。
4. （前几轮已记）`docker logs` 只钉 `--since` 不钉 `--until`，窗口随时钟增长，结论不可复现。
5. （工具口径）`planweave submit-review` 的 verdict 枚举是 `passed` / `needs_changes`，不是 `pass`。
