# 项目总览 — 2026-11-06

给第一次接手这个仓库的人。读完这一页，应该知道它是什么、做到了哪一步、哪些结论有证据、哪些还没有。

## 一、这是什么

给 TencentDB Agent Memory（tdai）的 L1 记忆加一层**可审计的遗忘策略**：保留打分、pin 语义、冗余淘汰、软删除 + 审计、失效标记、参数校准。

引擎在本仓库（`src/`），真正部署到上游的部分是 `patches/` 里的五份补丁（0101–0105），叠在 `E:\TencentDB-Agent-Memory` 的目录式 `store/sqlite/` 那一代代码上。

**核心立场**：「遗忘」是离开可召回集（`state` 变化 + 视图过滤），不是删字节。所有动作都进审计，审计只增不删，回退靠审计里的指纹。

## 三、有证据的结论

下面每条都指向一份带数字的报告，不是印象：

1. **衰减在冷启动语料上是净损失。** snapshot 上强制开门 precision 掉 13.3 个点（0.2375 → 0.1042）。这是 `minTrackingCoverage` 门槛存在的唯一理由。
2. **`halfLifeDays` 的平台是 5–14 天。** pinRecall 在这个区间不变（synthetic 0.833），越过 30 天开始下滑，90 天掉到 0.458。默认值从 30 改到 10。
3. **`clusterThreshold` 是悬崖参数。** 0.4 时吞掉 93.6% 的语料，0.6 距悬崖只有 0.2。默认值改到 0.7。另外它对**长文本完全失效**——超过 400 字走块级覆盖率，不看这个阈值。
4. **4-gram Jaccard 对长文本必然稀释。** 100 字前缀对 1200 字文档只剩 0.111。块覆盖率方案真重复召回 60/60、误合并 0/7080；分档阈值误合并 9.4%，被否。
5. **访问追踪的代价是 +0.139 ms**（基线 1.02 ms 的 13.6%），在 5 ms 阈值内。
6. **LLM 判据的误标率 70.6%–88.2%**，三个金标准口径都远高于 5% 门槛，所以 gate 拒绝 apply。而且两位标注者一致率只有 72%（κ=0.268）——**任务本身的标注噪声比门槛还大**。

## 四、没有证据的部分

这一节比上一节重要。

1. **没有真实模型跑过。** 本机只有 `bge-m3`（embedding），没有 chat 模型和 `OPENAI_API_KEY`。LLM 判据的全部数字来自 stub 与自建 HTTP 端点。
2. **没有人类标注。** C 的两位标注者都是 AI，且同一底层模型，72% 不能外推为人类一致性。
3. **回退后的“可召回”无法验证——而且原因是根本的。** E2 的容器演练证实了选择逻辑与审计，但补验时发现**生产容器跑的是没打过补丁的镜像**（无 `invalid_at` / `l1_recallable` / `state` 引用，镜像构建于 2026-10-26）。实测：把一条 active 记录改成 `archived` 后重启，它**仍然出现在检索结果里，分数一模一样**。所以“归档 → 不可召回”这个前提在当前环境不存在，E2 那半句是**阻塞**而不是待办，见 [可召回性验证](../experiments/可召回性验证-2026-11-06.md)。
4. **补丁没在真实目标树 apply 过，也没部署过。** 0104 改过两次（D4 同步数值、修 fold 时钟），每次只做了 hunk 自洽校验（24 hunks / 0 mismatch），没做真实 `git apply`。更关键的是第五节第三条：生产容器跑的镜像里**根本没有这些补丁**。
5. **`blockSimilarity` / `blockCoverage` 是新的拍的数。** D5 引入的这两个门槛（都 0.8）控制所有超过 400 字的重复判定，没有扫描过敏感度。
6. **分位退休只在访问追踪接通后才会发生。** `retirePercentile` 默认 0.1，但只在 decay 门开时生效；一个从未采集过访问数据的部署只会 archive，永远不会 retire。

## 五、几个会踩的坑

- **改一个参数会改变另一个参数是否生效。** floor 从 0.3 降到 0.2 把分数下界从 0.471 拉到 0.401，`archiveThreshold` 0.45 因此从"从不命中"变成"命中 83 条"。**改默认值之后必须重跑扫描**，D4 报告里踩过这个。
- **`avgScore` 的量纲变过。** floor 降 0.1 让它整体下移 0.1，历史绝对数值不可比。
- **D3 的数据在 D4/D5 之后重跑过一次。** 第一版数据已作废，看报告开头的时间戳。
- **补丁是 byte-exact 产物。** 改其中的代码必须同步 hunk 行数，加一行注释就会让 `git apply` 失败。
- **容器运行中改库会撞 `disk I/O error`。** 不是锁等待，是连接坏掉，必须停容器再改。
- **生产容器跑的是未打补丁的上游镜像。** `agentmemory/memory-core:latest`（构建于 2026-10-26）里 grep 不到 `invalid_at` / `forget_reason` / `l1_recallable`，检索完全不看 `state`。所以现在在生产上“归档”不会影响召回。没有确认新镜像之前，任何“遗忘在生产生效”的说法都是错的。
- **选召回验证样本必须先确认它有向量。** 854 条 active 里只有 556 条在 `l1_vec_rowids` 里；没向量的记录向量检索天然看不到，拿它当测试样本会得出“回退无效”的假结论（本轮演练里就出现了一次）。
- **`--rules` 这类未知参数曾被静默忽略并执行全量回退。** 已修（exit 1），但同类"参数拼错就扩大影响面"的设计值得继续警惕。

## 七、一句话

机制是完整的、被测量过的、可回退的；**但它还没在真实模型和真实人类判断下跑过**，而 C 画布的实测恰恰说明"什么算取代"这件事本身噪声很大。上线前的第一件事不是调参，是找人确认这个判断标准。
