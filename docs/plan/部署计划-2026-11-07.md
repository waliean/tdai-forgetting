## 一、P0：0105 的部署顺序 bug（必须在部署前修）

**这是本次核对最重要的一条。**

`0105-l1-invalid-filter.patch` 加了这一行，**没有 try/catch**：

```ts
this.db.exec("CREATE INDEX IF NOT EXISTS idx_l1_invalid_at ON l1_records(invalid_at)");
```

但**五份补丁里没有任何一份创建 `invalid_at` 列**——只有本仓库的 `src/migrate.ts` 创建它。

实测（在真实生产库副本上，按代码执行顺序复现）：

```
stock columns: NO state / NO invalid_at
after 0101 ALTERs: has state = true | has invalid_at = false
0105 CREATE INDEX threw: no such column: invalid_at
=> initSchema would THROW -> VectorStore degrades to no-op mode
```

`initSchema` 抛异常被上层 catch 成 **degraded 模式**（所有操作变 no-op），日志只写一行 error。后果是：**打补丁后的容器如果先于 `migrate` 启动，向量检索会静默死掉，而进程照常 health。**

更隐蔽的是第二层：即使把 index 那行包进 try/catch，`CREATE VIEW ... invalid_at IS NULL` 在 SQLite 里**建的时候不校验列**，`SELECT` 时才报 `no such column: invalid_at`。实测确认。也就是说视图本身也会变成一颗哑弹。

### 修法（待批）

新增 `0106-l1-invalidate-columns.patch`：

1. 在 0105 的 index 之前补两条**带 try/catch** 的 `ALTER TABLE ... ADD COLUMN invalid_at / superseded_by`（与 0101 的写法一致）；
2. 顺手把 0105 那条未保护的 index 也包进 try/catch；
3. 补一个测试：在 stock 库（无 `invalid_at`）上跑补丁后的 `initSchema` 序列，断言不抛且视图可读。

**这一条不修，部署就是不可回退的静默降级。** 优先级高于其他全部。

## 二、P1：补一个 `migrate` 命令

`node src/cli.ts migrate` 现在报 `unknown command`。`migrate()` 只在 `applyPlan` 内部被调用，意味着：

- 运维没法单独迁移；
- 部署 runbook 只能靠"先跑一次 apply"来触发迁移，而 apply 本身会改数据。

**加 `migrate --db <path> [--dry-run]` 子命令**，只做 schema 迁移、不动记录，输出与 `MigrationResult` 一致。这是 P0 修复的配套——有了它，"先迁移、再起容器"才是一条可执行的路。

## 三、P2：构建并切换生产镜像

前置：P0、P1 完成。

### 步骤

1. 在 `084bed45` 的 worktree 上按序应用 0101→0106（已在 `.scratch/deploy-084` 验证 0101–0105 全部 `exit 0`）；
2. `docker build -t agentmemory/memory-core:forgetting`（A 阶段实测约 13 分钟；`node:22-slim` 可经 `docker.1ms.run` 镜像拉取，npm 在 build 内可达，已实测）；
3. **停容器 → 跑 `migrate` → 起新镜像**；
4. 验证（见下）。

### 关键约束

- **必须先 migrate 再起容器**，否则命中 P0 的降级。虽然 P0 修完容器能自愈，但顺序仍应是"显式迁移、可见结果"。
- **`PULL=1` 会把 `latest` 拉回上游未打补丁的镜像。** `_lib.sh` 的 `pull_image` 在 `PULL=1` 时无条件 `docker pull`。要么把打补丁的镜像打成独立 tag（`memory-core:forgetting`）、改 `.env` 的 `MEMORY_CORE_IMAGE`，要么永久禁用 `PULL=1`。**建议前者**，别覆盖 `latest`。
- 生产库现 26.5 MB，先做一次 `sqlite3 .backup` 或停容器复制，保留回退点。

### 验证清单

| 检查 | 命令/证据 |
|---|---|
| 容器内能 grep 到补丁 | `grep -rl invalid_at /app/src` 非空 |
| 迁移把列加上 | `PRAGMA table_info(l1_records)` 含 `invalid_at` / `superseded_by` |
| 视图可读 | `SELECT COUNT(*) FROM l1_recallable` 不报错 |
| 检索仍工作 | `/v3/atomic/search` 返回非空、`strategy` 非 none |
| **归档真的不可召回** | 取一条有向量的记录置 `archived` → 检索应消失 |
| 回退仍可召回 | `rollback-forgetting.mjs --records <id>` → 检索应恢复 |

最后两条就是 E2 欠的那半句，P2 完成后一并结清。

## 四、P3：补回 `bge-m3`，否则向量路径永远是死的

`ollama list` 为空，生产报 `model 'bge-m3' not found`，检索全程走 FTS 回退。

这直接挡住两件事：

- P2 验证清单里"归档真的不可召回"——向量路径不工作时，测的是 FTS 过滤，不是向量过滤；
- 之前所有 `bench/eval-embedding.ts` 相关的结论都建立在 bge-m3 存在的前提上。

**决定点：重新拉 `bge-m3`（约 1.2 GB）还是换嵌入服务。** 拉回来最省事，但要占带宽和磁盘；换 provider 要改 `.env` 与 `tdai-gateway.yaml` 的 `embedding` 段。**需要阁下拍板。**

## 五、P4：两个新引入的"拍的数"

D5 引入的 `blockSimilarity` / `blockCoverage`（都 0.8）控制所有 >400 字的重复判定，**从没扫过敏感度**。`clusterThreshold` 对长文本已完全失效，这两个成了长文本唯一的旋钮。
