# 项目开发计划（2026-10-26）

从"引擎测过"走到"生产在跑、且有数据证明它没变坏"。

现状见 [项目现状与交接](../status/项目现状与交接-2026-10-26.md)。一句话：四层机制已经实现，118 个测试全绿；补丁在旧基线（`5299c00`）上应用、构建、容器内冒烟都过了，回退也演练过两遍；旧补丁的目标树已非上游现状（`65730e9` 上 3/4 应用不了），进了镜像的 0003 衰减接线也是死代码。**画布 R 已把这批补丁按新布局重做成 `0101`–`0103` 并对基线 `084bed45` 逐层应用通过**（记录见 [补丁重做](../design/补丁重做-2026-10-28.md)）。但**仍然没有任何补丁能上生产**：三份补丁只提交到本地 `83db099`（未推送），`access_count` 没有写入方，真实生产数据上 decay 会自动降级为不重排。下一个入口是画布 B `access-trace`。

## 目标

1. 补丁能在真实 MemoryCore 上落地，且可回滚。
2. 访问追踪接进 gateway，让冷启动门槛有机会打开——不接的话，衰减在真实部署里等于不存在。
3. 过期结论用显式失效标记处理，不再依赖时间衰减这个代理。
4. 默认参数由多语料校准得出，附带敏感度区间，而不是拍脑袋的 10% / 30d / 0.6。

## 非目标

- **L0 / L2 / L3 的淘汰**。四层语义不同，L0 是证据、L2 是结构、L3 是提炼，套同一个分数是错的。
- **自动调度**。阈值该先被人工审几轮；定时任务在阈值未校准时等于放大器。
- **物理删除**。销毁证据，需要单独的人工确认流程，不属于自动策略。
- **换框架**。调研结论已经否掉，成本高于加几列。

## 前提与假设

已验证：

- 822 条真实 L1 上，引擎能读出、能打分、能出计划、能软删除并留审计（快照副本上端到端跑通）。
- 冷启动门槛有效：强制衰减掉 3.5 个点，按门槛不掉。
- pin 中性 1.0 优于 1.5 与"从候选池移除"。

**未验证，风险全集中在这里：**

- ~~补丁能否 apply~~ **已验（在旧基线上）**：手写版全部无效，重做后四份在 `5299c00` 上依次应用成功、`build:plugin` 通过、被改文件 0 类型错误。详见 [补丁落地验证](../design/补丁落地验证-2026-10-26.md)。**限定**：那份树已不是上游现状，结论不可外推到 `65730e9`。
- ~~视图能否被检索路径替代~~ **已验且假设不成立**：两条路径都不读视图，归档后的记录仍可召回；已新增 0004 补丁用 JOIN 堵住，并加了 5 个回归测试。
- ~~容器内行为是否可信~~ **已验**：A4 容器内冒烟通过（REV-001），归档不召回与候选窗口回填都是实测，见 [补丁落地验证](../design/补丁落地验证-2026-10-26.md) 第八节。
- ~~回退是否可行~~ **已验（在补丁树上）**：A5 两遍演练 6.5 s / 13.9 s，52 条全部恢复。但演练对象是旧补丁树，生产是目录式布局，上线前需同口径再演。
- ~~容器内 core 是否已有 `access_count` 列~~ **已验（2026-10-28）**：生产镜像里没有；0101 建了列（`NOT NULL DEFAULT 0`），但**全树没有写入方**，所以真实数据上它恒为 0。写值方在画布 B。
- `appendRecall` 接进检索路径后对 p99 延迟的影响。追加一行 JSON 应该很便宜，但没测过。（画布 B 的 B4 验收项）

这些假设不成立的话，后续阶段的顺序会变。所以阶段一必须先做。

## 阶段划分

五个画布，依赖是硬约束，不是排期偏好：

```
A 补丁落地验证 ──┬──> B 访问追踪接线 ──┐
                │                      ├──> D 参数校准
                └──> C 失效标记 ───────┘
                                        └──> E 运维闭环
```

**A 是唯一的地基。** 补丁打不进去，B 和 C 都是在假设的代码上改。

**R 插在 A 与 B/C 之间**（上图未画，见「R 阶段收口」与「执行载体」）：A 的补丁对着旧布局，目标树漂移之后必须按新布局重做，R 就是那一步。**R 已完成**，所以 B 与 C 现在都可以开。

**B 与 C 可并行**，但共享 `l1_records` 的 DDL，两边都要加列。约定：B 只加 `access_count` / `last_access_time`（旧 0001 建过，重做后的 0101 也建了），C 加 `invalid_at` / `superseded_by`，两组列互不重叠，DDL 分两个补丁顺序合并即可。

**D 依赖 B 与 C**，校准需要真实访问数据和真实失效标记。**E 最后**，它把 A–D 的结果固化成可重复的操作流程。

## 画布 A：补丁落地验证

**为什么单独成一个画布**：这是唯一会碰 upstream 代码的地方，也是唯一可能推翻前面所有假设的地方。它必须能在不动生产的前提下完成。

| Task | 目标 | 验收 | 关键文件 |
|---|---|---|---|
| A1 补丁可应用性 | `git apply --check` 通过 | 在 upstream 干净工作树上 dry-run 成功，记录冲突点 | `patches/0001-0003` |
| A2 独立构建 | MemoryCore 能编译 | `npm run build` 出 dist 无错 | `MemoryCore/tsdown.config.ts` |
| A3 召回视图兼容 | ~~视图能被两条检索路径替代~~ **归档后的召回路径必须逐条堵住** | 快照副本起容器，召回仍返回结果，数量与基线一致；且归档记录不再从 FTS 与向量两条路径漏出 | `core/store/sqlite.ts` |
| A4 容器内冒烟 | 真实检索路径走一遍 | 容器 healthy，`memory_search` 返回 5 条，日志无 warn | 部署脚本 |
| A5 回退演练 | 能退回原状 | 回退后召回恢复（`scripts/rollback-forgetting.mjs` 恢复后同一 query 的 id 列表逐条一致） | runbook |

**A3 的验收口径改过，原因要留着。** 原口径是"把召回查询换成 `l1_recallable` 视图，归档记录就自动消失"。实测这个前提不成立：`searchL1Fts` 直接查 `l1_fts`、`stmtGetMeta` 直接查 `l1_records`，两条路径都不读视图，归档记录照旧被召回（视图本身是对的，只是没人用）。所以口径换成"归档后的召回路径必须逐条堵住"，并因此多出第四份补丁 0004（FTS 查询加 JOIN 过滤、`stmtGetMeta` 改查视图），配 5 个回归测试。细节在 [补丁落地验证](../design/补丁落地验证-2026-10-26.md) 第四节。

**验收口径**：A3/A4 必须在**数据库副本**上做，不能动生产库。做法是 `VACUUM INTO` 一份快照，把容器挂载指向副本。

**已知难点**：`searchL1Vector` 里有 `ZERO_VEC_BUFFER` 逻辑，跳过零向量依赖 KNN 返回的 NULL distance。把表换成视图后，KNN 仍从 `l1_vec` 取全量候选再 join，可能召回到已归档记录的 id 却拿不到元数据——这个分支必须显式测。

**Review gate**：A3 通过后评审一次。理由：改了 upstream 查询路径，且涉及"归档记录会不会漏进召回"这类静默错误。

## 画布 B：访问追踪接线

**为什么重要**：不接这个，覆盖率永远是 0，门槛永远关着，前面所有衰减工作在真实部署里都是死代码。

| Task | 目标 | 验收 | 关键文件 |
|---|---|---|---|
| B1 采集点定位 | 找到唯一该埋的位置 | 明确在 `executeMemorySearch` 返回前，而非每条 hit 的路径上 | `core/tools/memory-search.ts` |
| B2 接入 appendRecall | 检索后追加日志 | 单测：一次检索日志多一行；写失败不影响返回 | `src/recall.ts` |
| B3 离线折叠命令 | 日志转计数器 | CLI `forget fold`；折叠后日志重命名，重复折叠不双计 | `src/cli.ts` |
| B4 延迟影响 | 量化开销 | 200 次检索前后 p50/p99 对比，写进报告 | bench |
| B5 覆盖率爬升 | 真实数据验证门槛 | 累积几天后覆盖率超 10%，日志出现 `decay=on` | 观测 |

**落点已定**：埋在 upstream 的 `executeMemorySearch` 返回前（改 `MemoryCore/src/core/tools/memory-search.ts`），一处同时覆盖 MCP 工具与 HTTP `POST /v3/atomic/search`。auto-recall 与 dedup 不在 v1 范围：dedup 本就不算访问；auto-recall 走直调路径，漏它的代价要量化成覆盖率低估量级，并留下未来接入方案。

**验收口径**：B4 必须给真实数字。p99 增加超 5ms 就改成批量异步写。

**注意**：`appendRecall` 只记 top-N（默认 10）。记全量候选会把计数器变成"出现在候选池里"，不是"被用到"。

## 画布 C：失效标记

**为什么做**：实验三已经证明它比时间衰减强——衰减把最新复述顶到第一（0 → 1.000），但挤不掉过期副本（仍是 2 条）；显式标记两件都做到。

| Task | 目标 | 验收 | 关键文件 |
|---|---|---|---|
| C1 字段设计 | 加 `invalid_at` / `superseded_by` | DDL 幂等，旧代码不读即无影响 | `src/migrate.ts` |
| C2 判据来源 | 谁判"新结论推翻旧结论" | 人工命令为基线；判据文档含 LLM 方案设计（实现见 C6） | `core/record/l1-dedup.ts` |
| C3 召回过滤 | 失效记录不进结果 | 单测覆盖"失效与其替代者同时命中" | `sqlite.ts` |
| C4 计划集成 | 失效优先淘汰 | planner 新增 pass，理由进审计 | `src/planner.ts` |
| C5 效果复测 | 受控语料复跑实验三 | `stale-in-window` 从 2.00 降到 0.00 | `bench/supersede.ts` |
| C6 LLM 失效判据 | shadow 先行，误标率 < 5% 才生效 | shadow 不改 `invalid_at`；50 条复核集；门槛未达时 apply 被拒 | `src/llm-criteria.ts` |

**关键决策点**：C2 用 LLM 判断会引入成本和误判。误判的后果是把**仍然有效的结论标失效**，比漏标严重。已拍板（见文末「已拍板」）：人工命令是基线，LLM 判据要做，但先 shadow（判定写审计、不改 `invalid_at`）+ 50 条人工复核 + 误标率 < 5% 才允许 `--mode=apply`。实现落在 C6。

**Review gate**：C2 评审。理由：数据语义变更加 LLM 参与判定，两个都是静默错误高发区。

**为什么做**：10% 门槛、30 天半衰期、0.6 Jaccard 都是拍的。拍的参数换语料后会失效，而且失效时没有任何信号。

**验收口径**：D4 改默认值必须同时改 `test/` 里的期望值，PR 里贴前后对照。参数改动没有对照数据不予合并。

## 优先顺序与理由

按"能推翻多少已有假设"排，不按工作量：

1. **A**：推翻则 B/C 全部重做。
2. **B**：推翻"衰减在真实部署里有用"这个前提——不接追踪的话它确实没用。
3. **C**：实验三已证明它比现有机制强，但实现成本最高。
4. **D**：没有 D，前三个的参数都是猜的。
5. **E**：固化，不产生新认知。

A 与 B 之间有一个**决策点**：若 B4 测出追加日志的延迟不可接受，要改成进程内缓冲加批量落盘，这会改 `src/recall.ts` 的接口，进而影响 CLI 的 fold 命令。这个决策必须在 B4 之后、B5 之前做。

## 风险与回退

| 风险 | 触发信号 | 回退 |
|---|---|---|
| 补丁无法应用 | `git apply --check` 报冲突 | 改成运行时开关，不动 upstream 源码 |
| 视图破坏召回 | 召回条数少于基线 | 视图改回表，查询里加 `state` 过滤 |
| 折叠双计 | 同一日志被处理两次 | 日志重命名已防；再加 fold_id 幂等键 |
| 误标失效 | 有效结论被标 invalid_at | 只软标，召回可回看 |
| 延迟超预算 | p99 增加超 5ms | 改批量异步写 |

所有回退都不需要恢复备份——这是软删除设计的直接好处，也是当初不在 `apply` 里做物理删除的原因。

### 2. 两件推翻 A 阶段前提的新事实

1. **补丁目标树漂移。** 在 `origin/feat/server_team`（`65730e9`）上逐份 `git apply --check`：0001 FAILS（`store/sqlite.ts: No such file or directory`）、0002 APPLIES（纯新增）、0003 FAILS（`memory-search.ts:14` 冲突）、0004 FAILS（同 0001）。本地检出 `5299c00` 落后 origin 46 个提交，上游已把 `store/sqlite.ts` 重构成 `store/sqlite/` 目录。
2. **0003 是死代码。** 补丁进了镜像，但 `v2-router.ts:1210` 与 `tdai-core.ts:439` 调 `executeMemorySearch` 时都不传 `decay`，`memory-search.ts` 的重排只在 `if (decay)` 里跑；A4 容器日志里 `[decay]` 命中 **0 次**（当时的观察，日志已随容器删除，不可复算）。四层机制里的"检索排序"这一层在真实容器里从未执行过。可复算的代码依据与行号见 [补丁落地验证](../design/补丁落地验证-2026-10-26.md) 8.10 末段。
